# 第三阶段：PCM 旁路原型测试报告（电脑端 · 实测）

对象：`my-doc/03_uds_test/` 下的 AF_UNIX 原型（`uds_sink` + `uds_source` + 编排/校验脚本）
性质：**电脑端传输机制实测**。真机一次都没跑（真机环节见 §10）。
配套文档：`03_pcm_bridge_design.md`（架构与选型）、`03_script_audit.md`（既有脚本审查）

## 0. 一句话结论

> 在电脑上，**1280 B / 40 ms 的 PCM 帧通过 AF_UNIX 连续跑了 600 秒，15000 帧零丢失、零损坏、零乱序，
> 端到端延迟 P50 = 1.10 ms / P95 = 2.04 ms**；接收端被冻结 3 秒时，发送侧只丢 68 帧、节拍误差 3.07 ms，
> 而同样场景下"生产者直接阻塞发送"的对照版把节拍拖了 **2693 ms**。

判据逐条对照见 §8。

## 3. 被测对象

```
uds_source（模拟 hook 侧）                    uds_sink（模拟 AI 助手侧）
┌──────────────────────────────┐             ┌──────────────────────────────┐
│ 生产者线程 40 ms 绝对 deadline │             │ select(100 ms) + recv         │
│   → 组装 1320 B 帧           │             │   → 重组 / 魔数重同步          │
│   → ring_push（无锁 SPSC）    │   AF_UNIX   │   → magic/ver/len/crc 校验     │
│ 消费者线程                   │────────────►│   → 确定性载荷逐字节比对        │
│   → ring_pop → send 非阻塞    │  1320 B/帧  │   → seq 缺口 / 重复 / 乱序统计  │
│   → EAGAIN/ENOBUFS = 丢+计数  │             │   → 延迟分位、接收间隔          │
└──────────────────────────────┘             └──────────────────────────────┘
```

协议：40 B 头（magic/ver/flags/hdr_len/seq/ts_us/frames_total/rate/ch/bits/payload_len/crc）+ 1280 B 载荷。
上表 12 个字段全部由两端**各自独立实现**（C 手写序列化、Python `struct`），能对上说明协议描述无歧义。

参数：16000 Hz · 单声道 ch0 · 16 bit · 640 样本/帧 · 40 ms/帧 · 25 fps · 1320 B/帧。

### 5.2 baseline：10 分钟长稳

- 15000 帧 / 600.0 s，序号 0…14999 **完全连续**，`missing=0`、`dup=0`、`reorder=0`、`reject=0`、`resync=0`。
- 字节数 19,800,000 = 15000 × 1320，与帧数严格自洽。
- 速率 **32.23 KiB/s**，理论值 31.25 KiB/s × (1320/1280) = 32.23 KiB/s —— 头部开销 3.125% 对得上。
- 延迟：均值 1.24 ms，**P50 1.096 ms，P95 2.041 ms，P99 2.103 ms，max 14.66 ms**。
  P50≈1 ms 就是发送线程 1 ms 空闲轮询的量化结果（§12 修正 #1）。
- 入环耗时 `push_us_max = 45 µs`、平均 **0.2 µs** —— 这就是"hook 内允许做的全部工作"的真实量级。
- 节拍误差 `tick_late_max = 38.4 ms`，`tick_late_avg = 101 µs`：**只有 1 次**超过 40 ms 的调度抖动，
  同期主机正在编译与写文件（§9）。`tick_missed = 0` 表示没有任何一次落到"丢一整帧"的程度。

### 5.3 stall vs naive：本阶段最关键的对照实验

两侧 socket 缓冲都压到 8 KB，第 8 秒把**接收端冻结 3 秒**：

| | ring + 非阻塞发送（设计） | 生产者直接阻塞发送（对照） |
|---|---|---|
| 丢帧 | 68 帧（`send_drop_wb=68`） | 0 帧 |
| **入环/发送耗时 max** | **2 µs** | **2,693,724 µs（2.69 s）** |
| **节拍误差 max** | **3.07 ms** | **2653.7 ms** |
| 帧时间戳最大间隔 | 2759.95 ms（丢帧造成） | 2693.77 ms（**生产者被冻住**） |
| 收到帧数 | 932 | 933 |

同一台机器、同一份冻结脚本，只改"发送写在哪"：一个把 68 帧丢掉继续跑，另一个把 40 ms 节拍冻了 2.7 秒。
**这就是"旁路不能阻塞原厂录音线程"的定量证据。**

### 5.4 ringfull：环满

环容量调到 4 帧，第 5 秒让发送线程被调度走 1 秒：

- `ring_drop = 22`、`depth_max = 4`（正好塞满 4 槽，之后全部丢弃）→ 行为符合"满则丢"。
- 接收端 `missing = 22`，与 `ring_drop` **一一对上**。
- 生产者 `push_us_max = 24 µs`：环满时入队是"返回 0"，不是等待。
- 延迟 max 1001 ms = 发送线程被停掉的那 1 秒（帧在环里等），复现性很好。

### 5.5 skip：缺口统计的准确性

每 100 帧人为丢 1 帧（模拟上游丢帧）：

- 生产 500、入环 495、环满丢 5 → 序号 0/100/200/300/400 缺。
- 接收端：`seq_first=1`、`miss_before_first=1`、`missing=4` → **总缺 5，与实际注入完全一致**。
- 这条同时验证了"首帧之前的缺口"也被正确统计（早期版本漏掉了这一项）。

### 5.6 slow / slowbuf：延迟上限由谁决定

消费者故意变慢（每帧 60 ms > 到达间隔 40 ms）：

| 配置 | P50 | P95 | max | 发送丢弃 | 结论 |
|---|---|---|---|---|---|
| 默认缓冲 | 1664 ms | 2968 ms | **4298 ms** | 124 | 内核替我们排了 4 秒队 |
| `SO_SNDBUF = 8192` | 296 ms | 427 ms | **455 ms** | 175 | 上限被压到 ≈ 缓冲/带宽 |

**这条是设计缺陷的暴露**：原以为延迟上限由我们自己的 64 帧环形缓冲决定（2.56 s），实测发现
**内核 socket 缓冲才是真正的队列**，不显式设 `SO_SNDBUF`，一次助手侧卡顿就会把"4 秒前的语音"送进来。
设计文档 §5.5 已据此改稿：发送/接收两端都要显式设小，并按 `ts_us` 丢弃过期帧。

## 8. 结论

**能做**：把 16 kHz 单声道 PCM 用独立通道稳定送出去，且发送侧不会被接收侧拖死。
**还没做**：真机上的任何一步（§10）。

支撑证据链（按强度排序）：

1. **600 秒 15000 帧零丢失**（baseline，§5.2）
2. **停摆 3 秒只丢 68 帧、节拍误差 3.07 ms**，而阻塞版被冻 2.69 秒（§5.3）
3. **独立实现逐帧校验全 PASS**，缺口数与被注入的丢帧数完全一致（§5.5、§6）
4. **延迟可量化**：P50 1.10 ms / P95 2.04 ms / P99 2.10 ms（§5.2），且上限的决定因素已定位（§5.6）

## 9. 噪声与解释（不要把噪声当结论）

| 现象 | 解释 |
|---|---|
| baseline `tick_late_max = 38.4 ms`、`ts_delta` 最小 3.6 ms | 主机同时在做编译/文档 IO。`tick_missed=0` 说明没有丢整帧；3.6 ms 的短间隔是"绝对 deadline 不漂移"的正常追赶（上一拍晚了，下一拍就按原时间点补），不是抖动 |
| `ringfull` 也出现 1 次 42.8 ms 迟到 | 同一次外部负载；该场景 `push_us_max` 只有 24 µs，与被测代码无关 |
| sink 的 `gap_max = 81 ms`（baseline） | 接收进程被调度走的最大间隔；帧仍在内核缓冲里，没有丢（`missing=0`） |
| `slow` 场景的 `tsgap_max = 1200 ms` | 帧头时间戳间隔包含丢帧；只有 `missing=0` 的场景才能用它看节拍 |
| `naive` 的 P50 只有 41 µs | 因为帧直接落进内核缓冲，没有排队；代价是生产者被冻住——**延迟低不等于设计好** |

## 12. 测试驱动出的 4 处设计修正（都已回写设计文档与代码）

| # | 问题 | 症状 | 修正 |
|---|---|---|---|
| 1 | 发送线程空闲轮询写成 500 µs | Windows 上 `Sleep(500/1000)=Sleep(0)` → **占满一个核**（实测 419 s CPU / 410 s 墙钟） | 轮询改 1 ms，`tgz2_sleep_us` 最小 1 ms；CPU 降到 **1.3 %**，代价是 P50 延迟 ~1 ms |
| 2 | 首帧 deadline 多算一个周期 | 第一段帧间隔 80 ms，`ts_delta_max` 恒为 80 | `deadline` 初值改为"当前时刻"，间隔回到 39.9~40.1 ms |
| 3 | 重组缓冲只有 10.5 KB（8 帧），小于单次 `recv` 突发上限 | 慢消费者时 `recv` 一次拿 64 KB → 缓冲被清空 → **假 resync + 假 bad magic**（`slow` 曾报 2 次） | 缓冲改 256 KB，且 `recv` **直接读进重组缓冲**（零拷贝、读量受剩余空间约束）；`slow` 的 resync 归零 |
| 4 | 以为延迟上限由我们自己的环形缓冲决定 | 慢消费者下 P50 延迟 1.66 s / max 4.3 s | 定位为**内核 `SO_SNDBUF`**；显式设 8 KB 后上限降到 455 ms。设计文档 §5.5 增补"两端都要设小 + 按 ts 丢过期帧" |

第 3 条尤其值得记：如果不做"独立实现对账 + 慢消费者场景"，这个假 resync 会一直被当成"UDS 不可靠"。
