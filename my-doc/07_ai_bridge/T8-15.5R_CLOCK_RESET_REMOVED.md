# T8-15.5R 取消"时钟基准重置"自动受理

基线：`651c74760479895fbd7471d9c9763613b3333933`
本轮提交：`COMMIT_SHA_PLACEHOLDER`（main）

**结论**：审查意见成立。上一版的"大幅倒退 + 下一拍读到不小于候选的值就受理"这条路径，
本质上是"同一个异常序号读两次就开麦"——重复读到相同内容什么也证明不了，而 host 测试 B10
把它固化成了预期行为。本轮**彻底删掉自动基准重置**，换成"时间合理性 + 严格递增"两条硬规则，
并把 B10 那组测试改成"旧值重复读取不得触发"的负例。

---

## 1. 现在的判定（`android/tg_req_seq.h`）

```
读侧：tg_req_read()      空文件 / 半截 / 负数 / 夹脏字符 / 溢出 / 两份数字 -> 整条作废，不动基线
受理：tg_req_accept()
  seq < 1000                          -> TG_REQ_R_TINY     半截数字
  seq > now + 1.5 s                   -> TG_REQ_R_FUTURE   未来值（手工写进去的 epoch 等）
  seq < now - 120 s                   -> TG_REQ_R_TOO_OLD  不可能是"刚发出"的请求
  last_seq < 0                        -> "first"           受理
  seq > last_seq                      -> "new"             受理
  seq == last_seq                     -> TG_REQ_R_REPEAT   重复值，忽略
  seq < last_seq                      -> TG_REQ_R_BELOW    静默重设基线，**不触发**
```

**开麦只剩两种来源**：没有基线（守卫启动时文件是空的），或者序号比基线大且时间上说得通。
倒退最多只丢掉一条请求，永远不会在没有用户指令时开麦。

## 2. 为什么可以不要基准重置

- worker 与守卫**读同一个时钟**：`wu_now_ms()` 与守卫的 `mono_ms()` 都是 `CLOCK_MONOTONIC`。
  真机实测该内核 `MONOTONIC == BOOTTIME`（`MONOTONIC=153994000 BOOTTIME=153994000`），
  休眠期间照常走，两侧不会分叉。
- worker 重启后 `native_req_seq` 归零，但写入值是 `max(now_ms, last+1)` = `now_ms`，
  仍然比文件里的旧值大 —— **正常路径永远不会倒退**。
- 历史遗留脏基线（例如 T8-15.4b 之前手工写进去的 epoch 值）不需要靠"猜"来纠正：
  第一条真请求会以 `BELOW` 静默落地（丢一条），第二条开始正常触发。**自愈而不误开麦**。
