# T8-13.4 最小收尾修复：q==0（queue/inflight）接入会话超时保护

- 基线提交：`a5841aca27e3eea5934ae3b7a1a23d1350e5c75e`（T8-13.3 真机验证）
- 本轮性质：**纯主机侧代码修复 + 主机回归**，不操作真机，不重启 `:core`，不触碰原厂 KWS / ASR /
  音量媒体路由 / R13（R13-01）/ Hook 汇编桩。
- 结论：缺口闭合。`q==0 + stage=queue/inflight` 现在与 `q>0` 走**同一个** TTS 生命周期入口
  （`sc_on_tts_queued` → SPEAKING + 5 倍安全截止），不再存在"永久停在 PROCESSING"的代码路径。

---

## 一、审查指出的缺口（复述，逐条对上代码）

`ai_worker.c` `provider_attempt()` 成功分支里，`tts_enqueue()` 的三种返回：

| 分支 | 原行为 | 问题 |
|---|---|---|
| `q > 0`（新条目入队） | `sc_on_tts_queued()` → SPEAKING + 5×截止 | 正常 |
| `q == 0` 且 `stage=done/failed` | `sc_on_request_result(ok=1)` → 回 LISTENING + 1×截止 | 正常 |
| `q == 0` 且 `stage=queue/inflight` | **只保留等待，不调用任何生命周期入口** | **缺口** |

因为 `sc_on_submit()` 只把状态置为 PROCESSING、**不挂有效截止**，`sc_poll()` 也**不处理
PROCESSING 超时**（见 `session_ctrl.c:286` / `:298` 两处 deadline 判定，条件都不含 PROCESSING），
所以一旦 TtsExec 没有为该 event_id 发布 `playing`/`idle`，会话会永久停在 PROCESSING，
`request_active` 永久为 1，后续会话的 FOLLOWUP/CLOSING 也不会发生。

真机未自然出现 `q==0`（T8-13.3 报告已标 NOT OBSERVED），属静态可判定的残留路径 —— 本轮补齐。

---

## 二、修改一：`ai_worker.c`（q==0 三分类）

位置：`provider_attempt()` 成功分支，`q == 0` 内层。

```c
if (stage == done|failed)            -> sc_on_request_result(ok=1)            // 不变
else if (stage == queue|inflight)    -> sc_request_owns() 前置校验
                                        └ 成立 : sc_on_tts_queued()  // SPEAKING + 5×截止
                                        └ 不成立: 只记日志，不推进、不伪造 SPEAKING
else /* stage 为空/未知 */           -> 记 ANOMALY + note_error，
                                        sc_on_request_result(ok=1)           // 安全终结
```

要点对齐任务书三条：

1. **queue/inflight**：先确认"当前 `request_active=1` 且 request_id 与 `pend.event_id` 完全一致"
   （`sc_request_owns()`），再调用 TTS 生命周期入口。进入 SPEAKING 并启动 **现有** 的 5 倍安全
   截止；`event_id` 归属保留在 `sc_on_play_state()`，继续等真实 `playing`/`idle`。
   **不当作已播放完成**（不调用 `sc_on_request_result`，`request_active` 保持 1）。
2. **done/failed**：行为与 T8-13.2 完全一致（成功语义终结 → LISTENING + 1×窗口）。
3. **stage 为空/未知**：不猜"已播放"、不伪造 SPEAKING。按"本请求不会再有播放收尾"安全终结
   （LISTENING + 1×窗口，避免永久 PROCESSING），并同时留两处可观测痕迹：`always()` 打
   `ANOMALY tts idempotent hit with unknown stage`，`t6b_status_note_error()` 计入错误。
   若 TtsExec 之后确实播了，其收尾事件会以 `request_active=0` 的迟到回调被 `sc_on_play_state`
   过滤（测试 17.8 覆盖），不污染下一轮会话。

附带（同一入口的一致性）：`q > 0` 分支现在也检查返回值，归属不成立时打一条
`tts queued but request NOT owned`。播放本身由原厂 TtsExec 独立完成，不受影响，只是状态机不接管。

## 三、修改二：`session_ctrl.c` / `.h`（入口收紧）

新增只读判据（worker 与状态机共用，避免两处各写一套而漂移）：

```c
int sc_request_owns(const sc_ctx *s, const char *request_id);
/* 1 = 有活动请求 && 传入 id 非空 && 当前 request 非空 && 完全一致 */
```

`sc_on_tts_queued()` 收紧为：

| 输入 | 结果 |
|---|---|
| 活动请求 + id 完全一致 | 接受：SPEAKING + `5 × followup_timeout_ms` 截止 |
| 无活动请求 | 拒绝：`stale_callbacks++`，状态/request/deadline 全部不动 |
| 空 id / NULL id | 拒绝，同上 |
| 旧 id（prev_request 或陌生 id） | 拒绝，同上 |

`q>0` 的正常路径不受影响：生产链路上 `sc_on_submit()` 必然先于供应商成功（`uttq_pop_to_pend`
建 pend 时登记），此时 `request_active=1` 且 id 一致。

### 既有测试的一处必要修正（如实记录）

`[4] TTS 播放期间打断` 原先在"上一轮请求已被 `sc_on_request_result` 终结"之后直接调用
`sc_on_tts_queued(旧 id)` 并期待 SPEAKING —— 那正是本轮被禁止的"无活动请求也推进 SPEAKING"。
现在该用例先建立本轮的会话与请求（`sc_on_session_text` + `sc_on_submit`）再走真实 queued 事件，
语义不变（SPEAKING → 打断 → INTERRUPTED → 同请求 interrupted idle 接受 → 窗口关闭）。
**这是放宽行为被依赖的证据本身**：除它以外，全库没有第二处依赖宽松入口的调用。

## 六、本轮范围外的边界（未做，也不本轮做）

- **未部署真机、未重启 `:core`**：任务书明确"不操作真机"。因此设备上仍是 T8-13.3 的
  `0adf2cf7…`（`a5841aca` 状态的二进制），与本轮产物并存不冲突。下次上机时若要带本轮修复，
  需重新 push + `run_ai_worker.sh stop/start-deepseek`，并复跑 T8-13.3 §A/§B 的观察项。
- **q==0 / 死信 / TTS 失败重试路径在真机仍为 NOT OBSERVED** —— 本轮只闭合其代码路径与主机断言，
  不因此宣称"真机已观察"。要让真机自然命中 `q==0 queue/inflight`，需要构造"同一 event_id 二次
  入队"场景（例如在 TtsExec 消费前重放同一事件），属下一阶段的验证编排工作。
- **PROCESSING 仍没有通用截止**。这是有意保留的：PROCESSING 的退出由供应商终态（成功/死信）
  与 TTS 生命周期负责，本轮把"幂等命中后无入口"这条漏路接到 SPEAKING 截止上；其余进入
  PROCESSING 的路径都会在供应商终态处终结（T8-13.2 四情况）。给 PROCESSING 直接加超时会与
  长耗时模型请求冲突，不在本轮范围。
- `stale_callbacks` 在非活动窗口内因重复快照读取而累积（T8-13.3 已记录，2397 次），本轮未改。
