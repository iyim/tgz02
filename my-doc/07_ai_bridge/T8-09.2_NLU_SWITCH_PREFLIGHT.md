## 二、新 Supervisor 启动条件核对

### 2.1 必须使用的参数（不得省略 `--injector` / `--so`）

```bash
nohup /data/local/tmp/t6/tg_supervisor \
  --injector /data/local/tmp/t8/tg_injector \
  --so       /data/local/tmp/t8/libtg_hook.so \
  --name     com.alibaba.ailabs.genie.smartapp:core \
  --pidfile  /data/local/tmp/t8/tg_supervisor.pid \
  --log      /data/local/tmp/t8/supervisor.log \
  >/dev/null 2>&1 &
```

- supervisor **二进制**仍用 `/data/local/tmp/t6/tg_supervisor`（当前唯一一份，`17dec6e0…`；本轮不重编、不替换）。
- 省略 `--injector`/`--so` 的后果：落到 `DEF_INJECTOR=/data/local/tmp/t6/tg_injector`、
  `DEF_SO=/data/local/tmp/t6/libtg_hook.so`（`tg_supervisor.c:44-45`）→ 重启会把旧库注回去。

### 2.2 单实例锁的真实机制（本轮核对源码后的重要结论）

`acquire_single_instance(pidfile)`（`tg_supervisor.c:427-446`）：

```c
fd = open(pidfile, O_RDWR | O_CREAT | O_CLOEXEC, 0644);
if (flock(fd, LOCK_EX | LOCK_NB) != 0) {
    ... "another supervisor is already running (pid=%d, pidfile=%s)" ... 退出码 1
}
```

- 单实例锁是 **`flock` 在 pidfile 这个文件上**，锁的粒度是"**这个路径**"，不是全局。
- 因此 `/t6/tg_supervisor.pid` 与 `/t8/tg_supervisor.pid` 是**两把互不相干的锁**
  → **新旧两个守护可以同时运行，谁也不会阻止谁。**
- 推论（切换时的硬约束）：**"先停旧守护"不是可选项**。只要旧守护还活着，它会在 `:core` 重建后把
  `/t6/libtg_hook.so` 注进去；新守护随后注入 `/t8/...` 会因 basename 冲突失败（见 2.4）。
- 无残留锁风险：进程退出（含 `SIGKILL`）时内核自动释放 `flock`；优雅退出还会
  `flock(UN)` + `close` + `unlink(pidfile)`（`tg_supervisor.c:679-683`）。
  所以**旧守护被正常 kill 之后 `/t6/tg_supervisor.pid` 会消失**，这是预期行为，不是故障。
- pidfile 里的数字只是"展示用"，源码明确不依赖它判活（判活用 `kill(pid,0)`，`tg_supervisor.c:191`）。
  **操作时不要盲信这个数字**（PID 可能被复用）—— 每次都用 `ps -p <pid> -o ARGS` 复核身份。

### 2.3 三套守护的路径矩阵（互不冲突）

| 守护 | pidfile（锁） | 日志 | injector | hook .so |
|---|---|---|---|---|
| 旧 T6 | `/t6/tg_supervisor.pid` | `/t6/supervisor.log` | `/t6/tg_injector`（默认） | `/t6/libtg_hook.so`（默认） |
| 新 T8 | `/t8/tg_supervisor.pid` | `/t8/supervisor.log` | `/t8/tg_injector` | `/t8/libtg_hook.so` |
| TTS Guard | `/t7/ttsguard.sup.pid` | `/t7/ttsguard.sup.log` | `/t6/tg_injector` | `/t7/libtg_ttsguard.so` |

三者的 pidfile 与日志路径两两不同 → **互不阻塞、互不覆盖**。
TTS Guard 守护（4685）本轮**不修改、不停止**，其 `--so` 已固定指向 `/t7/libtg_ttsguard.so`。

### 2.4 同 basename（`libtg_hook.so`）造成的注入互斥

注入器的"是否已加载"判定是 **basename 子串匹配 maps**（`tg_injector.c:580-590` + `rc_maps_has`），
命中后 `dlopen(path, RTLD_NOW|RTLD_NOLOAD)`（`:676`）。因此：

| 场景 | 结果 |
|---|---|
| 进程里已有 `/t6/libtg_hook.so`，想注 `/t8/libtg_hook.so` | `already=1` → `NOLOAD` 查的是 `/t8/...`（未加载）→ **NULL → exit 17** |
| 进程里已有 `/t8/libtg_hook.so`，想注回 `/t6/libtg_hook.so` | 同上 → **exit 17** |
| 进程里没有任何 `libtg_hook.so` 映射 | `already=0` → `dlopen(RTLD_NOW)` 真加载 → 成功 |

**结论：切换与回滚都必经一次 `:core` 重启来清空映射，不能靠"换 injector 路径"直接替换。**

## 三、恢复方案（R1–R5，全部可直接执行）

> 通用四段式：**① 读 PID → ② `ps -p` 复核身份 → ③ 执行 → ④ 复核结果**。
> 通用判据（"当前 :core 里是哪一套"）：
> ```bash
> adb shell "su -c 'cat /proc/<CORE_PID>/maps'" | grep libtg_hook
> ```
> 路径 `/t6/` + inode **78644** = 旧；路径 `/t8/` + inode **63251** = 新。

> **串行原则（T8-09.3 新增，适用于 R1–R5 全部流程）**
>
> 1. 新 `:core` 出现后，**先等 TTS Guard Supervisor 完成注入**（上限 **30 s**），并确认 maps 里已有
>    `/data/local/tmp/t7/libtg_ttsguard.so`（inode **86583**）、`/t7/ttsguard.sup.log` 出现完成态；
> 2. 确认此刻**没有其它 Injector 正在操作该 `:core`**（`ps` 无 `tg_injector`、`TracerPid: 0`、日志尾为完成态）；
> 3. 之后才允许启动 Hook 守护（旧 T6 或新 T8，取决于回滚目标）；
> 4. **任何情况下都不允许两个 Supervisor 同时对同一个 `:core` 执行注入**；
> 5. 30 s 内 TTS Guard 没恢复 → 先按 **R5** 处理，**不要**先起 Hook 守护，也不要"两个一起上"。
>
> 原因见 §4.0：并发 attach 会打破 `world_frozen` 前提，而这正是写 NLU 入口补丁的唯一安全条件。

### R1：新 Supervisor 启动失败

**判据**（任一）：`ps` 里没有新守护；`/t8/supervisor.log` 出现
`fatal: cannot open pidfile` 或 `another supervisor is already running`；日志根本没生成。

**步骤**

```bash
# 1) 看新守护是否真的在（不要只信 pidfile）
adb shell "ps -A -o PID,PPID,ARGS | grep tg_supervisor | grep -v grep"
#    期望只剩 4685（TTS Guard）；若还有一个带 --so /t8/... 的，说明它其实起来了 → 转 R2

# 2) 若有残留新实例，按 argv 精确杀掉（不按数字猜）
adb shell "su -c 'kill <新守护PID>'"

# 3) 若这个 :core 是刚重启出来的：先等 TTS Guard 完成注入（≤30 s），再起 Hook 守护
#    （串行原则；判据：maps 有 /t7/libtg_ttsguard.so 且日志出现 inject end ... ok）
adb shell "su -c 'cat /proc/<CORE_PID>/maps'" | grep libtg_ttsguard
adb shell "su -c 'tail -3 /data/local/tmp/t7/ttsguard.sup.log'"
#    30 s 内没恢复 → 转 R5，**不要**先把 Hook 守护起起来

# 4) 【关键，修正 T8-09 的 R1 不完整】把旧守护恢复起来，不能让 :core 处于无守护状态
adb shell "su -c 'nohup /data/local/tmp/t6/tg_supervisor \
  --injector /data/local/tmp/t6/tg_injector --so /data/local/tmp/t6/libtg_hook.so \
  --name com.alibaba.ailabs.genie.smartapp:core \
  --pidfile /data/local/tmp/t6/tg_supervisor.pid \
  --log /data/local/tmp/t6/supervisor.log >/dev/null 2>&1 &'"

# 5) 复核：旧守护在、旧库被认领
adb shell "su -c 'tail -3 /data/local/tmp/t6/supervisor.log'"
#    若 :core 仍是切换前那个（里面已有旧库）→ 应看到 "already hooked: pid=... (state=1); skip install"
#    若 :core 已被重启过（里面没有 hook 库）→ 应看到 "inject end: ... exit=0 hooked=1"

# 6) 复核映射：必须是 /t6/ + inode 78644
adb shell "su -c 'cat /proc/<CORE_PID>/maps'" | grep libtg_hook

# 7) 功能复核（见 3.6 的统一检查表）—— 没做完第 6、7 步，不得宣称"已恢复"
```

> T8-09 的 R1 只写了"停掉新守护"，那是**不完整**的：停掉新守护后 `:core` 处于无人看管状态，
> 下次任何原因导致的 `:core` 重建都不会再被注入 Hook，AI 链路会静默失效。本版把"恢复旧守护 + 复核映射 + 功能复核"
> 纳入 R1 的必做项。

### R2：新 Injector 注入失败（exit 17 / 18 / 19 / 22 等）

**步骤**

```bash

# 3) 若 maps 里已经出现 /t8/libtg_hook.so（说明库进去了但后续失败）：

#    若 maps 里没有任何 libtg_hook：
#    → 先等 TTS Guard 完成注入（≤30 s，串行原则），再起旧守护（同 R1 步骤 4），
```

## 四、切换执行方案（10 步，**本轮不执行**）

> 前置：`:core` 重启需**单独审批**。执行人需在每一步之后核对"期望"，不符即停并按第三节对应 R 处理。
> **T8-09.3 核心约束：任何时刻只允许一个 Injector 操作 `:core`。**
> 新 `:core` 出现后，TTS Guard Supervisor 会先动手注入；必须等它**完全结束**（≤30 s）才允许启动 T8 Supervisor。

### 4.0 为什么必须串行（并发注入的真实危害）

注入器的工作方式（`remote_call.c` / `tg_injector.c`）：

| 阶段 | 代码 | 对目标进程做了什么 |
|---|---|---|
| 附加 | `rc_attach`（`remote_call.c:561`），`ptrace(PTRACE_ATTACH, tid)`（`:607`） | 选中一个可中断的执行线程 attach 住 |
| 准备 | `rc_prepare` | 在目标里分配 scratch / trap / 栈，并**写入**这些区域 |
| 冻结（仅写入口时） | `rc_pause_all`（`:732`） | 对**每一个**线程逐个 `PTRACE_ATTACH` + `waitpid` |
| 失败清理 | `rc_resume_all`（`:717`） | 把自己抓住的那部分线程逐个 `PTRACE_DETACH` |

由此产生的并发冲突：

1. **ptrace 是按线程独占的**：两个 Injector 同时对同一线程 `PTRACE_ATTACH`，后者得到 `EPERM`；
   `rc_pause_all` 一旦失败就 `rc_resume_all(set)` 回滚（`remote_call.c:754-780`），
   把这批线程**放回运行**——而此时另一个 Injector 还以为自己"冻结了全世界"。
2. **这会直接破坏唯一的安全前提**：`--nlu-install` / `--nlu-uninstall` 之所以敢写入口，是因为
   注入器先 `pause_and_check` 再传 `world_frozen=1`（`tg_injector.c:367-375`），库里的 `np_install`
   对 `world_frozen=0` 一律拒绝。并发注入会让这个"世界已冻结"的承诺变成假话 ——
   不是"两条命令打架"，而是**安全前提被削弱**。
3. **半恢复状态**：两条注入各自 `dlopen` 不同的库；一条成功一条失败时，进程里可能出现
   "TTS Guard 在、Hook 不在"或反之；严重时两边都 `rc_resume_all`，线程被 resume 两次，
   或者一边把另一边的 trap 页恢复掉 → `:core` 卡死/崩溃。

**结论：串行不是效率偏好，是正确性要求。** 30 s 到点没等到 TTS Guard，就停下来报告，不要"两个一起上"。

### 4.1 执行步骤（S1–S10）

> 与 T8-09.2 初版的差别：原 S5（起 T8 守护）与 S7（查 TTS Guard）顺序颠倒——
> 现在把"等 TTS Guard 恢复 + 确认无并发"提到"启动 T8 守护"**之前**。

```bash
# S1 停旧 T6 守护（SIGTERM → 优雅退出，会 unlink /t6/tg_supervisor.pid）
adb shell "su -c 'cat /data/local/tmp/t6/tg_supervisor.pid'"        # 先取值，应为 279
adb shell "ps -p 279 -o PID,ARGS"                                   # 复核身份：必须是 tg_supervisor
adb shell "su -c 'kill 279'"

# S2 确认旧守护已退出、:core 未受影响
adb shell "ps -A -o PID,PPID,ARGS | grep tg_supervisor | grep -v grep"
#    期望：只剩 TTS Guard 守护（4685）
adb shell "su -c 'cat /proc/<CORE_PID>/maps'" | grep libtg_hook
#    期望：仍是 /t6/ + inode 78644（旧库还在内存里，守护退出不会卸载它）

# S3 重启 :core（需审批）：取 PID → 复核 → kill -9
adb shell "ps -A -o PID,ARGS | grep 'genie.smartapp:core' | grep -v grep"
adb shell "su -c 'kill -9 <CORE_PID>'"

# S4 等新 :core 出现（上限 30 s；不出现 → R4）
#    出现后立刻记下 NEW_CORE_PID，后面每一步都用它
for i in 1 2 3 4 5 6; do adb shell "ps -A -o PID,ARGS | grep 'genie.smartapp:core' | grep -v grep" && break; sleep 5; done

# S5 等 TTS Guard Supervisor 完成注入（硬上限 30 s）
#    TTS Guard 守护（4685）会自行发现新 :core 并注入 /t7/libtg_ttsguard.so。
deadline=30; i=0
while [ $i -lt $deadline ]; do
  adb shell "su -c 'cat /proc/<NEW_CORE_PID>/maps'" | grep -q libtg_ttsguard.so && break
  sleep 1; i=$((i+1))
done

# S6 判定 TTS Guard 是否真的恢复（三条缺一不可）
#  6a. 映射存在且 inode 正确
adb shell "su -c 'cat /proc/<NEW_CORE_PID>/maps'" | grep libtg_ttsguard
#      期望：/data/local/tmp/t7/libtg_ttsguard.so，inode 86583
#  6b. 日志有本轮成功记录（时间戳必须晚于新 :core 的启动时刻）
adb shell "su -c 'tail -5 /data/local/tmp/t7/ttsguard.sup.log'"
#      期望：inject end: pid=<NEW> exit=0 hooked=1  或  already hooked: pid=<NEW> (state=1); skip install
#  6c. 30 s 内没等到 → 【停止条件】：
#      · 不启动 T8 Supervisor
#      · 保留 /t7/ttsguard.sup.log 与 /t8/ 现状（不清日志、不删文件）
#      · 报告实际状态（maps 内容、日志尾、ps）
#      · 等待进一步处理（转 R5）

# S7 确认此刻没有任何 Injector 正在操作该 :core（三条同时满足才继续）
adb shell "ps -A -o PID,ARGS | grep tg_injector | grep -v grep"      # 期望：无输出
adb shell "su -c 'grep TracerPid /proc/<NEW_CORE_PID>/status'"       # 期望：TracerPid: 0
adb shell "su -c 'tail -2 /data/local/tmp/t7/ttsguard.sup.log'"      # 期望：尾行是完成态（见 6b）
#  任何一条不满足 → 等 2 s 再看一次；仍不满足 → 停止，不要启动 T8 Supervisor

# S8 启动 T8 Supervisor（2.1 的命令，参数一个字都不能少）
adb shell "su -c 'nohup /data/local/tmp/t6/tg_supervisor \
  --injector /data/local/tmp/t8/tg_injector --so /data/local/tmp/t8/libtg_hook.so \
  --name com.alibaba.ailabs.genie.smartapp:core \
  --pidfile /data/local/tmp/t8/tg_supervisor.pid \
  --log /data/local/tmp/t8/supervisor.log >/dev/null 2>&1 &'"
sleep 3
adb shell "su -c 'tail -5 /data/local/tmp/t8/supervisor.log'"
#    期望：inject end: pid=<NEW> exit=0 hooked=1

# S9 确认新 Hook 映射
adb shell "su -c 'cat /proc/<NEW_CORE_PID>/maps'" | grep libtg_hook
#    期望：/data/local/tmp/t8/libtg_hook.so，inode 63251（≠78644），且只有一组（单实例）

# S10 后续状态核验（先读 4.2 的代价说明；两个库都稳定映射之后才允许执行）
adb shell "su -c '/data/local/tmp/t8/tg_injector \
  --name com.alibaba.ailabs.genie.smartapp:core \
  --so /data/local/tmp/t8/libtg_hook.so --check'"
#    期望：hook_status=0 hooked=1
adb shell "su -c '/data/local/tmp/t8/tg_injector \
  --name com.alibaba.ailabs.genie.smartapp:core \
  --so /data/local/tmp/t8/libtg_hook.so --nlu-status'"
#    期望：nlu hook_installed=0 takeover=0 state_ready=1；stats 里 np_installs=0、prot_state=-1
# 保持 takeover=0：不要执行 --nlu-on。若 --nlu-status 读到 takeover=1 → 停手，转 R3。
# 最后按 3.6 表做功能复核。
```

### 4.2 `--check` / `--nlu-status` 的代价（不是"读 maps"）

这两条命令**不是只读**：

- 都会 `rc_attach`（PTRACE_ATTACH 一个线程）→ `rc_prepare`（在目标里**写** scratch/trap/栈）→
  `dlsym` 与 `rc_call` 远程执行库函数；
- `--nlu-status` 还会调用 `tg_nlu_prepare()`（解析 `onNlpResult` 符号并**校验入口序言**），
  如果库当时没被加载，注入器还会 `dlopen` 它（`tg_injector.c:676`）。

因此：

1. **必须在 S6/S7 之后**执行（TTS Guard 已注入完成、无并发），不能在 S5 的等待窗口里查；
2. 两次查询（`--check`、`--nlu-status`）**串行**执行，不要并行跑；
3. 查询期间 `:core` 的线程会被短暂暂停（毫秒级），这是可接受的，但不能与任何注入动作重叠；
4. 查询失败（exit 13 attach / 19 prepare）时，先看 `ps` 里是否有别人正在注入，再决定是否重试 ——
   **不要连发多次**。

## 六、风险与前置条件（执行人必读）

1. **Injector 并发是最危险的一条**（§4.0）：两个注入器同时 attach 同一 `:core` 会互相把线程 resume，
   使 `world_frozen` 承诺失真；而 `--nlu-install` 正是靠这个承诺才敢写入口。**串行是硬约束。**
2. **30 s 超时必须停手**：TTS Guard 未在 30 s 内恢复 → 不启动 T8 Supervisor、不清日志、报告并等待，
   不要为了赶进度并发注入。
3. **两个守护可并存**（2.2）：只要旧守护没停，`/t8` 守护起来也不会赢——`:core` 重建后旧守护会抢先注入旧库。
4. **同 basename 互斥**（2.4）：任何"换路径重新注入"的想法都要经过 `:core` 重启，否则 exit 17。
5. **重启窗口语音中断**：`:core` 被 kill 到重建之间，唤醒/ASR/TTS 全部不可用（数秒~数十秒）。
6. **`:core` 可能不自动拉起**：需要操作者手动打开应用（R4）。
7. **旧守护退出会 unlink `/t6/tg_supervisor.pid`**：之后 `cat` 失败是正常现象，不代表异常。
8. **PID 可能被复用**：所有 kill 前必须 `ps -p` 复核 argv 身份。
9. **`/t8` 属主是 shell:shell**：功能无影响（755 + root 跑 injector + app 只读）；
   若要与会 `/t6` 一致，可在切换前 `su -c 'chown root:root /data/local/tmp/t8/*'`（非必需，需另行批准）。
10. **磁盘余量 301 MB**：本次切换不产生大文件；但若开 debug 日志需留意。
11. **切换会清空全部内存态**：T6 patch、sender、会话表、NLU 补丁状态全部归零 —— 这是"干净起点"，
   也意味着切换前若曾打补丁，其状态不可迁移。
12. **TTS Guard 与 Hook 同处 `:core`**：`:core` 一重启两者一起失效再恢复；它自己的守护（4685）不受本轮影响。
