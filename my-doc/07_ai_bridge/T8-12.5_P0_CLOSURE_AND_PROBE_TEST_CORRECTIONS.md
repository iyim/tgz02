### 1.2 条件 C5 的语义（本阶段的关键纠正）

【反汇编】`SessionManager::isSessionValid(char h, int sid)` @ `0x11544c`（52 B，全文）：

```
11544c  mov  r12, r0            ; r12 = this
115450  mov  r0, #0             ; r0 = 0（默认无效）
115454  ldr  r3, [r12, #64]     ; r3 = this->[64] = 当前活动 sid
115458  cmp  r3, r2             ; ★ 与传入 sid 比较
11545c  moveq r0, #1            ;   相等 → r0 = 1
115460  cmpeq r1, #0            ;   （仅在相等时）h == 0 ?
115464  beq  0x11546c           ;   相等且 h == 0 → 走状态判断
115468  bx   lr                 ;   否则返回 r0（不等 → 0；相等且 h != 0 → 1）
11546c  ldr  r1, [r12, #104]    ; this->[104] = 会话状态
115470  mov  r0, #0
115474  cmp  r1, #6
115478  movwlt r0, #1           ; 状态 < 6 → 1
11547c  bx   lr
```

等价 C 语义：

```c
int isSessionValid(char h, int sid) {
    if (sid != this->[64]) return 0;      /* ★ sid 相等性检查就在这里 */
    if (h != 0) return 1;
    return (this->[104] < 6);             /* [104] = 会话状态，6 = 已结束 */
}
```

分发器对 `what=11` 传入 `h = 1`，所以：

> **条件 C5 = `res->[+140] == SessionManager[+64]`。sid 不一致的云侧结果会在分发器被丢弃（`0x11c274 → 0x11c3c8`，只打日志）。**

**因此"云侧路径无 sid 比较"是错的**：比较确实存在，只是不在 `RouterManager::onResponse` 里，而在分发器里。上一阶段只沿调用链向下看，没有回头看消息投递后的分发器，这是本阶段的修正点。

### 1.4 类型码 {3,5} 的业务含义：静态不可证

| 事实 | 证据 |
|---|---|
| 类型码来自 `(id >> 20) & 0xF` | `0x10fe48 ubfx r10, r1, #20, #4` |
| `id` 来自字符串解析：`MmiCtx::getId(char* s)` = 若 `strlen(s) >= 33` 则 `StrUtils::toInt32(s + 32)`，否则返回 0 | `0x0fffbc`–`0x0ffff4` |
| 该字符串来自网络回包 JSON | `GcsManager::onResult` → `json_tokener_parse_2` → `JsonHelper::getJsonStringEx` → `MmiCtx::getId` |
| `{3,5}` 是唯一汇入 `onNlpResultInner` 的取值；`4` 汇入 `GcsManager::onResponse`；`1`、`2` 走其它分支 | `0x10fe58` / `0x10ff90` / `0x10ff14` 等 |

结论：**类型码是服务端下发的数据，不是本地枚举**。因此"3/5 = 云侧技能结果"这类说法**没有静态依据**，只能：① 由协议文档确认，② 由真机观测（T1 层看到 `what=11` 且 C5 成立）反推。本阶段把它列为 **U12（未证实）**，并明确"不得据函数名推断业务含义"。

### 2.1 `type` / `res` 的三条来源（完备）

【反汇编】`SessionDispatch::onNlpResult` 全库只有 3 个调用点（PLT ann `0x58b8`）：

| 调用点 | 调用者 | `arg2` | `res` | 语义（依据） |
|---|---|---|---|---|
| `0x111134` | `SessionManager::exitTalk(sid, flag)`，仅 `flag=1` 时执行（`0x111100 beq` 跳过） | **2** | 新建 152 B，`[+4]=1, [+8]=2` | **打断/退出**：`exitTalk` 由 `what=14` 触发（`0x11c4dc`） |
| `0x11cbf8` | `SessionProxy::onHandler` 的 what=1 收尾块 | **3** | **NULL** → `onNlpResult` 内部合成 152 B，`[+8]=3` | **会话收尾** |
| `0x11d674` | `SessionProxy::onNlpResultInner(int,int,res)`（尾跳） | 透传 | 透传 | 正常结果转发（`what=7` 链路） |

### 2.2 收尾块是否会被重复/提前触发

【反汇编】`SessionProxy::onHandler` 到达收尾块的唯一入口 `0x11c9f4`：

```
11c9f4  ldr  r0, [r4, #4]                  ; SessionManager*
11c9f8  bl   SessionManager::getSessionStatus()
11c9fc  cmp  r0, #6
11ca00  bne  0x11cbcc                      ; ★ 状态 != 6 → 进入收尾块
11ca04  …（日志 392）… → 0x11c400 返回      ; 状态 == 6 → 只打日志，不重复收尾
```

收尾块 `0x11cbcc`：

```
11cbcc  ldr r0,[r4,#12] ; mov r1,#1 ; bl Handler::removeMessage(1)
11cbd8  ldr r0,[r4,#4]  ; r1 = sid ; r2 = 6 ; bl SessionManager::setSessionStatus(sid, 6)
11cbe8  ldr r0,[r4,#8]  ; r1 = sid ; r2 = 3 ; r3 = 0 ; bl SessionDispatch::onNlpResult(sid, 3, NULL)
11cbfc  ldr r0,[r4,#12] ; mov r1,#1 ; bl Handler::removeMessage(1)
11cc08  ldr r0,[r4,#4]  ; r1 = sid ; r2 = 0 ; r3 = 3 ; b  SessionManager::onNlpResultEnd(sid, NULL, 3)
```

结论：

- **重复结束：不会**。`getSessionStatus() == 6` 是幂等门（`0x11c9fc`），第二次 what=1 只会打日志。
- **提前结束：不会由这段引起**。它只在 `what=1` 且状态 != 6 时执行，且自身第一步就把状态推到 6。
- **状态分叉：会**。`setSessionStatus(sid,6)`（`0x11cbe4`）在补丁点**之前**执行，`onNlpResultEnd`（`0x11cc20`）在补丁点**之后**执行；两者都不在补丁范围。因此接管一旦丢弃 `onNlpResult(sid,3,NULL)`，**管理器认为会话已结束，而"结果投递/收尾"这一环被吞掉**。
- **槽位无法释放：是**。`t8_to_on_session_end()` 在 `libtg_hook.c` 中**无任何调用点**（`grep t8_to_` 全量核对：只有 `init / enabled_set / on_final / should_drop / snapshot_take / enabled`），槽位只能靠 30 s TTL。

| 结论 | 证据强度 |

| `arg2` 只被用于两件事：① `!= 0 && res == NULL` 时决定是否合成对象；② 写入合成对象的 `[+8]` | 【反汇编】`0x118f2c cmp r4,#0`、`0x118f54 str r4,[r10,#8]` |

### 2.4 必须放行 / 可以接管（分类规则）

```c
/* 在 tg_nlp_cb 入口，按 type 分类，再决定是否查表 */
if (type == 3) return 0;   /* 会话收尾：必须放行，并在放行前后释放槽位 */
if (type == 2) return 0;   /* exitTalk 合成：必须放行（否则 CDM 收不到"本轮结束"） */
/* 其余：按 sid 查表决定是否接管 */
```

理由（全部来自本阶段证据）：

- `type=3`：它后面紧跟着 `onNlpResultEnd`，且 `setSessionStatus(6)` 已执行；丢弃它等于只留"结束标记"而丢掉"结束动作"。

## 三、任务三：U10 / R21 双库绑定

### 3.1 两份实现的可见性事实

| 事实 | 证据 |
|---|---|
| `libsmartbox.so` 与 `libagmmi.so` 都**定义**了整套 13 个会话/分发符号（`onNlpResult`/`onNlpResultInner`/`onPushNlpResult`/`playAudios`/`onResponse`/`exitTalk` …） | `readelf --dyn-syms`，见 `evidence/t8-12-p4/libagmmi_duplicate_symbols.txt` |
| 两库**都没有** `DF_SYMBOLIC`（`FLAGS` 只有 `BIND_NOW`，`FLAGS_1` 只有 `NOW`） | `readelf -dW`（本阶段复核） |
| 两库都在 `.text` 里保留 PLT 桩并用 `bl <plt>` 调自己的这些函数（说明符号是**可抢占**的，没有本地绑定） | `plt_map.ps1` 反解 + 调用点计数 |
| `/system` 下 **823 个 `.so` 中没有任何文件以 `UND` 导入**这些符号 | `evidence/t8-12-p4/all_so_symbol_scan.txt` |
| **没有任何库 `NEEDED` `libagmmi.so`**；`libagmc.so`/`libagui.so`/`libsaladapter.so` 才 `NEEDED libsmartbox.so` | 全库 `readelf -dW` 反查（本阶段新增） |

由"无 `DF_SYMBOLIC` + 全部走 PLT"可推出：**两库对本库内这些函数的调用，都由动态链接器按全局符号查找顺序解析**，因此所有调用者最终命中**同一份**实现（赢家）。

### 3.2 `dlsym(RTLD_DEFAULT)` 是否足以定位同一份实现

| 问题 | 答案 |
|---|---|
| 6 个符号是否可能各自赢家不同？ | **不会。** 两个候选库对 6 个符号**全部**都是 `DEF`，所以每个符号的查找都在同一对候选里做，胜出的永远是**同一个库**（同一个全局查找作用域、同一次装载） |
| 如何自证 | 对 6 个符号逐个 `dlsym(RTLD_DEFAULT, …)` + `dladdr()`，断言 6 个 `dli_fbase` **完全相同**；不一致就拒绝安装（不猜） |
| 由此得到的地址是否就是"被调用的那份"？ | **是**（同一符号在全局作用域只有一个绑定；无 `DF_SYMBOLIC` 即无本地绑定旁路） |
| 仍需注意 | `libsmartbox` 是别人的 `DT_NEEDED`，通常**先**装载；若 `libagmmi` 先被 `dlopen`，赢家就是它 —— 这只能由运行期核验回答（U10） |

### 3.3 只读核验方案（不执行 Injector、不修改内存）

目标：判定 ① 两库是否都装载、② 谁赢、③ 6 个安装点的真实地址。

**方法（全部只读）**

1. **装载与基址**：读 `/proc/<pid>/maps`，抓 `libsmartbox.so` / `libagmmi.so` 的行，得到每个库的最低可执行映射起点与其 `p_vaddr` 偏移 → 基址；同时按出现顺序判断装载先后。
2. **谁赢（决定性证据）**：每个库对同一符号都有自己的 PLT 桩，桩体里带 GOT 槽位地址（`plt_map.ps1` 已能在静态阶段算出，例如 libsmartbox 的 `SessionManager::onNlpResultInner` 桩 `0x92b28` → GOT `0x1f15c0`；libagmmi 的对应桩 `0x433fc` → GOT `0xccfcc`）。运行期读 `/proc/<pid>/mem` 里 `base + GOT偏移` 的一个 4 字节值（**只读**），得到链接器填好的目标地址，再与
   `base_smartbox + 0x00114b98` 和 `base_agmmi + 0x000600b4` 比较：
   - 等于前者 → `libsmartbox` 赢；
   - 等于后者 → `libagmmi` 赢；
   - 都不等 → 第三种实现，立刻停止。
3. **6 个安装点归属**：对 6 个符号各做一次上一步（或用一次 `dlsym`+`dladdr` 自检），确认 6 个都在同一 `dli_fbase` 下；随后
   `addr = dli_fbase + (vaddr - 该库该符号的 vaddr)`，逐个打印并与上表核对。
4. **交叉校验**：`dlsym` 得到的地址应等于第 2 步读出的 GOT 目标地址；不相等说明有第三方插桩，停止。

**为什么这不是"用静态扫描代替运行期结论"**：静态部分只提供"桩 → GOT 槽位"的映射（这一步是纯 ELF 解析，已由 `plt_map.ps1` 自证 3546/3546、1622/1622）；"槽位里填了谁"**必须在设备上读**。本阶段只把方法定下来，**没有执行**（禁止真机）。

**结论级别**：U10 在设备上跑完第 1–4 步之前，**任何"补丁地址 = libsmartbox 基址 + vaddr"的写法都视为未验证**。
