# T8-06.1 修复：原始页面权限查询失败被误判为 RWX

只修 ChatGPT 审查发现的一个 P1：`page_prot()` 用 `7` 同时表示"RWX"和"查不到"，
于是 `/proc/self/maps` 不可读时，`nlu_pp_unprotect()` 会把 7 当成合法基线记下来
（`g_nlu_prot_valid = 1`），后续 `nlu_pp_reprotect()` 就"恢复"成 RWX —— 页面永久可写，
而且是静默的。

## 1. 两个函数（逐字采用任务书代码）

`page_prot()`：
* 打不开 `/proc/self/maps` → `-1`；遍历完仍没有匹配行 → `-1`；
* 命中时按 `PROT_READ/PROT_WRITE/PROT_EXEC` 组合返回，**7 从此只表示"真的 RWX"**。

`nlu_pp_unprotect()`：
* 没有基线时先查询；`original_prot < 0` 或含 `R|W|X` 之外的位 →
  `"cannot determine original page protection (page=0x...); refusing to change protection"`，
  返回 `-1`，**不设置 `g_nlu_prot_valid`、不调用 `mprotect`**；
* 只有查询成功才写 `g_nlu_orig_prot` / `g_nlu_prot_valid = 1`；
* `mprotect(RWX)` 失败时错误文本带 `what`（空则 `unknown`）、页地址与 errno。

`nlu_pp_reprotect()`（T8-06 已改，本轮不变）在没有基线时同样拒绝，不猜。

## 4. 仍存在的页面保护风险（如实列出）

1. **T6 `onStream` Hook 与 NLU stub 页仍有旧写法**：`tg_hook_install()` /
   `tg_hook_uninstall()` / `build_nlu_stub_page()` 里是 `old = page_prot(page)` +
   `mprotect(..., old ? old : (PROT_READ | PROT_EXEC))`。`page_prot()` 现在返回 `-1`
   表示未知，而 `-1` 在 C 里是真值，于是这条路径会执行 `mprotect(prot=-1)`；
   Linux 对含非法位的 prot 返回 `EINVAL`，**页面保持 RWX**（与改动前的
   "`7` → 恢复成 RWX" 同一最坏结果，未变差，但也未修好）。
   属于本轮禁止扩大的范围，未动；建议下一轮按 `nlu_pp_unprotect` 的写法统一。
2. **NLU 入口补丁路径已闭合**：基线未知时在 `mprotect` 之前就拒绝，页面不会被打开写权限；
   恢复时无基线也拒绝。
3. **基线只读一次并缓存**：若之后被别的组件改了页权限，恢复用的是旧基线。
   手动核对/重试导出 `tg_nlu_prot_state()` / `tg_nlu_prot_restore()` 可用于事后确认与修
   复，不自动重读。
4. **首次写时页面若已可写**（例如上一轮失败残留 RWX），基线就会记成 7 并"如实恢复成 7"；
   `prot_dirty` 标记 + 手动恢复是缓解手段。
5. **RWX 窗口本身**：`mprotect(RWX)` 到恢复之间，其他线程可以写该页；这属于更底层的
   页面级加固，不在本轮范围。
6. **未做真机验证**：`mprotect` 的真实内核行为、SELinux Permissive 下的差异只能上机确认；
   本轮仅有主机行为测试 + ARM32 编译。
