How to read the two controls
----------------------------
* tsan_race_true is the control that proves the tool is alive.  It adds one
  deliberately unsynchronised store (`s->now = s->now + 1` from four threads).
  TSan answered with exactly one report:

    WARNING: ThreadSanitizer: data race (pid=193)
      Read of size 8 at 0x7b8800000008 by thread T1 (mutexes: write M2):
        #0 alloc_locked  t8_12_9_lifecycle_model.c:229
        #1 on_final      t8_12_9_lifecycle_model.c:299
        #2 worker        t8_12_9_lifecycle_model.c:638
      Previous write of size 8 at 0x7b8800000008 by thread T2:
        #0 clock_tick_worker  t8_12_9_lifecycle_model.c:197
        #1 worker             t8_12_9_lifecycle_model.c:658

  Therefore "0 warnings" in tsan_normal is falsifiable, not vacuous.

* tsan_race_control splits one atomic increment into read + write-back, both
  still under the mutex.  It loses updates but is NOT a data race, so TSan
  correctly reports 0.  That is the whole point: the count identity is a
  different oracle (logical lost updates) from TSan (unsynchronised accesses),
  and a lost-update control cannot substitute for either.

Bug found during this run and fixed
-----------------------------------
v3_join_abandon_before_fix.txt is the pre-fix log: `--join-abandon` printed
INCOMPLETE and then died with SIGSEGV (EXIT=139, core dumped).  Cause: the four
worker structs lived in `scenario_concurrent`'s stack frame, the abandoned
threads kept incrementing their own counters, and the frame was reused after the
function returned -> writes into a dead frame.  Fix: `static worker_t w[4]`
(and the state was already heap-allocated).  v4 exits 2 on both platforms.
