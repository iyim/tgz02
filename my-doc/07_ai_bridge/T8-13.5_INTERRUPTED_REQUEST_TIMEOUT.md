# T8-13.5 最小修复：打断后活动请求的超时清理

- 基线提交：`c08f9d92ae36d66b90d8bf9173cbbcc09739375c`（T8-13.4）
- 改动文件：`android/session_ctrl.c`、`tests/t8_13_session_ctrl_unit_test.c`（+ 本报告与两份日志）
- 范围：只补 INTERRUPTED 状态的活动请求兜底。未改 `sc_on_interrupt()` 的即时迁移语义，
  未给 PROCESSING 加通用超时，未触碰其它状态机逻辑。
- 结论：悬挂路径闭合。INTERRUPTED 且请求仍活动时，截止到达即连请求一起清场，
  迟到的旧播放收尾按 stale 处理，无法重开会话、无法污染新请求。

---

## 一、问题（复述并对上代码）

| 步骤 | 原行为 | 后果 |
|---|---|---|
| 1 | 请求在 `SC_SPEAKING`，`request_active=1`，截止 = 5 × 窗口 | — |
| 2 | `sc_on_interrupt()` → `SC_INTERRUPTED`，把 5× 截止**覆盖**成 1× 窗口 | 安全网被削短 |
| 3 | 但它**不清除** `request_active` | 请求仍"活着" |
| 4 | `sc_poll()` 的通用关闭分支要求 `!request_active` | 永远进不了 CLOSING |
| 5 | TtsExec 不发布 interrupted/idle 收尾时 | **永久停在 INTERRUPTED** |

这与 T8-13.4 修掉的"缺播放事件导致 PROCESSING/SPEAKING 悬挂"属同一类生命周期缺陷：
状态迁移覆盖了截止，却没有覆盖请求终结责任。

---

## 二、修改（`session_ctrl.c`，`sc_poll()` 内新增一个分支）

插在 SPEAKING 兜底之后、通用关闭分支之前：

```c
if (state == SC_INTERRUPTED && request_active && deadline_ms > 0 && now_ms >= deadline_ms) {
    timeouts++;
    closes++;
    request_active = 0;                                  // 清除活动请求
    prev_request   = request;                            // 旧 id 退役（迟到回调识别）
    request        = "";                                 // 清空当前请求
    state          = SC_CLOSING;                         // 可观测瞬时态
    deadline_ms    = 0;
    return state;                                        // 下一拍由 CLOSING 分支回 IDLE
}
```

对齐任务书要求逐条：

- [x] 当前 request 复制到 `prev_request`
- [x] 清除 `request_active`
- [x] 清空当前 `request`
- [x] `timeouts++`、`closes++`
- [x] 进入 `SC_CLOSING`
- [x] 清除 `deadline_ms`
- [x] 下一次 poll 正常进入 `SC_IDLE`（沿用既有 CLOSING 分支，未改）
- [x] 真实 interrupted/idle 先到则走原有收尾（本分支要求"截止已到"，不会抢先）
- [x] `sc_on_interrupt()` 未改（仍是 INTERRUPTED + 1× 窗口，语义不变）
- [x] PROCESSING 仍未加通用超时（长耗时模型请求不受影响）

进入 CLOSING 后，`prev_request` 保留旧 id：`sc_on_play_state()` 在 `!request_active` 时对
`prev_request`/陌生 id 一律计 `stale_callbacks` 并返回 0，状态不动 —— 这是既有归属规则，未改。
