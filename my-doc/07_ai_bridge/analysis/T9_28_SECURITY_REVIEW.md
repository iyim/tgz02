# T9-28 安全边界审查（L2 越权、注册表权限模型、既有特权通道审计）

对应审查意见 §三.3（AI 工具调用安全）与 §三.4（注册表不得成为权限入口）。
原则一句话：**AI 只能"描述想法"，执行权只在编译进二进制的回调表里；
配置只能把能力收窄，不能把能力放大。**

---

## 1. 威胁模型

| 威胁主体 | 能做什么 | 不能做什么 | 现有防线（【代码】） |
|---|---|---|---|
| 任意第三方 App（uid ≠ 目标） | 写 `/data/local/tmp/t5_bridge/work`（**0777，实测**）、伪造事件文件 | 写 `t9_ui/inbox`（0700）、读 worker 状态（0640 root:u0_a71）、写 `/data/misc/tgz02`（0770 system:system） | `tg_inbox.h:5-20`：外来 uid 的文件被**丢弃并 unlink**，按 uid 限速，单轮扫描有上限 |
| 桌面 App 自身（u0_a71） | 写 inbox（say/ask/stop/modeltest/open）、读写 DB | 直接执行 root 操作 | `inbox` 的 kind 白名单（`tg_inbox.h:36-56`）+ worker 侧二次白名单（`ai_worker.c:1421-1487`） |
| 拿到 root 的人 | 一切 | — | 不在本设计防御范围 |
| 云端模型（经代理） | 返回任意文本 / 任意 `tool_calls` / 任意参数 | 直接触碰设备（provider 不执行任何东西，`provider.h:12-16` 铁律） | 本轮新增七步校验（§3） |
| 被改坏的配置文件 | 改 `skills.json` / `worker.conf` / `models.json` | 改编译期白名单与 owner 常量 | 收窄校验（§2）+ 启动可观测 |
| 网络中间人（局域网代理） | 改模型响应 | 改设备内状态 | 响应只当数据用；参数必过 validator |

关键事实：`/data/local/tmp/t5_bridge/work` 是 **0777**（本轮实测），任何 App 可写。
这决定了**安全状态（ownership 表与回执）绝不能放在那里** —— 见 OWNERSHIP §2.3。

## 2. 技能注册表的权限模型（审查意见问题 4）

### 2.1 四个层次，能力只降不升

| 层 | 内容 | 谁能改 | 能否扩大能力 |
|---|---|---|---|
| ① **编译期白名单** | `exec` 回调表（id → 函数指针）、`owner` 常量、`route_bit` 常量、参数 schema 的**类型** | 只有改源码 + 过架构审查 | **是**（唯一入口） |
| ② **部署期期望值** | `requires_hook_build`、`rules_hash`、允许的 owner 集合、`tools` 能力位 | 部署脚本（root） | 否（只能声明"我期望什么"） |
| ③ **运行期开关** | 技能启用（App `skills` 表 / `worker.conf`）、`skill_*_enabled`、语义/工具调用总开关 | 用户/运维 | 否（只能关） |
| ④ **清单文件** `skills.json` | 标题、描述、例句、负例、回话模板、参数**约束收紧**（如 `max_len` 更小）、`enable_key` 绑定 | root 可写该文件的运维 | 否（只能收窄） |

### 2.2 `skills.json` 的收窄校验（加载时执行，任一条不满足即拒载该技能）

| # | 校验 | 违反时 |
|---|---|---|
| V1 | `exec` 必须在编译期白名单表里 | 拒载 + `manifest_reject[unknown_exec]++` |
| V2 | `owner` 必须与编译期常量**完全相同**（不许 JSON 把 factory 改 local，也不许反向） | 拒载 + `[owner_conflict]++` |
| V3 | `owner=local` 与 `route_bit != 0` 同时出现 | **不拒载**，但记 `mask_owner_inconsistent++` 并在状态页提示（生效期以 owner 为准，mask 只在回滚路径用；见 OWNERSHIP §4.1） |
| V4 | 参数类型/必需性不得放宽（只能收紧 `max_len`、只能增加 `enum` 限制） | 拒载 + `[param_loosen]++` |
| V5 | 不得为 `owner=factory` 的技能声明 `enable_key`（原厂能力不可被清单开关） | 拒载 + `[factory_toggle]++` |
| V6 | 例句/负例各 ≤4 条、单条 ≤24 字、总计 ≤4 KB | 截断 + 计数（不拒载） |
| V7 | 未知字段一律忽略（前向兼容），但未知 `id` 被拒载 | 拒载 + `[unknown_id]++` |

拒载不会让语音整体失灵：该技能退回编译期默认描述，其余技能正常。状态文件里
`skills.manifest_rejected` 列表可见（App 设置页显示红字）。

### 2.3 为什么 owner 不允许出现在清单里（要写进代码注释）

因为 owner 同时是**安全边界**：`local` 意味着"原厂 NLU 会被丢弃、由我们执行"。
如果运维把 `alarm` 从 factory 改成 local 而代码里没有对应的执行回调与 route 位清理，
结果就是 F1（双执行）或 F2（静默）。所以 owner 只能由代码变更 + 审查来改。

## 3. L2 工具调用的七步校验（审查意见问题 3）

模型返回的 `tool_calls[i]` 依次过：

| 步 | 校验 | 失败处理 |
|---|---|---|
| 1 | `name` 必须在**本轮下发的工具表**里（即 `owner=local` 且启用） | 丢弃 + `tool_unknown++`，不执行、不播报"我做了" |
| 2 | 本轮只接受 **1 个** tool_call；多于 1 个 → 只执行第一个 | `tool_multi++`，播报时明确"其余没做"（MULTI_INTENT §5） |
| 3 | `arguments` 必须是合法 JSON 对象，字段名必须属于该技能的参数表 | `tool_badargs++` + 针对性追问（不猜） |
| 4 | 类型/范围：str 截断到 `max_len`（UTF-8 安全）、int 在 [min,max]、enum 必须在允许集合 | 同上 |
| 5 | 语义校验：时间可解析、方向合法、歌名非空且不含控制字符 | 同上 |
| 6 | **业务结果校验**：如 `music.play` 的 query 必须"搜到 ≥1 条完整曲目" | 不说"正在播放"，改说"没找到 X，换个说法" |
| 7 | 执行后校验：设备状态是否真的变了（`MusicService` 回 `cmd` 回执 / 播放状态快照） | 记 `tool_effect_miss`，播报固定失败文案 |

七步里任一失败都**不回落 L3**（避免"没做成"+"模型另编一段"的双答），
文案与计数见 MULTI_INTENT §6。

### 3.1 实测支撑（为什么第 6、7 步是必需的）

| 现象 | 证据 | 对应步 |
|---|---|---|
| 模型编造参数 `{"query":"热门流行歌单"}` | `evidence/t9-27/resp_b_vague.json` | 6 |
| 模型把"关音乐"映射成 `pause`（动作近似替代） | `resp_f_stop.json` | 4/5（枚举里必须补 `stop`） |
| 模型一次只返回一个动作 | `resp_c_multi.json` | 2 |
| 有工具就会绕开原厂答天气 | `resp_d_weather.json` | 1（物理上不给） |

### 3.2 超时、熔断、循环

| 项 | 规则 |
|---|---|
| 单次 L2 超时 | 2000 ms；超时即弃权到 L3（不再等） |
| 熔断 | 一次超时/失败后 60 s 内不再尝试 L2，直接 L3（避免"每句话都等 2 秒"） |
| 循环上限 | 不允许"模型再调一次"的循环；单轮决策，硬上限 1 |
| 重试 | 不重试（同一句重试会放大延迟与双答风险） |
| 结果缓存 | 同一 `event_id` 只执行一次（复用既有 `tts_probe_stage` 幂等语义，`ai_worker.c:1936`） |

## 4. 既有特权通道审计（本方案的"不许新增"清单）

设计不新增任何执行通道，只审计已有的四条：

| 通道 | 位置 | 输入约束 | 残余风险 |
|---|---|---|---|
| `kind=open` 代开页面 | `ai_worker.c:1463-1487`（`opens[]` 白名单，组件名写死）；`tg_inbox.h:55` | 只认 `alarm/market/settings` 三个词，`strncmp` 前缀匹配 | 前缀匹配意味着 `alarmxyz` 也会命中 → 建议改**精确相等**（P5 小修） |
| `music.*` 命令 | `ai_worker.c:1988-2008`（`am start-foreground-service` + `--es cmd/arg`） | `cmd` 由技能内部枚举（`2068-2082` 否则 `E_ARG`）；`arg` 来自 `ir_music_query` 提取，会经 `am` 的参数化传参 | `arg` 是搜索关键词，进入 App 后拼到 HTTP 查询串 → 必须有 URL 编码（App 侧已用 OkHttp/编码，需一次渗透式自测） |
| `kind=say/ask` | `tg_inbox.h:36-39`、`ai_worker.c:1495-1537` | 文本 ≤1024B，UTF-8 校验，kind 白名单 | 任意 App 若能写 inbox 就能让它说话（但 inbox 是 0700，只有我们 App） |
| `stop` | `ai_worker.c:1441-1454` | 必须带合法 `tts_id` | 仅能停自己的播报 |

**新技能不得新增通道**：音乐/闹钟/记忆都通过"App 侧 Binder/服务"或"inbox 的已存在 kind"完成，
禁止新增"把字符串拼进 `system()`/`sh -c`"的路径。这条写进代码评审清单。

## 5. 原厂能力隔离（为什么不能给模型看天气）

【实测】T9-27 用例 d：工具表里没有天气时，模型回答"我目前还不能查询天气，只能控制音乐/音量/设备状态"。
反推：**只要给它工具，它就会自己答**，从而绕过原厂的云端天气技能（真机可用，见
`T9_17_ORIGINAL_WEATHER_CHAIN_REPORT.md`）。

所以隔离手段是**物理的**（工具表构造时过滤），不是提示词约束：

```c
/* 工具表生成：只允许 owner=local（编译期常量，清单不可改） */
for (i = 0; i < SK_COUNT; i++)
    if (desc[i].owner == SK_OWN_LOCAL && enabled(desc[i]))
        emit_tool(desc[i]);
```

配套断言（启动时）：若工具表里出现任何 `owner != local` 的条目 → 视为代码缺陷，
直接以"空工具表"启动并记 ERROR（宁可关掉 L2 也不越界）。

## 6. 数据外泄面

| 数据 | 现在是否出网 | 本方案变化 | 处理 |
|---|---|---|---|
| 用户原话 | 是（L3 每次都发） | 不变 | — |
| 工具表（技能描述） | 新增 | 技能名/描述/参数名出网 | 描述不得含设备标识；上限 8 个、≤40 字 |
| 设备状态摘要（歌名/音量/在播状态） | 新增 | 出网 | 只含结构化字段；可关（`skill_ctx_inject=0`）；文档明示 |
| `reasoning_content` | 已在响应里 | 不出网、不落盘 | 只计数；解析时丢弃（`t6b_ds_parse_toolcall` 不读该字段） |
| API key | 不出网（只在请求头） | 不变 | 状态文件/日志从不记录（既有约束） |
| 记忆库内容 | 否 | 保持不变（不注入 L2） | 记忆技能只在本地读写；**不把记忆条目放进提示词** |

记忆不上云是刻意的：记忆是长期隐私数据，一旦注入 L2 就等于每天把用户画像发出去。

## 7. 清单/表被篡改的后果

| 文件 | 篡改后果 | 缓解 |
|---|---|---|
| `skills.json`（清单） | 最多改描述/例句/文案，或关掉某技能 | 收窄校验 V1–V7；owner 不可改 |
| `ownership.json` | 可让 hook 放行/接管错 | 只有 root 能写；`rules_hash`/`build` 校验；`owner` 与 owner 常量不一致的条目按 factory 处理并计数（`mask` 生效期不参与判定） |
| `ownership.ack.json` | 可伪造"hook 已确认" | 目录 0770 system:system（App 不可写）；**残余风险**：root 级伪造不在防御范围 |
| `models.json` | 可把 `tools` 打开/指向恶意端点 | 端点本身是用户配置；L2 失败即熔断；工具表仍由本地生成 |
| `worker.conf` | 可开关技能 | 只能关；开启受编译期回调是否注册限制 |

## 8. 残余风险（明确保留，不假装消除）

| # | 残余风险 | 影响 | 为什么接受 |
|---|---|---|---|
| SR1 | root 可写 ownership 表 → 可让系统进入任意归属组合 | 需要 root | root 已经能做任何事 |
| SR2 | `open` 通道是前缀匹配 | 可能打开非预期组件 | 列表只有 3 项且组件名写死；P5 改精确匹配 |
| SR3 | 音乐 query 进入 App 的网络请求 | SSRF/注入面在 App 侧 | 由 App 的网络层编码；P3 加一次自测 |
| SR4 | 模型可让 `music.play` 用任意 query 搜索 | 播放不相关内容 | 业务结果校验 + 用户可打断 |
| SR5 | SELinux 若转为 Enforcing，回执写不进去 | 本地技能全退化（不双执行、不静默） | 有明确降级；补 sepolicy 即可 |
| SR6 | `reasoning_content` 可能包含敏感推理，若有人改代码误播 | 泄露 | 明确"不读该字段"的单元测试 |
