## 2. 最重要的一条修订：归属判定只能在 hook，不能在 worker

这是 T9-27 的一个**方向性错误**，审查意见没有直接点出，但它决定了问题 1 的解法。

### 2.1 事实：hook 的丢弃是不可逆的

【代码】`nlu_takeover.c:248 t8_to_should_drop()` 返回 1 时，`SessionDispatch::onNlpResult` 的原厂 NLU 结果
被丢弃 —— 原厂**不会执行技能，也不会产出那句话**。worker 在几百毫秒后才看到事件，此时：

- 它无法"把原厂 NLU 还回去"；
- 它如果自己执行，就等于接管；它如果不执行，用户就听不到任何回答。

所以 T9-27 里"worker 判定 owner=local，hook 读文件失败回退 mask"这个组合会直接生产 F2（静默），
审查意见问题 1 的担心**在代码层面成立**，不是理论风险。

### 2.2 推论：worker 不能是"归属的最终裁决者"

T9-27 让 worker 产出归属表、hook 消费，隐含假设是"worker 说了算"。
但 hook 先跑，且一旦 TAKE 就无法撤回。因此正确的责任划分是：

| 决定 | 谁做 | 为什么 |
|---|---|---|
| 这句话原厂能不能执行（PASS/TAKE） | **hook**（唯一能决定的地方） | drop 不可逆 |
| 这句话要不要由本地技能执行 | **worker**，但**必须服从 hook 的结论** | 若 hook 已 PASS，原厂会执行/回答，worker 再执行就是 F1 双执行 |
| 归属表（谁的意图） | worker 产出，hook 只读 | 便于集中管理与观测 |
| 归属表**生效**的时机 | 两侧按**同一个时间戳**同时生效 | 见 OWNERSHIP §3 |

据此确立三条不变量（贯穿全部六份文档）：

> **I1（不可双执行）**：worker 执行本地技能，必须同时满足：hook 已 TAKE 该句 + 归属表对本句有效 + 表已过 `not_before` 且未过租约。
> **I2（不可静默）**：hook 在任何不确定状态下必须 PASS 而不是 TAKE。PASS 的最坏结果是"原厂按自己的理解处理/回答"，它不会导致静默，也不会导致双执行（因为此刻 worker 按 I1 不执行）。
> **I3（必须可观测）**：任何降级（表过期、build 不匹配、回执缺失、L2 超时）都要有计数器 + 一行日志 + 状态文件字段，不允许"静默降级"。

### 2.3 由此带来的一处能力缺口：hook 侧的识别覆盖

I2 的方向（不确定就 PASS）意味着：hook 认不出"现在有点吵"是音量意图时，它会 TAKE，
于是原厂拿不到这句话，worker 又必须服从（I1）—— 结果是这句话永远到不了音量能力。

【实测】本轮 42 句验证集里，现有 `intent_route` 风格的关键词匹配对 4 条音量口语变体全部弃权
（`evidence/t9-28/L1_EXPERIMENT.txt`，M1 行）。也就是说这类话术**今天是坏的**，不是新架构引入的。

所以修订案把"L1 本地语义"从 worker 侧**移到 hook 侧**（有界实现），理由：

- 它影响的是 PASS/TAKE，只能由 hook 决定（§2.2）；
- 它是纯计算：静态例句表 + bigram/词典，无 I/O、无分配、可预测；
- 代价是 hook 变大了一点 —— 必须给硬预算并实测（§3.4）。

>T9-27 说"L1 在 worker"。修订：**L1 在 hook**（判定用），worker 侧保留一份相同实现用于
>"自测/回放/解释"，两者由**规则哈希**互相校验（OWNERSHIP §7），不允许无检测漂移（F3）。

### 2.4 附带结论：`route bit` 退出判定链

T9-27 让"归属"与"mask"并存（`bit==0` 才 TAKE），于是 `owner=local` 但 bit 仍置位时必然双执行
—— 这正是 F1 的结构性来源。修订后：

| 状态 | 判据 | 说明 |
|---|---|---|
| `H3_ACTIVE`（ownership 生效） | **只看 owner 表** | `PASS ⇔ factory`；`TAKE ⇔ local/ai` |
| `H6_DISABLED`（ownership 关闭） | 看 mask（T9-26 行为） | 唯一的回滚路径 |
| 其他（PENDING/EXPIRED/REFUSED） | `PASS_ALL` | I2 不静默 |

`mask` 字段继续留在表里，仅用于可读性与回滚，不参与生效判定。
代价：`ir_route_bit()` 与 owner 常量需要在代码评审里同步（否则回滚路径与原意不符），
因此状态里输出 `mask_owner_inconsistent` 计数作为提醒。

## 3. L1 本地语义：用数据回答审查意见问题 2

审查意见的原话是"不能只凭四条正例和四条负例就认定一个技能具备足够的语义覆盖率"。
本轮做了可复跑的对比实验（脚本 `evidence/t9-28/t9_28_l1_experiment.py`，报告 `L1_EXPERIMENT.txt`）。

### 3.1 实验设置

- 42 句人工标注验证集，覆盖：审查意见点名的 4 条音量变体、点歌 7 种说法、控制 6 种、
  设备状态 4 种、原厂能力 9 句（天气/闹钟/时间/关屏）、记忆 3 句、AI 域 5 句、易混 4 句。
- M1 = T9-27 原方案（char bigram Dice，`accept≥0.62`、`margin≥0.08`，每技能 4 正例）。
- M2 = 结构化模板（触发词族 + 槽位剥离 + 否决条件）。
- M3 = M2 优先；M2 弃权时**只允许** Dice 在"本地技能"里补位（原厂能力一律不补）。

### 3.2 结果【实测】

| 方法 | 正确 | 弃权（交给上层） | 误接管原厂 | 说明 |
|---|---|---|---|---|
| M1 Dice | 23/42 = **54.8%** | 28 句 | 0 | 失败模式是**弃权过多**，不是乱接 |
| M2 模板 | 36/42 = **85.7%** | 13 句 | 0 | 唯一误判：`电池是什么原理` → `device.status` |
| M3 模板+Dice | 38/42 = **90.5%** | — | 0 | Dice 只在"本地技能"里补位时才有正收益 |

三条必须写进设计的结论：

1. **Dice 的坏处不是误接管，而是把 2/3 的话推给 L2。** 28/42 弃权 × 实测 L2 延迟 1.1–2.9 s
   （T9-27 §3.1）= 用户等 1–3 秒才听到"我在听了"。这个代价在 1 GB 设备上不可接受，
   所以 L1 **必须**有足够的召回，不能拿"阈值保守"当安全。
2. **模板（触发词族 + 槽位）比 Dice 强得多，但它就是"更好的关键词表"。**
   审查意见担心"补词不可持续"，用实验也能证明：把 M2 的 6 个失败项逐个补进词表后指标到 100%
   （脚本末段）—— 这恰恰说明指标会随"补词者的想象力"漂移，所以**门槛必须是独立测试集 + 拒识率**，
   而不是"再补几个词"。
3. **两套方法的冲突需要仲裁。** 本次 42 句里 M1/M2 冲突 0 句，但这是样本少；规则仍要事先定死
   （本地技能冲突 → 取模板结果并记日志；模板弃权 → 允许 Dice 补；两者都弃权 → L2）。

### 3.3 修订后的 L1 结构（三层，逐层弃权）

```
归一化（沿用 ef_normalize/ef_strip_fillers）
   ↓
L1-a 保护跨度标注：引号/书名号内、数字+单位、时间词 → 不参与后续打分（多意图也用同一份，见 MULTI_INTENT §2）
   ↓
L1-b 模板匹配（主）：每个技能一组"触发族 + 必需槽位 + 否决条件"，命中即出候选（≤2 个）
                     **覆盖 factory 意图**（音量/天气/闹钟/时间的口语变体），这是修 §2.3 缺口的关键；
                     它仍是纯本地的确定性匹配，不是模型，所以允许它判 factory；L2 不允许
   ↓ 无候选
L1-c 相似度补位（辅，只对 owner=local）：char bigram Dice，accept≥0.62 且 margin≥0.10
   ↓ 仍无候选
弃权 → L2（云端工具）→ 仍无 → L3
```

- 阈值从 T9-27 的 `margin≥0.08` 提到 **0.10**：本轮样本里 `这首歌真好听`(0.06)、`播放器怎么设置`(0.07)
  都靠 margin 挡住的，0.08 的余量太薄。
- **拒识是一等公民**：L1 的三层都允许"没有候选"，并且要计数（`l1_abstain`）。
  弃权率高说明语料/模板不足，是产品指标，不是错误。
- **不得引入本地大模型**：本机 1 GB RAM / ARM32 / Android 8.1，且当前没有任何推理运行时。
  若将来要上"离线训练的线性 n-gram 分类器"，准入条件是：模型 ≤2 MB、纯 C 前向、无第三方依赖、
  在**独立** ≥300 句测试集上比 M3 提升 ≥8 个百分点。否则不做（本文 §6 D2）。

### 3.4 hook 侧预算（必须实测，否则不上）

| 项 | 预算 | 现状 |
|---|---|---|
| 例/表只读数据 | ≤ 8 KB | 【推断】按 40 技能 × 4 例 × 24 字估算 |
| 单句耗时 | ≤ 1 ms（`onStream(isFinished=1)` 内） | 【待测】需真机埋点 |
| 动态分配 | 0 | 设计约束 |
| I/O | 0（归属表读取已有缓存，另计） | 设计约束 |

不满足任一条，L1-b 就退回 worker 侧 + 只对 local 生效（即 T9-27 的形态），
并在状态页写明"原厂口语变体不覆盖" —— 宁可承认能力边界，也不在 :core 里塞不确定的东西。

## 5. 其余修订（对应审查意见 3/4/5）

### 5.1 L2 收紧（问题 3）

| 项 | T9-27 | 修订 |
|---|---|---|
| 工具表 | 只含 local（对） | 保留，并加"上限 8 个 / 描述 ≤40 字 / 关掉读类优先" |
| 参数校验 | 一句"过 validator" | 七步流水线（类型→范围→枚举→长度→UTF-8→权限→业务结果），见 SECURITY §3 |
| 编造参数 | 只说"搜到才算成功" | 增加"不得播报未验证事实"的硬规则 + 失败文案表 |
| 多工具 | 未定义 | 只接受 1 个；多于 1 个按"第一个 + 明确反馈其余未执行" |
| 超时 | 2 s | 保留，并加"一分钟内不再尝试 L2"的熔断 |
| 原厂隔离 | 规则 | 保留 + 实测依据（T9-27 用例 d） |

### 5.2 权限模型（问题 4）

四层，且**只能向下收窄**：

```
① 编译期白名单（exec 回调表、owner 常量）      ← 唯一能"扩大能力"的地方，改代码 + 过审查
② 部署期期望值（ownership 表里的 requires_hook_build / rules_hash / 允许的 owner 集合）
③ 运行期开关（worker.conf、App 的 skills 表）
④ 清单文件（skills.json）                      ← 只能收窄：可关、可改描述/例句/文案，不可改 owner/exec
```

`skills.json` 的 parser 在加载时做"收窄校验"：若清单里的 `owner` 与编译期常量不一致、或 `exec`
不在白名单表里、或试图给 `factory` 技能加 `enable` 开关 → 整条技能被拒载 + 计数 + 状态页红字。
细节与拒绝码见 SECURITY §2。

### 5.3 多意图（问题 5）

- 切分不再只看连接词：先标"保护跨度"（书名号/引号里的歌名、`七点` 这类时间、数字+单位），
  再在剩余文本里找"动作跨度"，连接词只在两个动作跨度之间起**分隔**作用。
- 混合调度给出三档策略并明确默认值（MIX-0：只做本地段 + 明确反馈；MIX-1：本地 + 原厂整句、
  仅限幂等动作；MIX-2：本地 + 本地等价实现，需 A/B 实测）。默认 **MIX-0**，因为它是唯一
  不需要复制原厂语义的档位。
- 模型只回一个 `tool_call` 时，**不得**假定整句完成：必须做残句检测并明确播报（MULTI_INTENT §5）。

### 5.4 与 App 已有 `skills` 表的关系（新增，T9-27 未处理）

【代码】App 侧已经有一张技能表和一个对外快照：

- `Db.java:75-82` — `skills(id, name, enabled, state, sort, last_used_ms)`，`state ∈ on|unavailable|planned`
- `Db.java:84-91` — `execution_logs(id, skill, action, detail, ok, ts_ms)`，注释写着"T10 will write these"
- `DataService.java:465` — 每次变更导出 `skills.public.json` 到快照目录

这意味着"技能启用状态"已经有一个**面向用户的真源**。修订后的单一真源链：

```
用户点开关 (App) → skills 表 → skills.public.json 快照 → worker 读取并合并
                                                        ↓
                                       worker.conf 的值只作为"部署默认"，被快照覆盖
                                                        ↓
                                            归属表 ownership.json（含 enable 位）
                                                        ↓
                                                        hook
```

冲突处理：快照存在且未过期 → 以快照为准并打日志；快照缺失/过期 → 用 `worker.conf`；
两者都没有 → 用编译默认。**不允许**出现"状态页显示开、实际没生效"而无日志。

另外 `execution_logs` 表已就位但没人写（【代码】注释 T10）。本方案要求技能执行都写一行
（skill/action/ok/detail），这样"为什么没反应"在 App 里可查，不必翻 logcat。
