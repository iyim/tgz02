# T9-28 技能目录（Factory / Local / AI / Hybrid 与"不重复开发"判定）

对应审查意见 §三（额外要求）。目标不是列清单，而是给出**归属判定规则**，
使"以后加技能"变成"注册 + 实现回调 + 定义参数与权限"，而不是改语音路由。

证据标记：`【实测】` 真机跑出来的；`【代码】` file:line；`【推断】` 未验证。
凡 `【推断】` 的能力都不得直接进入 P0–P4 的实施范围，必须先测绘。

---

## 1. 归属判定规则（先判归属，再谈实现）

按顺序问三个问题，第一个命中即为归属：

| 顺序 | 问题 | 命中 ⇒ 归属 |
|---|---|---|
| Q1 | 原厂**已经能正确完成**，且我们能观察到它成功（日志/`dumpsys`/屏幕/播报）？ | **factory** |
| Q2 | 原厂做不到（无能力 / 这个账号无权益 / 报"控制不了音箱里的应用"），且本机能自己完成？ | **local** |
| Q3 | 需要理解与生成（闲聊、知识、故事、改写、摘要），或需要组合本地数据做自然语言表达？ | **ai**（表达由模型，动作仍走 local） |

推论（要写进评审清单）：

- **Q2 必须带"原厂实测失败"的证据**，不能凭"我觉得原厂不会"就自建。T9-25 音乐就是这条路：
  【实测】原厂回"我这边暂时没法打开新视听，也控制不了音箱里的应用"（`evidence/t9-25`，事件 330）。
- **Q1 命中后不得再自建**（哪怕自建更好）。天气/闹钟/时间/音量/开关屏都属于此列。
- 若 Q1 后来退化（原厂云端下线），再走 Q2，并保留回退开关。

## 5. Hybrid（AI 理解 + 本地执行）——目前为 0，是下一步的形态

| 候选 | 为什么是 hybrid | 需要的组件 |
|---|---|---|
| "把刚才那首歌加到我喜欢" | 需要理解指代（AI/上下文）+ 本地歌单写入 | `skill_ctx` + `music.favorite`（新回调） |
| "明天有什么安排，念给我听" | 本地 `schedules` 数据 + 自然语言表达 | `schedule.query` + L2 二轮（`needs_phrasing`） |
| "讲个恐龙故事" | 内容由 AI，播放/打断由本地 TTS 队列 | L3 + `tts_enqueue`（已有） |
| "按昨晚那个音量放歌" | 上下文（音量历史）+ 本地执行 | `skill_ctx.volume` + 参数补全 |

原则：hybrid 里**动作永远是 local**，AI 只产出"要做什么/说什么"，不产出"怎么做"。

## 6. 冲突与互斥（必须写死）

| 冲突 | 规则 |
|---|---|
| factory 闹钟 vs 自有闹钟 | **只能有一个 owner**。owner=factory 时 `alarm.set` 不注册、`0x100` 置位；owner=local 时反过来并清位。两者同时成立 = 双执行（F1），归属表校验直接拒载 |
| factory 媒体 vs 本地音乐 | 同上。`music` 没有 route 位（【代码】`intent_route.c:855`），但这**不再是问题**：ownership 生效期间 hook 以 `owner` 为准（`factory ⇒ PASS`），`mask` 只在回滚路径（`H6_DISABLED`）才被使用。所以"music 的 owner 切回 factory"是合法且安全的操作，不需要动 `ir_route_bit()`。**前提是 P1 必须先落地"owner 优先、mask 仅回滚"这条语义** |
| 记忆 vs AI | 记忆条目**不进提示词**（SECURITY §6），避免隐私外泄与幻觉 |
| 日程 vs 原厂日程 | 【推断】原厂可能有日程/提醒技能（corpus 有"今天都有什么日常/日程"）→ 先测绘，若可用则 factory |

> 上表第二行是一个**真实的架构约束**：`owner` 与 `route_bit` 必须联动。
> 本方案因此把"`owner=factory` 必须有 route 位、`owner=local` 必须没有"作为表校验规则 V3 的对称条款，
> 并在 P1 里给 `music` 预留一个"可回收的位"（仅当 owner 切 factory 时置位，代码常量控制）。

## 7. id 命名与清单映射

```
<域>.<动作>          小写，点分，稳定不改（日志/事件/工具名/DB execution_logs 都用它）
music.play  music.ctrl  device.status  memory.add  memory.query
schedule.add  schedule.query  alarm.set  app.open  config.web
```

与 App 侧的关系：

| App | worker | 关系 |
|---|---|---|
| `skills(id,name,enabled,state,sort)`（【代码】`Db.java:75-82`） | 归属表 `enabled` 位 | App 是**用户可见的开关真源**，经 `skills.public.json` 快照下发 |
| `execution_logs(skill,action,detail,ok,ts_ms)`（【代码】`Db.java:84-91`） | 技能执行结果 | 每次执行写一行（T10 预留，本方案要求提前用上） |
| `SKILL_ALARM` / `SKILL_CALENDAR` 卡片（【代码】`SkillsHomeActivity.java:98-109`） | `alarm.set` / `schedule.*` | 卡片状态应与归属表一致（避免"页面写着规划中、实际能语音用"或反之） |

## 9. 目录与"技能中心"页面的一致性

审查意见提到"不要变成只能执行固定命令的遥控器"。落地到页面：

| 页面位置 | 现在（【代码】） | 修订后 |
|---|---|---|
| 技能中心 · 闹钟 | 已开（`skillCard(...,true)`） | 显示 owner=factory，点进仍是我们的闹钟页（只读展示 + 跳原厂） |
| 技能中心 · 日程 | 已开，但无语音 | 显示"未接入语音"，避免误导 |
| 技能中心 · 音乐 | **仍写"待接入"**（`SkillsHomeActivity.java:107`） | 必须改成"已可用"，与实际能力一致（现在文案是错的） |
| 技能中心 · 天气/设备控制 | "规划中" | 天气改"由原厂提供"；设备控制按 M3 结论 |
| 设置 · 技能开关 | 无 | 新增"哪些技能由本机执行"（只读展示 owner + 总开关） |

> 注意：`SkillsHomeActivity.java:107` 的"音乐 · 待接入"是**现存的产品文案错误** ——
> 音乐已经能用（T9-25/T9-26 真机验证）。这类"页面与能力不一致"会直接误导用户与后续开发，
> 建议在 P0 顺手修（不改架构，只改文案）。
