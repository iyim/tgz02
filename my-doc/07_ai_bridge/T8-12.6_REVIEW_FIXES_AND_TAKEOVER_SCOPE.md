## 三、R13 / R14 修复策略复核（任务二）

### 3.1 三条来源与必须放行的两条（复核结论不变）

【静态已证实】`SessionDispatch::onNlpResult` 全库 3 个调用点：

| 调用点 | 来源 | `type` | `res` | 处理 |
|---|---|---|---|---|
| `0x111134` | `SessionManager::exitTalk(sid,1)`（`what=14` 触发，`flag=1`） | 2 | 新建 152 B `[+4]=1,[+8]=2` | **必须放行** |
| `0x11cbf8` | `what=1` 收尾块（状态 != 6 时） | 3 | NULL → 内部合成 `[+8]=3` | **必须放行** |
| `0x11d674` | `SessionProxy::onNlpResultInner(int,int,res)`（`what=7` 链路） | 透传 | 透传 | 按会话判定 |

`type=2` 的原厂副作用（复核第二问）：`exitTalk` 在调用 `onNlpResult` 之后还会执行
`0x111138 ldr r0,[r7]; ldr r1,[r0,#4]; blx r1`（销毁合成对象）与 `0x1111a0-0x1111c4` 的 `IMmiCore` 两处虚调用。也就是说：**放行 `type=2` 才能让这两处 MMI 通知照常发生；但即使被拦，`exitTalk` 自身的清理仍会跑**——被吞掉的恰好是"结果投递/播报"这一段。这就是"状态分叉"的具体形态。

### 3.2 收尾块的幂等门（复核"重复/提前结束"）

【静态已证实】`0x11c9f4`：

```
11c9f8  bl   SessionManager::getSessionStatus()
11c9fc  cmp  r0, #6
11ca00  bne  0x11cbcc        ; 状态 != 6 → 收尾
11ca04  …日志 392… → 返回    ; 状态 == 6 → 只打日志
```

结论：**不会重复收尾**；**不会由这段引发提前收尾**（它只在 `what=1` 且状态 != 6 时执行）；**状态分叉确实存在**（`setSessionStatus(6)` 在补丁点前、`onNlpResultEnd` 在补丁点后）。

### 3.3 第五阶段建议里的两处错误（本阶段纠正）

**错误一：在 `tg_nlp_cb` 里对 `type=3` 立即 `t8_to_on_session_end()`（清槽）。**

时序问题（评审第 3 点）：该回调返回 0 之后，**原厂 `onNlpResult` 与紧随其后的 `onNlpResultEnd` 都还没执行**。若此刻立即清槽，那么：

- 同一轮里**已经在 Handler 队列中排队、尚未被处理**的 `what=7`/`what=11` 结果，会因为槽位消失而**被放行给原厂**→ 该轮接管失效（漏拦，不是安全问题但是功能问题）；
- 收尾与结果处理之间的先后顺序不由我们控制（不同消息、同一 Handler 队列）。

**修正设计**：收尾时**不清槽，只压缩截止时间**：

```c
/* t8_to_on_session_end() 语义改为"提前到期"，而不是"立即清空" */
void t8_to_on_session_end(t8_to_state *st, const char *session)
{
    /* 保留原函数：立即清空 */
    /* 新增：t8_to_expire_soon(st, session) —— deadline = min(deadline, now + T8_TO_GRACE_MS) */
}
```

新增 `T8_TO_GRACE_MS = 2000`：宽限期内仍按"已登记"拦截（保护同轮晚到结果），宽限期后自然过期（槽位不再被占 30 s）。

**错误二：把两个 5 s 全局窗口直接删掉 / 让 session 缺失直接放行。**

见 §3.4——这不是"代码冗余"，是原有安全策略，不能翻成 fail-open。

### 3.4 五个场景的影响分析（评审要求逐项）

前提：接管开启时，`should_drop()==1` 表示"这一条 AI 结果由我们接管，原厂不执行"。
安全方向 = **宁可多拦，不可漏执行**；稳定方向 = 不要把无关会话一起拦死。

| 场景 | 现状行为【静态已证实】 | 风险 | 本阶段建议 | 是否改变安全方向 |
|---|---|---|---|---|
| **① session 缺失**（`sid<=0` → key 为空） | 开 **全局** `failclosed_until_ms = now+5s`；该次必丢；**5 s 内任何未登记 sid 也被丢** | **跨会话误拦**：别的会话在 5 s 内不能接管也不能放行原厂 → 表现为 5 s 内"AI 结果全部被吞" | 保留"该次必丢"；窗口**按触发它的 key 绑定**（key 为空时也单独成项），不污染其它 sid | **不变**（仍是 fail-closed） |
| **② 槽位容量耗尽** | `alloc` 失败 → **全局** `degraded_until_ms = now+5s`；溢出会话当次丢 | 同上，全局污染 | 同上：窗口只绑溢出会话的 key | **不变** |
| **③ sid 复用** | 新 `on_final` 命中已有槽 → 只刷 TTL（`reentrant_marks`） | 旧会话的"未到期槽"会让新会话立刻进入接管（可能拦掉本不该拦的） | 收尾时压缩截止时间（§3.3），使旧槽在 2 s 内失效；新 `on_final` 重新登记 | **不变** |
| **④ 正常会话结束** | 无收尾钩子，只能等 30 s TTL | 30 s 内同 sid 的新会话被误接管（若 sid 复用） | `type=3` 时压缩到 `now+2s` | **不变** |
| **⑤ takeover 状态异常**（`mutex_ready==0`、或 `enabled` 读到 1 但初始化失败） | `t8_to_should_drop` 首行 `if (!st->mutex_ready) return 1`；`on_final` 返回 `T8_TO_TAKE_FAILCLOSED`；`tg_nlp_cb` 的 `NLS_FAILCLOSED` 直接 `return 1` | 拦得更多（可能吞掉正常结果） | **保持不变**，这是最后一道安全网 | **不变** |

**结论**：现有策略的**唯一真实缺陷是"窗口作用域是全局"**，不是"窗口存在"。最小修改 = **把两个全局时间戳换成"按 key 的窗口数组"**（或等价地：在窗口生效期内只对"触发者 key"生效），**不删除、不改成 fail-open**。

### 4.2 谁能绕过当前补丁

当前补丁只在 `onNlpResult` 上（`nlu_patch`）。因此 **`onNlpResultInner` 与 `onPushNlpResult` 两条路径完全不受约束**。前者有**已知且可达**的触发链（云侧回包，经 C1–C5），后者触发者不明但符号可被 `dlsym` 调用（U11）。

### 4.3 三个入口共用现有 Hook 机制的可行性（ABI 层）

- 三者都是 ARM32 `void` 成员函数，prologue 均为 `push {…} / add r11,sp,#N`（**无 PC 相对**，已逐条证明）。
- 现有 stub 的回调原型是 `cb(self, a1, a2, a3)`；对三者都成立，只是解释不同：

  | site | a1 | a2 | a3 |
  |---|---|---|---|
  | `onNlpResult` | sid | **type** | **res** |
  | `onNlpResultInner` | sid | **res** | 无意义（`r3` 未初始化） |
  | `onPushNlpResult` | sid | **res** | 无意义 |

  → **不需要新的 stub 形态**，只需在回调里按 site 解释参数。`type` 分类只对 `onNlpResult` 有效（另两者没有 type，且它们的语义只有"真实结果"）。
- 返回值：三者都是 `void`；现有 stub 的"跳过"分支返回 `r0=0`，对三个入口都无害（现有代码已在 `onNlpResult` 上这么用）。

### 4.4 最少补丁点

| 目标 | 需要几个补丁点 |
|---|---|
| "覆盖全部技能执行路径" | **3**（`playAudios` 全库仅这 3 个调用者，覆盖 3 个即封闭） |
| "只覆盖已知可达路径" | 2（`onNlpResult` + `onNlpResultInner`；`onPushNlpResult` 目前无可达触发者） |

按评审给出的优先级（"不能让本地指令接管后，又从另一条未覆盖的路径执行原厂技能"），**推荐 3**：第三个的成本与第二个相同（同一 stub 模板、同一 `nlu_patch` 事务机制），而收益是把 `what=12` 这条"目前不可达但可被 `dlsym` 激活"的口子一并封住。

### 4.5 重复执行 / 遗漏执行分析

| 情形 | 结论 |
|---|---|
| 同一轮同时命中两个入口 | **不会**：三个入口分别由 `what=7` / `what=11` / `what=12` 触发，一轮只投递其中一种 |
| 补丁后重复执行 | **不会**：跳过的是被调函数本体，调用者（`what=7/11/12` 分支）在返回后只做 `msg[+12]=0`、`return`，不会重投 |
| 补丁后遗漏执行 | 只有当"某条执行路径既不在 3 个入口内、也不经 `playAudios`"时才可能。当前证据：`playAudios` 的 3 个调用者被完全枚举，`processMediaCommand`/`preProcessCommand` 的唯一调用者也在 `playAudios` 内 → **无第四跳** |
| 新风险 | 三入口同时接管后，**`type` 分类只存在于 `onNlpResult`**；`onNlpResultInner`/`onPushNlpResult` 只能按会话判定，若某天它们被用于"收尾"语义，就会误拦（记为 U14，需在实现时加断言：这两个 site 的 `res != NULL`） |

### 4.6 推荐方案

> **补 3 个点**：`SessionDispatch::onNlpResult`（已有）+ `onNlpResultInner` + `onPushNlpResult`。
> 回调按 site 解释参数；`type∈{2,3}` 仅在 `onNlpResult` 上放行；另两个 site 只要 `res != NULL` 就按会话判定。
> 需要一个"多点事务"：要么把 3 个点纳入 `nlu_patch` 的同一次 `world_frozen` 事务（任一点失败即全部回滚），要么串行安装并记录 `installed_mask`，任一点失败则停止并回滚已安装的点。

## 五、R21 / U10 双库绑定（任务四）

### 5.1 第五阶段结论中的过度断言（本阶段收回）

第五阶段写过："`dlsym(RTLD_DEFAULT)` 对 6 个符号可靠（两库都定义全套 ⇒ 赢家必然同一库）"。**这句话只对"全局组（global group）"成立**，不能推广：

| 情况 | bionic 行为 | 后果 |
|---|---|---|
| 两库都在**全局组**（被 `DT_NEEDED` 拉入，或 `dlopen` 用 `RTLD_GLOBAL`） | 符号查找走同一个全局组、同一个顺序 → 每符号只有一个赢家，`dlsym(RTLD_DEFAULT)` 与"库内部 PLT 绑定"一致 | 第五阶段的断言成立 |
| `libagmmi` 被 **`RTLD_LOCAL`** `dlopen` | 它进的是**本地组**：外部引用看不到它；但它**自己的重定位**会先在自己的本地组里找到自己那份 → **它内部的 PLT 调用绑定到自己** | `dlsym(RTLD_DEFAULT)` 返回 `libsmartbox` 那份，而 `libagmmi` 内部执行的是它自己那份 → **两者不一致** |

【静态已证实】的事实只到这一步：

- 两库都 `DEF` 全套符号、都是 `GLOBAL DEFAULT`（非 `protected`）、都**没有** `DF_SYMBOLIC`；
- 没有任何 `.so` `NEEDED libagmmi`；`libagmc`/`libagui`/`libsaladapter` `NEEDED libsmartbox`；
- 因此 `libagmmi` **只能**由 `dlopen` 进入（`RTLD_LOCAL` 或 `RTLD_GLOBAL` 未知）→ **本地组/全局组归属未定** → **U10 不能关闭**。

### 5.2 逐符号的桩 / GOT 槽位（本阶段新增，静态）

| 符号 | libsmartbox 桩 | GOT 槽 | libagmmi 桩 | GOT 槽 |

### 5.3 逐符号比对方案（设备只读）

对每个符号、每个库各做一次：

```
maps:  base_smartbox, base_agmmi        （缺哪个就记 "not loaded"）
read:  v_smartbox = *(u32*)(base_smartbox + GOT_smartbox[sym])
       v_agmmi    = *(u32*)(base_agmmi    + GOT_agmmi[sym])
判据:  v == base_smartbox + vaddr_smartbox  → 绑定到 smartbox 那份
       v == base_agmmi    + vaddr_agmmi     → 绑定到 agmmi 那份
       其它                                  → 第三方/未解析 → 停止
```

**两种典型结果及其含义**

| 结果 | 含义 |
|---|---|
| 两库的槽位都指向**同一个** `base+vaddr` | 正常全局组行为：一个赢家，`dlsym` 与内部绑定一致 |
| `smartbox` 槽位指向自己、`agmmi` 槽位也指向**自己** | `libagmmi` 在本地组（`RTLD_LOCAL`）→ **两份实现都在被用** → 只补一份必然漏 |

第二种情况正是"不能断言 `dlsym` 必然一致"的实证路径，也是**必须按库分别核验**的原因。

### 5.4 设备只读核验：所需数据、权限、失败判据

| 项 | 内容 |
|---|---|
| 需要的数据 | `/proc/<pid>/maps` 中两库的映射行（基址、顺序、是否装载）；`/proc/<pid>/mem` 在 `base+GOT` 处的 4 字节读（每符号每库一次，共 16 次） |
| 权限 | `uid 0`（root）；SELinux 当前为 Permissive；读 `/proc/<pid>/mem` 需要 `PTRACE_MODE_ATTACH` 检查，root 满足。**不写任何内存、不注入、不 ptrace-stop** |
| 失败判据（任一命中即停） | ① 目标进程 pid 变化；② `libsmartbox` 未装载；③ 任一槽位值不等于两个候选之一；④ 同一符号两库槽位指向不同 `base+vaddr` 且都不是自己那份；⑤ `maps` 中两库基址与静态 `p_vaddr` 对不上 |
| 输出 | 每符号一行：`sym=<name> smartbox_got=0x… -> <lib:+vaddr> | agmmi_got=0x… -> <lib:+vaddr>` + 结论 `winner=<lib>` 或 `split` |

**本阶段未执行**（禁止操作真机），因此 **U10 保持"未证实"**。
