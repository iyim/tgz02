## 一、任务一：pthread 生命周期与检测器自身的竞争

### 1.1 审查指出的两个缺陷，都是真的

第七/八阶段 `scenario_concurrent()` 的收尾是：

```c
/* T8-12.8（错） */
for (i = 0; i < 4; i++) {
    rc[i] = pthread_create(&th[i], NULL, worker, &w[i]);
    if (rc[i] != 0) create_ok = 0;          /* 继续尝试，然后…… */
}
if (!create_ok) { pthread_mutex_destroy(&st.mu); return; }   /* 线程可能还在跑 */
...
jrc[i] = pthread_join(th[i], NULL);
if (jrc[i] != 0) join_ok = 0;                /* 然后照旧读计数器、销毁 mutex */
```

两个后果都成立：**create 部分成功时立刻销毁 mutex**；**join 失败后仍然把"线程已结束"当成事实**。`need_lock()` 诊断路径也确实在读 `depth/owner`（其他线程正在锁内改写）并写全局 `fails`。

### 1.2 修复

```c
/* 线程身份用 TLS 整数，不碰 pthread_t */
static __thread int g_tid = 0;              /* main = 0, worker = tid + 1 */
#define A_LD(p)   __atomic_load_n((p), __ATOMIC_RELAXED)
...
static void need_lock(state_t *s, const char *who)
{
    if (A_LD(&s->depth) <= 0 || A_LD(&s->owner) != g_tid) {
        A_ADD(&s->lock_violations);         /* 只写原子计数，不写全局 fails */
        printf("  [FAIL] LOCK-AUDIT violation: %s ...\n", who);
    }
}
```

`lock()`/`unlock()` 用同一套 relaxed 原子维护 `owner/depth`。这样**即使真的漏锁，检测器本身也不再引入新的数据竞争**，所以它可以和 TSan 一起跑（这正是本轮 TSan 主跑 0 报告的前提之一）。

创建/join：

```c
for (i = 0; i < 4; i++) {
    if (t_create(&th[i], &w[i], i) == 0) ncreated++; else { create_ok = 0; break; }
}
if (!create_ok) {
    for (i = 0; i < ncreated; i++) if (pthread_join(th[i], NULL) == 0) njoined++;
    chk(njoined == ncreated, "已成功创建的线程全部 join 完成");
    pthread_mutex_destroy(&st->mu);          /* 现在才允许销毁 */
    chk(counters_snapshot(st, w, ncreated, 0, &s) == -1, "部分创建时拒绝读取共享计数器");
    g_incomplete = 1; return;
}
```

join 失败分支：

```c
if (!join_ok) {
    chk(counters_snapshot(st, w, 4, 0, &s) == -1, "join 失败后拒绝读取共享计数器");
    chk(g_mutex_destroyed == 0, "join 失败后没有销毁 mutex");
    printf("  [INFO] 有线程是否退出无法确认：按 INCOMPLETE 处理，绝不 PASS\n");
    g_incomplete = 1; return;                /* 不 free、不销毁、不读计数器 */
}
...
if (g_incomplete) { printf("RESULT: INCOMPLETE ..."); hard_exit(2); }
```

`counters_snapshot()` 是**行为断言**而不是注释：`all_joined == 0` 时它返回 -1 并拒绝读，正常路径则要求返回 0。

### 1.3 顺手发现并修掉的第三个缺陷（审查没提，但更脏）

加 `--join-abandon`（线程**真的**不被回收）后，Linux 上先打印 INCOMPLETE 再 **SIGSEGV（EXIT=139，core dumped）**：

```
  [INFO] 有线程是否退出无法确认：按 INCOMPLETE 处理，绝不 PASS
Segmentation fault (core dumped)
EXIT=139
```

原因不是"进程退出不安全"，而是**我的测试写错了**：`worker_t w[4]` 在 `scenario_concurrent()` 的**栈帧**上，被弃置的线程仍在 `w[i].l_*++`，而函数返回后那个栈帧已被主线程复用 → 写进别人的栈。修复：`static worker_t w[4]`（状态本来就已在堆上）。修复后两个平台都干净退出 2。

证据：`evidence/t8-12-p9/nas-tsan/v3_join_abandon_before_fix.txt`（修复前）/ `plain_join_abandon.txt`（修复后）。

### 1.4 六个模式的跨平台一致性

| 模式 | Windows 主机 | Linux（NAS，无 TSan） | Linux（NAS，TSan） |
|---|---|---|---|
| 无参数 | PASS 71/0，exit 0 | PASS 71/0，exit 0 | PASS 71/0，exit 0，0 race |
| `--create-fail 2` | INCOMPLETE 60/0，exit 2 | 同左 exit 2 | 同左 exit 2，0 race |
| `--join-fail 1` | INCOMPLETE 59/0，exit 2 | 同左 exit 2 | 同左 exit 2，0 race |
| `--join-abandon 1` | INCOMPLETE 59/0，exit 2 | 同左 exit 2 | 同左 exit 2，0 race |

| `--race-true` | PASS（无 TSan，无意义） | FAIL 71/1，exit 1 | PASS 71/0，exit **66**，**1 race** |

`--race-control` 在 TSan 下 0 报告不是漏洞，是正确行为，见 §2.3。

## 二、任务四：在 Linux 上真跑 TSan

### 2.1 环境（这段是新的，因为之前确实是空白）

用户 NAS：`Linux 6.18.18.c1126-trim #1126 x86_64`，Debian 12 bookworm，12 核；容器 `debian:bookworm-slim` + `gcc (Debian 12.2.0-14+deb12u1) 12.2.0` + `libtsan.so.2.0.0`。专用目录 `/vol2/1000/t8_12_9_tsan`，**容器内编译运行、目录 bind-mount**，**没有在 NAS 宿主机上安装任何东西**，也没有改系统的任何配置。

> 过程记录（不含在结论里）：第一次尝试用官方源，apt 在容器里挂了 18 分钟仍在下载，放弃；第二次换阿里云镜像但同时加了 `http_proxy=192.168.1.13:7890`，容器连不上宿主的代理端口，apt 失败；第三次**只用镜像、不加代理**，2 分钟内装完。

### 2.2 主结果

```
file                RESULT                          exit  TSan 报警数
tsan_normal         PASS (checks=71  fails=0)        0     0
fsm_tsan_run        PASS (checks=551 fails=0)        0     0
```

`tsan_normal.txt` 里 `ThreadSanitizer` 字样出现 **0 次**（不是"报警被过滤"，是整个文件里一处都没有）。也就是说：4 线程 × 20000 次、覆盖登记/本地判定/收尾/查询/时钟推进/空 key 的并发场景，在 `-fsanitize=thread` 下**没有任何未同步访问**。

### 2.3 两个对照，各证明一件事

**对照 #1 `--race-control`（拆成读-写回，仍在锁内）**：TSan 报告 **0**，但精确计数断言 **FAIL**（`11055 vs 13333`）。

> 这说明 TSan 和计数恒等式是**两个不同的 oracle**：TSan 只看"有没有未同步访问"，丢不丢更新它管不了；反过来计数恒等式看不出"读到脏值但没丢"。两者都要有，谁也不能替代谁。

**对照 #2 `--race-true`（真正的无锁自增）**：这是本轮最关键的一条证据，用来排除"TSan 装了但没生效"这种假绿灯。

```
==================
WARNING: ThreadSanitizer: data race (pid=193)
  Read of size 8 at 0x7b8800000008 by thread T1 (mutexes: write M2):
    #0 alloc_locked        t8_12_9_lifecycle_model.c:229
    #1 on_final            t8_12_9_lifecycle_model.c:299
    #2 worker              t8_12_9_lifecycle_model.c:638
  Previous write of size 8 at 0x7b8800000008 by thread T2:
    #0 clock_tick_worker   t8_12_9_lifecycle_model.c:197
    #1 worker              t8_12_9_lifecycle_model.c:658
```

`EXIT=66`（`TSAN_OPTIONS exitcode=66`）、`TSAN_RACE_WARNINGS=1`。**TSan 在这个环境里确实在检测、确实会报警。** 所以 §2.2 的"0 报警"是可证伪的结论，不是"工具没跑起来"。

### 2.4 TSan 能证明什么、不能证明什么

| 能 | 不能 |
|---|---|
| 会话表模型在 4×20000 并发下无未同步访问 | 不能证明 `libsmartbox.so`（ARM32）无竞争 |
| 检测器自身（`need_lock`）不再引入竞争 | 不能替代真机探针 / 设备侧观测 |
| 上表 6 个模式在 TSan 下无额外报告 | 不能证明"逻辑正确"，那要靠语义断言 |

TSan 在这里替掉的是"第七阶段那句 4 线程 PASS"的可信度缺口，不是设备验证。

## 三、任务二：三点事务的冻结/恢复生命周期

### 3.1 先修一个模型错误：停止 PC 的检查必须在冻结之后

第八阶段把 `pc_in_range` 放在 `PRECHECK` 里（冻结之前）。这在真实 Injector 里是**无效检查**：检查完到写字节之间，线程可以自己走进入口。真实 `tg_injector.c` 的顺序是 `pause_and_check`（先停线程再查 PC），模型必须对齐：

```
PRECHECK(读原字节) → FREEZE(一次) → 停止 PC 检查 → INSTALL → 组读回 → RESUME(一次) → verdict
```

### 3.2 冻结与恢复各一次，并且有顺序证据

```c
static int freeze_threads(world_t *w) {
    if (w->freeze_count != 0) { w->order_violation++; return -1; }  /* 二次冻结直接记违规 */
    w->freeze_count++; w->ev_freeze = step(w);
    if (w->f.freeze_fail) return -1;          /* 一个都没停住 */
    w->froze = 1;
    if (w->f.freeze_partial_fail) return -1;  /* 停了一部分，attach 失败 */
    return 0;
}
```

不用"注释说顺序对"，用事件序号断言：

| 断言 | 含义 |
|---|---|
| `ev_freeze < ev_first_store` | 冻结在第一次字写之前 |
| `ev_freeze < ev_pc_check` | 冻结在停止 PC 检查之前 |
| `ev_group_readback < ev_resume` | **三点全部读回之后**才恢复线程 |
| `ev_rollback_done < ev_resume` | 失败路径上**回滚完成之后**才恢复线程 |
| `freeze_count == resume_count == 1`（凡是冻结过） | 不逐入口重复冻结/恢复 |
| `order_violation == 0` | 没有发生二次 freeze/resume |

### 3.3 verdict：唯一允许调用方分支的东西

```
V_SUCCESS                     装好、读回、线程已恢复
V_INSTALL_FAILED              什么都没改，线程已恢复
V_ROLLBACK_FAILED             入口脏，线程已恢复
V_RESUME_FAILED               线程可能仍冻结（安装可能已成功）——绝不可当成功
V_ROLLBACK_AND_RESUME_FAILED  上面两件同时发生
```

判定优先级写死并逐场景断言：

```c
if (!install_ok && state == ST_ROLLBACK_FAILED)  → ROLLBACK_FAILED 或 ROLLBACK_AND_RESUME_FAILED
else if (!resume_ok)                              → RESUME_FAILED
else if (!install_ok)                             → INSTALL_FAILED
else                                              → SUCCESS
```

`[S10]` 就是"安装成功但恢复失败"：3 个入口全部是补丁态、FSM 到 `DONE`，但 verdict 是 `RESUME_FAILED`，并断言 `verdict != V_SUCCESS`。`[S11]` 是"回滚失败 + 恢复失败"，verdict `ROLLBACK_AND_RESUME_FAILED`，且断言它既不是 `INSTALL_FAILED` 也不是 `SUCCESS`；随后清掉写故障执行 `install_recover()` → `RECOVERED`，但 verdict **仍是** `RESUME_FAILED`（线程还冻着），且恢复过程没有再 freeze/resume 一次。

### 3.4 场景与断言

原有 24 类单点故障 + 9 例扫描**全部保留**（S0/S1*/S1f/S1p*/S2*/S3*/S4*/S5*/S5b/S6*/S7/S8/S9），新增：

| 新增 | 内容 |
|---|---|
| `[S1q]` | 冻结部分成功（停了一部分后 attach 失败）→ 必须恢复，verdict INSTALL_FAILED |
| `[S10]` | 安装成功、恢复失败 → RESUME_FAILED |
| `[S11]` | 回滚失败 + 恢复失败 → ROLLBACK_AND_RESUME_FAILED；恢复后仍 RESUME_FAILED |
| `[S12]` | 6 组单字安装故障全部满足 freeze==1 / resume==1 / 非 SUCCESS / 非 RESUME_FAILED |

断言数 **231 → 551**（运行时统计：`check_invariants()` 现在每个场景跑 14 条，含 I6/I7/I8）。

### 3.5 这份模型仍然不是 Injector

`FROZEN` 在这个模型里是一个状态 + 计数 + 事件序号，**不是 ptrace**。它证明的是"事务的**状态推进顺序**正确、每种失败都有不冒充成功的结论"，不能证明 `rc_pause_all`/`rc_resume_all` 在设备上真的停住了线程、也不能证明 `pause_and_check` 的重试窗口足够。**不能拿 551 条 PASS 批准生产 `np_group`。**

## 四、任务三：P0-1 保持不降级

按审查要求：

2. 三条风险逐条保留（`T8-12.8` §2.5 原文未删）：
   - **R-2 TTL 到期后旧结果仍可能放行**（压制长度 = 既有 TTL，不是新常数）；

   - R-4 压制可能吞掉本该放行的结果（策略取舍，待审查确认）。

4. **禁止用延长 TTL 宣称解决**：TTL 是既有常量，把它调大只是把窗口推远，不产生代次信息。任何"把 30 s 改成 5 min 就解决了"的说法都不成立。
5. 下一步研究方案（只读，不改行为）：

| 步骤 | 内容 | 产出 | 前提 |
|---|---|---|---|
| O1 | 在 `tg_nlp_cb` 里只读打印 `Message{what,arg1,arg2,obj}` + `NlpResult` 前 160 字节 hexdump + `[+140]` sid + `CLOCK_MONOTONIC` + 本 hook 自增计数 | 每轮一条记录，判断有没有"每轮唯一"的字段 | 设备授权（**尚未获得**） |

O1 是**纯读**：不写任何共享状态、不改返回值、不改变时序，输出到自己的环形缓冲/文件；必须在 takeover 关闭状态下做。
