# T8-15.5 续听请求可靠性修复与连续对话阶段验收

基线：`763abda090abebf6a098e02b3904798889a2780c`
本轮提交：`1f8ae476`（main，已推送）

> ⚠️ **后续修订**：本文描述的"`clock-base reset` 二次观测确认"已被 `T8-15.5R` 删除
> （见 `T8-15.5R_CLOCK_RESET_REMOVED.md`）—— 审查指出"同一个异常序号读两次就受理"本身
> 就是误开麦路径。原子写、严格解析、停止/退出撤销、共用协议代码均保留。

**结论**：上一轮审查指出的"请求文件读写竞态"确实存在，并且比审查描述的更宽——不只是空文件，
**被截断的半截数字（`121635016` → `1216`）同样会被旧的"倒退很多就当换计时基准"规则受理成一次开麦**。
本轮把它按"先校验、再二次确认"重做，写侧改原子替换，并把"停止/退出时撤销在途请求"补上。
Host 单测 55 项、真机 8 个场景（含静默对照）全部通过，T8-15 连续对话阶段可以验收。

## 1. 修的到底是什么

### 缺陷 A（审查指出）：空文件被当成"计时基准重置"

旧判定只有两行：

```c
if (seq > last_seq || (last_seq - seq) > 60000) { ...受理... }
```

`fgets` 读到空文件时 `seq` 保持 `-1`，`last_seq - (-1)` 必然大于 60000 → 受理 → 开麦。
现场是**真实竞态**：旧写侧 `fopen(..., "w")` 先截断再写，守卫的 120 ms 轮询很容易撞进这个窗口。

### 缺陷 B（审查未提，host 单测现场抓出）：半截数字同样会被受理

只加"数值是否合法"不够。`121635016` 被截成 `1216` 时：

- 内容是合法十进制、非负 → 校验通过；
- `1790000000 - 1216 > 60000` → 命中"大幅倒退"；
- `1216 >= 1000` → 我第一版加的"下限"也挡不住（真序号是 9 位数，它的前缀大多仍然 ≥ 1000）。

第一版修法在 host 单测里当场被判 FAIL（`prefix [1216] fired v=1216`）。所以最终形态不是"加阈值"，
而是**倒退必须被第二次观测确认**（见第 2 节）。

### 缺陷 C：写侧非原子

`fopen(T8_CONT_REQ_FILE, "w")` 会先截断。改成"同目录临时文件 + `rename` 原子替换"，
读侧永远只会看到"完整旧值"或"完整新值"。

### 缺陷 D：停止/退出时在途请求没人撤销

worker 侧 `native_relisten_due_ms`（原厂指令后 1200 ms 补一次开麦）和 `native_rel_waiting`
在用户说"停止/退出"时没有清掉，只能靠守卫的 hold 文件兜底。现在两边都撤：
`native command: pending re-listen cancelled by exit (due_in=xxx ms waiting=1)`。

### 缺陷 E：新请求顶替旧请求时静默

连续两个原厂指令时，第二条请求会覆盖还没开麦的第一条。行为本身是对的（只需要一次开麦），
但旧代码不留痕。现在记 `continuity req: seq=X superseded by seq=Y (not fired yet)` 并计入 `req_dropped`。

## 2. 实现：请求契约抽成一份共用代码

新增 `android/tg_req_seq.h`，**worker 与守卫编同一份**（不是两份实现，也不是测试用的副本）：

| 函数 | 作用 |
|---|---|
| `tg_req_parse(buf,n,&seq)` | 严格解析：空内容、负数、前后夹脏字符、超长、溢出、两份数字 → 全部返回失败 |
| `tg_req_read(path,&seq)` | `fopen` + `fread` + 上面的解析；打不开/空文件同样失败 |
| `tg_req_write_atomic(path,seq)` | 写 `<path>.tmp` → `fflush`+`fsync` → `chmod 0666` → `rename` 覆盖 |
| `tg_req_accept(st,seq,now)` | 受理判定：`first` / `new` / 需二次确认的 `clock-base reset` |

受理规则最终形态：

```
seq 非法（解析失败）        -> 忽略，不动基线
seq < 1000                  -> 忽略（真序号是 CLOCK_MONOTONIC 毫秒，9 位数）
last_seq < 0                -> "first"（守卫启动时文件是空的，这条就是真请求）
seq > last_seq              -> "new"
倒退 > 60000 且距上次重置 > 3 s
    -> 只记候选 cand_seq，本次不触发
下一拍（>=120 ms 后）
    seq >= cand_seq         -> "clock-base reset"（确实换了计时基准，受理一次）
    超过 600 ms 没确认      -> 候选作废
```

为什么"两次观测"能挡住半截文件而放行真重置：

> ⚠️ 这一小节描述的是 `1f8ae476` 当时的做法。`T8-15.5R` 已经把它删掉：两次观测挡不住
> "残留的合法旧值连续出现两次"。现在倒退只静默重设基线，永不触发。保留原文只为对照。

- 半截内容会立刻被完整内容覆盖（值变大）→ 确认后按**完整序号**开麦一次（真请求没丢）；
- 换计时基准时对端会一直用新基准写，值稳定或继续增大 → 确认；
- 只是脏数据（空/负号/垃圾字符）根本不进候选；
- 3 s 节流保证一串异常值不会连着触发多次。

守卫侧的日志现在能区分四种情况：`accepted (new)` / `accepted (first)` /
`accepted (clock-base reset)` / `request file invalid/empty/busy - ignored (invalid=N)`。

## 3. 请求生命周期逐项检查（审查第二节）

| 检查项 | 结论 | 证据 |
|---|---|---|
| 连续两个原厂指令会不会丢前一个请求 / 重复开麦 | 不会。各自一次请求、各自一次确认；未开麦就被顶替的记 `superseded` | 真机 s5：`1971107`(+216 ms)、`1971122`(+260 ms) |
| 待处理期间用户停止/退出能否立即终止 | 能。worker 清 `native_relisten_due_ms`/`native_rel_waiting`，守卫另有 hold 终态丢弃 | 真机 s6；守卫日志 `dropped (stop/exit hold)` |
| 已触发但 worker 未确认时会不会重复发 | 不会。worker 每次指令只发一次，无自动重发；5 s 内没确认只记 `NOT confirmed` | `aiw_request_continuity` 仅由路由分支调用一次 |
| Worker 重启后旧请求文件会不会误开麦 | 不会。worker 重启不写文件；守卫基线在内存里不动 | 真机 07:25:14 重启 worker，守卫基线仍 121721933，之后无自发开麦 |
| 守卫重启后旧序号会不会被误消费 | 不会。启动时读到合法序号只当基线（`baseline seq=...`），读到空/非法则不建基线 | 真机 07:25:32 `request baseline seq=121721933`（当场无开麦）；host F1/F2 |

另外这一轮真机还暴露了一个**与本缺陷无关**的现象（见第 7 节已知问题）：`:core` 重启后应用自己的
启动语可能被回声识别，worker 会当成指令执行一次。

## 5. 真机验证（TG-Z02，ARM32，`192.168.1.9:5555`，root）

部署：守卫换 `.so` 必须换进程（活进程里二次注入会 `prepare=-5 playTts prologue mismatch`），
所以 `:core` kill 一次由系统拉起（pid 30807 → 21638），supervisor 注入 `libtg_ttsguard_t8155.so`；
worker 换二进制后 `run_ai_worker.sh stop/start`（uid=0，pid 21569）。
`renew_ms=0`、`continuity_auto=1`、`continuity_type=1` 配置不变。

回放方式：PC 扬声器 → 设备麦克风，**事件驱动**（等原厂真的开出 `wakeupType=1` 的会话再说话，
不靠固定 sleep，避免压在自己 TTS 尾巴上或等过静默超时）。

### 5.3 时钟基准的一个真机发现（顺带确认修法没有掩盖问题）

设备休眠 8.25 h 后 `CLOCK_MONOTONIC` 走了 8.25 h（该内核 MONOTONIC == BOOTTIME），
worker 的序号从 `121721933` 直接跳到 `151660001`。守卫按 `new` 正常受理——这正说明
"跨基准"分支不是常态路径，正常重启/休眠只会让序号**变大**，不会误判。
