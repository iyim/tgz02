# T8-12.19 退出指令行为审查与收尾回调定向定位

- 基线：`8242571c2d61bd0afa4c9fd2019c8acf5331a32d`
- 本轮性质：**静态审查 + 真机数据复盘**，不修改生产代码、不操作设备（除非另行授权）
- 分析对象：`libsmartbox.so`（sha256 `f6e3c354…df80940`，与设备 `/proc/30807/maps` 装载的是同一文件）、
  `intent_route.c`、`nlu_takeover.c`、`libtg_hook.c`
- 工具：NDK `arm-linux-androideabi-objdump`（287 438 条指令全量反汇编 + 自写 BL/立即数扫描）
- 证据目录：`my-doc/07_ai_bridge/evidence/t8-12-p19/`

## 0. 结论先说

1. **「退出」被 DROP 是分类规则覆盖缺口，不是设计意图**：本地意图路由表里**根本没有退出类意图**，
   `ir_classify("天猫精灵退出")` → `IR_NONE` → 被当成 AI 会话登记 → `should_drop` → DROP。
   DECIDE 模式下用户说「退出」设备无反应 —— 确认为**用户可感知的行为缺陷**，本轮给出最小修复方案（§4），未实施。
2. **type=2/3 的调用点已静态定位**（§3）：
   - type=2：`SessionManager::exitTalk` 合成 `NlpResult` 后调 `onNlpResult(sid, 2, 合成对象)` —— **res 非空**；
   - type=3：`SessionProxy::onHandler` 内 `setSessionStatus(sid,6)` → `onNlpResult(sid, 3, NULL)` → `removeMessage` → **`onNlpResultEnd(sid, NULL, 3)`**。
3. **两个 type 都经过我们 hook 的 `onNlpResult`**（BL 扫描证明无其它直调路径，onNlpResult 是被 Handler 间接调用的唯一分发点）——
   被动观测的拦截点选对了，不存在"第二条漏网路径"。
4. **最重要发现（R13 修复的正确性由反汇编直接证实）**：type=3 之后紧跟
   `SessionManager::onNlpResultEnd(sid, NULL, 3)` —— 这是原厂会话**收尾清理**。
   在 R13 之前，DECIDE+已登记会话会让 `tg_nlp_cb` 返回 1 → **跳过原厂 `onNlpResult` 函数体** →
   **`onNlpResultEnd` 永远不执行** → 原厂会话清理流程泄漏。R13 的无条件放行让这条链恢复完整。
5. type=3 稀发性的解释：它由 Handler 消息驱动（`Message::obtain` 在 0x11c81c 处同样构造 type=3 消息），
   在会话清理/超时路径触发，不是每轮命令稳定出现 —— 与 T8-12.16 的单次命中、以及本轮 9 轮未命中一致。

## 一、为什么「退出」被 DROP（代码路径逐步追踪）

真机事实（T8-12.18）：

| 指令 | 模式 | 回调 | 判定 |
|---|---|---|---|
| 「天猫精灵，现在几点了」 | DECIDE | type=0 | **PASS**（本地 time 指令） |
| 「天猫精灵，退出」 | DECIDE | type=0 | **DROP** |
| 「天猫精灵，退出」 | PASS | type=0 | PASS |

路径：`tg_onstream_cb` → `nlu_note_final(sid, text)` → `t8_to_on_final(&g_to, key, text, now, g_nlu_mask, &why)`。

### 1.1 为什么被分类为 AI

`nlu_takeover.c`（T8-12.5 起）：

```c
hit = ir_classify(text, &ir);
enabled = (hit && (route_mask & ir_route_bit(ir.intent))) ? 1 : 0;
...
if (hit && enabled && ir.complete) { ...passed++...; return T8_TO_PASS; }
why = !hit ? T8_TO_WHY_AI : (!enabled ? T8_TO_WHY_AI_INTENT_OFF : T8_TO_WHY_AI_INCOMPLETE);
...注册会话... return T8_TO_TAKE;
```

`ir_classify("天猫精灵退出")`（`intent_route.c`，归一化后剩余"退出"）：

- 意图枚举只有 `volume / weather / screen_off / time / screen_on / media / stop` —— **没有 exit**；
- 全库唯一含「退出」的关键词是 `IR_VOL_UNMUTE` 里的「退出静音」（音量否决/恢复语境）；
- `ir_match_stop` 关键词是「停止/停下/停一下/先停/暂停/别说了/别说/不要说了」—— 不含「退出」。

⇒ `hit=0` → `why=T8_TO_WHY_AI` → **登记** → `onNlpResult(type=0)` → `t8_to_should_drop` → `1` → `tg_nlp_cb` 返回 1。

### 1.2 DROP 之后原厂行为

`tg_nlp_cb` 返回 1 → stub 走 `mov r0,#0; bx lr` → **`SessionDispatch::onNlpResult` 原函数体不执行** →
原厂对该结果的全部后续（技能执行 / 会话收尾）都不发生。「退出」在 DECIDE 模式下设备无反应 —— 与真机观测一致。

### 1.3 是设计还是遗漏

判定为**遗漏**，依据：

- `intent_route.h` 的设计注释明确列出七类基础语音能力，没有任何一条提到退出/结束对话；
- 退出在原厂是真实存在的能力（反汇编证实 `SessionManager::exitTalk`、`SessionProxy::onExitTalk` 等符号齐全）；
- 「退出静音」反而进了音量否决表 —— 说明作者审过「退出」字样，但只从音量语义角度处理了。

## 二、type=2 / type=3 定向定位（反汇编证据）

### 2.1 调用方式：全部间接，hook 是唯一拦截点

287 438 条指令的 BL/B 直调扫描：`SessionDispatch::onNlpResult`（0x118ebc）**没有任何直接调用者**
（唯一命中是 `onNlpResultInner` 尾调 `onRouterDetailInfo`）。它是 Handler 体系经函数指针/虚表调用的，
我们的入口补丁是这个分发点的唯一 interception —— **type=2/3 一定会经过 hook**，不存在第二漏网路径。

### 2.2 type=2：`SessionManager::exitTalk` @0x1110e4

```asm
0x011110c  bl   operator new(0x98)              ; new 一个 152 字节 NlpResult
0x0111114  bl   NlpResult::NlpResult()
0x0111118  mov  r0, #1
0x011111c  mov  r1, #2                        ; 合成结果字段 = {1, 2}
0x0111120  stmib r7, {r0, r1}
0x0111124  mov  r1, r6                        ; r1 = sid（exitTalk(int sid, …) 的参数）
0x0111128  mov  r2, #2                        ; r2 = type = 2
0x011112c  ldr  r0, [r5, #16]                 ; this->dispatch
0x0111130  mov  r3, r7                        ; r3 = 合成 NlpResult
0x0111134  bl   SessionDispatch::onNlpResult  ; → hook: type=2, res 非空
0x0111138  ldr  r0, [r7]  … blx r1            ; 虚调合成结果的析构
0x01111a0  bl   IMmiCore::getInstance() …      ; 继续原厂退出链路
```

**修正一处此前的假设**：type=2 的"合成结果"**不是 NULL**，而是一个真实的合成 `NlpResult`（res 非空）。
我们的 `resnull` 字段在真机上如果抓到 type=2，预期值应为 `resnull=0`。

### 2.3 type=3：`SessionProxy::onHandler` @0x11c238 内 0x11cbf0

```asm
0x011cbd4  bl   Handler::removeMessage(sid)
0x011cbe0  bl   SessionManager::setSessionStatus(sid, 6)   ; ← 会话状态先置 6（结束）
0x011cbf0  onNlpResult(sid, 3, NULL)                          ; r2=3, r3=0
0x011cc04  bl   Handler::removeMessage(sid)
0x011cc20  b    SessionManager::onNlpResultEnd(sid, NULL, 3)   ; ← 收尾继续
```

- **type=3 的 `res` 确实为 NULL**（`mov r3,#0`），与审查判断一致；
- 它是 Handler 消息驱动的清理路径（0x11c81c 处同函数还用 `Message::obtain(...,3,0,...)` 构造 type=3 消息再投递），
  所以触发时机随会话状态机而定 —— 解释了稀发性与 T8-12.16 的 -6.5 s 反序样本；
- **R13 的价值由这段汇编直接证实**：`onNlpResult(type=3)` 之后紧跟 `onNlpResultEnd(sid,NULL,3)`。
  R13 之前若 DECIDE+已登记 → 返回 1 → 原函数体被跳过 → **`onNlpResultEnd` 不会执行** → 会话收尾链断裂；
  FAILCLOSED 同理。R13 放行后这条链完整。

## 三、「退出」DROP 的定性

**确认为用户可感知的行为缺陷**（仅 takeover 开启时）：DECIDE 模式下用户说「退出」，原厂结果被丢弃，设备不结束交互。
takeover 关闭（当前常态）时无此问题。

## 四、最小修复方案（待批准，未实施）

改动集中在 `intent_route.c/.h`，一处配置（`libtg_hook.c` 的默认 mask）：

1. `intent_route.h`：新增 `IR_EXIT`，新增路由位 `#define T7B_ROUTE_EXIT 0x80`（`T7B_ROUTE_ALL` 相应 0xFF？——
   见第 4 点的取舍）；
2. `intent_route.c`：新增 `ir_match_exit()`（关键词「退出」「退出一下」「结束对话」；**否决词**「静音」「登录」——
   且匹配器放在 volume **之后**，避免抢走「退出静音」）；挂在 `ir_classify_norm` 链尾；
   `ir_route_bit`/`ir_intent_name` 补 case；
3. `libtg_hook.c`：`g_nlu_mask` 默认 `0x7F` → `0x7F|T7B_ROUTE_EXIT`，让 DECIDE 登记时退出被归类为
   `hit && enabled && complete` → `T8_TO_PASS` → 不登记、不 DROP。

效果：仅退出类命令从"登记+DROP"变为"本地直通"；其它 AI 命令（讲笑话等）的接管行为不变。
风险：「退出」作为短词的误命中（如"退出登录"）—— 用否决词 + 放置顺序控制；主机 route 单测需同步补用例。

**未实施**：按任务书要求，先交判断与方案；确认后按上述最小补丁实施并补主机单测与真机验证。

## 五、type=2/3 定向真机验证方案（待批准后执行）

现在调用点已明确，被动观测可以做成**定向**的：

1. **type=2**：由 §2.2 可知它随 `exitTalk` 触发。原厂退出链路的可靠入口是 `IMmiCore`/会话超时；
   实操方案：启用 takeover（DECIDE）会造成"退出"被 DROP 的缺陷状态（§三），
   因此正确做法是**先合入 §四的最小修复**，再在 DECIDE 下说「退出」——此时退出不再被 DROP，
   原厂退出链路（含 `exitTalk`→type=2）应自然触发，探针预期记录 `type=2 / resnull=0 / decision=PASS / term_pass+1`。
   —— 也就是说：**R13 的真机命中验证依赖 §四的修复先行**，两件事是串行的。
2. **type=3**：由 Handler 清理路径触发（`setSessionStatus(sid,6)`），时机与会话状态机相关；
   已知的一次命中发生在会话清理时。方案：长会话 + 超时等待 + 10 s 间隔轮询 `tg_nlu_observe`
   （现有分块导出已支持），出现即核对 `resnull=1`。

两步都以现有 p18 探针完成，无需新框架、无需改原厂行为。
