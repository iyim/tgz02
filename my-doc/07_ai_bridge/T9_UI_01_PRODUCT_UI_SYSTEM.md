## 3. 这套设计建立在四个实测事实上

设计不是凭空画的，以下事实全部来自本项目的源码与设备（而不是"一般 Android 应用"的假设）：

1. **画布是 1024×600、density 160、无系统状态栏**（`wm size` / `wm density` / 截图内容从 y=0 开始）。
   所以设计稿与屏幕 1dp:1px 对齐，不考虑刘海、状态栏、竖屏。
2. **应用没有 `res/`**（`build.ps1` 只用 aapt2 处理 manifest）。
   所以没有矢量图、没有 ripple、没有 state-list、没有自定义字体——图标必须用 Canvas 画，
   圆角必须用 `GradientDrawable`，按下态只能用背景色变化。
3. **设备只有 Regular/Bold 两档字重**（`DroidSans` + `NotoSansCJK`）。
   所以层级靠字号、颜色、间距，不设计 500/600 字重的细腻层级。
4. **产品 Activity 不读 Intent**（T9-07R1 的既定结论）。
   所以技能页共用一个宿主 Activity，用进程内静态交接 id，不为每个技能加 Activity + Intent extra。

## 4. 六个关键设计决策

| 决策 | 理由 | 代价 |
| --- | --- | --- |
| 一级导航固定五项，不再增加 | 新增功能只进技能中心，导航一次定死 | 技能再多，导航栏也不会变长 |
| 技能页**不是** Activity，是宿主里的一个 View | 不改 manifest、不叠 Activity 栈、不做 Intent 解析 | 技能页无法被外部直接拉起（本项目不需要） |
| 首页九状态，且 UI 只读不写 | 状态来自 `status.public.json`，停止是唯一的写操作（携带 `tts_id`） | 新增状态需同时改 worker 状态词表与 UI 文案 |
| 浅色主题 = 同一套 token 换值 | 布局与组件零改动，降低双主题维护成本 | 状态色与软底需要两套"软底上的文字色"（已定义 `--t-*`） |
| 图标用几何原语在 Canvas 上画 | 没有 res/ 时这是唯一可维护方案；26 个图标约 180 行 | 图标风格偏几何，不能直接吃设计师的 SVG |
| 不引入栅格系统、不用 ConstraintLayout | 只有一个物理尺寸，栅格系统的成本换不来收益 | 将来换屏需要按 §6 的退化规则调整 |

## 7. 诚实说明（未做到与限制）

1. **原型是 HTML/CSS 渲染的，不是设备截图。** 它按设备的真实画布（1024×600、scale 1）渲染，
   尺寸/字号/间距与文档逐值一致，但字体是 Windows 的 YaHei，设备上是 Noto Sans CJK——
   字宽行高一致、字形略有差异。本阶段按要求不写业务代码，所以还没有"新界面跑在设备上"的截图。
2. **三张技能页是设计原型，不是已实现功能。** 闹钟/日程/音乐的功能页要到 T10 之后按契约逐个接入；
   现在写它们会违反"本阶段以设计为主"的要求。
3. **浅色主题只交付了 token 与一张首页示意**，其余页面没有各出一张浅色图。
   如果需要逐页浅色稿，可以在 T9-UI-02 落地后由同一套 `shoot.ps1` 一次性批量产出。
4. **`index.html` 总览需要 Chrome**（本地打开即可，无网络依赖）；原型也可用
   `ui/prototype/shoot.ps1` 一键重出全部截图。
5. 音乐技能的"待接入"是目前产品真实状态（无曲库授权）；设计上把它画成"页面在、能力没有"，
   而不是画一张假的可用播放器。

## 9. 三个需要审计确认的设计决定

1. **文字对话页的去向**：设计里把它降级为「设置 → 系统 → 对话记录」（只读列表 + 清空），
   首页彻底没有文字入口，调试输入继续用 adb 脚本（`t9_08b_r2_dev_say.sh`）。
   如果希望保留一个可写的文字入口（例如排查模型问题时），需要指定它挂在哪里。
2. **首页快捷入口的数量**：固定 4 个（最近使用的 3 个技能 + 「全部技能」）。
   如果你希望首页更干净（例如只留 3 个、或只留「全部技能」一个），我按你的口径改。
3. **浅色主题是否作为正式能力**：当前设计是"深色默认 + 浅色可切换"。若产品只面向这块音箱屏，
   也可以只做深色、把浅色保留为 token（不做开关），减少一倍的界面验收工作量。
