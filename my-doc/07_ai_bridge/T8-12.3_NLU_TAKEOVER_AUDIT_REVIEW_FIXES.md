## 〇、本阶段最重要的结论（先给结果）

1. **第二阶段的"C1 修正"本身是错的。** 第二阶段删掉了第一阶段"`what=11` → `onNlpResultInner`"的判断，理由是"`what=11` 落到默认分支 `0x11c5c0`"。真实原因是我们当时只找到了**第一张**跳表：`0x11c37c` 不是默认分支，而是**第二张跳表的分发头**。
2. 修正后的事实：`what=11` → `0x11c410` → **`SessionDispatch::onNlpResultInner(sid,res)`**（第一阶段的判断是对的），并且该函数**直接调用 `playAudios`**，掩码 `0x20000`，**完全绕过被打补丁的 `SessionDispatch::onNlpResult`**。
3. 但"普通 AI 结果是否走 what=11"这一关键问题，本阶段**已经用静态证据回答了一半**：`what=11` 的唯一发起者是 `SessionProxy::onNlpResultInner(int,res)`，而它唯一的调用者是 `SessionManager::onNlpResult` 中**"sid 不匹配 + `res->isTtsStreaming()`"** 的分支。也就是说：**同 sid 的常规结果不会走 what=11**。这使"补丁覆盖主路径"从"猜测"升级为"有静态证据"，但**跨 sid 的 TTS 流式结果会走一条执行技能却不受补丁约束的路径**（新风险 R16）。
4. `exitTalk` 的 `type=2` 合成结果**不会执行原厂媒体指令**，原因不是"`res==NULL`"，而是 `NlpResult` 构造函数把 `[+144]` 初始化为 **`-1`**，`playAudios` 用 `[+144] == 0` 作为"要不要处理媒体指令"的门。第二阶段的机制解释需要改写（结论方向不变）。
5. `playAudios` 的 NULL 分支**不是 no-op**：它跳过媒体指令与命令 JSON 处理，但仍然对 MMI 单例做**一次接口虚调用**（`vtable+32`，`r1 = res->[128]` 或 `0`）。"没执行技能" ≠ "没做任何后续处理"。
6. `SessionProxy::onHandler`（`0x11c238`）**当前没有任何补丁**，且它是全部 16 种 `Message` 的唯一漏斗。这解决了探针方案里"P2 与现有补丁入口冲突"的问题：**不要去二次补 `onNlpResult`，改在 `onHandler` 上装只读探针**。

### 2.1.2 `0x11c37c` 是第二张跳表的分发头

## 三、2.2 四个 `NlpResult` 入口的真实技能执行路径

### 3.1 方法与自证

PLT 符号解析不再用"stub 序号 ↔ `.rel.plt` 序号"的假设，而是**从 stub 自身字节反解 GOT 槽位**，再用该槽位去 `.rel.plt` 查名字：

- 脚本：`analysis/t8_12/plt_map.ps1`（本阶段新增）
- 自证结果：解码出 **3546** 个 stub / `.rel.plt` 也是 **3546** 项，一一对应，无孤儿、无重复
- 关键映射（节选）：`0x93368 → SessionManager::isSessionValid`、`0x93188 → SessionDispatch::playAudios`、`0x933a4 → SessionDispatch::onNlpResultInner`、`0x933b0 → SessionDispatch::onPushNlpResult`、`0x933bc → SessionDispatch::onSpecialNlpResult`、`0x93194 → SessionDispatch::onRouterDetailInfo`、`0x92c54 → SessionDispatch::onNlpResult`、`0x8eb5c → Message::obtain`

1148bc  cmp  r0, r1  (sid)

>
> 第四阶段在同一个库内找到了**第二个、且无门控的** `what=11` 触发源：
>

> [T8-12.4_NLU_TAKEOVER_SOURCE_AND_PROBE_ABI_REVIEW.md](T8-12.4_NLU_TAKEOVER_SOURCE_AND_PROBE_ABI_REVIEW.md) §2.3–2.7。

### 3.3 是否进入 `playAudios` / `AudioManager::processMediaCommand`

| 入口 | `playAudios` 调用点 | 掩码 `r1` | `processMediaCommand` 唯一调用点 |

`playAudios` 全库调用点 **3 个**，全部落在上面三个函数体内；`processMediaCommand` 全库调用点 **1 个**，就在 `playAudios`；`AudioManager::preProcessCommand` 全库调用点 **1 个**，也在 `playAudios`。

### 3.4 纠正 R1 的"三个兄弟入口"表述

R1 的措辞把三件事混成了一件。必须分三层说：

| 层次 | 内容 |
|---|---|
| **L1 存在 NLP 结果入口**（4 个） | `onNlpResult`、`onNlpResultInner`、`onPushNlpResult`、`onSpecialNlpResult` |
| **L2 存在原厂技能执行路径**（3 个，且都已定位到具体调用点） | `onNlpResult`（`0x119200`）、`onNlpResultInner`（`0x11899c`）、`onPushNlpResult`（`0x118a2c`）——三者都进 `playAudios` → （条件满足时）`processMediaCommand` + `preProcessCommand`。`onSpecialNlpResult` **不在**此列 |
| **L3 当前 Hook 实际覆盖**（1 个） | 只有 `onNlpResult`（入口 `0x118ebc`，`nlu_patch` 事务） |

"发现入口" ≠ "发现技能执行路径" ≠ "已覆盖"。R1 的"三个兄弟入口确实会执行技能"在**函数名单**上是对的，但必须写明是哪三个、以及第四个不执行。

### 3.5 是否还存在其他执行原厂技能的路径

按"`playAudios`/`processMediaCommand`/`preProcessCommand` 全库调用点完备"这条硬约束，未发现其他路径。但不等于"云侧结果只有这三条路"：`SessionDispatch::onNlpResult` 体内还有 `onRouterDetailInfo(0x10000,…)`（`0x1191d8`）、`bl 0x11802c`（`0x119070`，JSON 解析/上报）、`UtManager`/`AutoTestManager` 旁路，以及 `getForegroundInfo`（`0x118f94`）。这些是"结果投递"而非"技能执行"，但对 CDM 状态同样可能有效应（见 §四、§六）。

### 5.2 `0x117f48` 的虚函数是什么

- 对象来源：`playAudios` 入口 `0x117d58 bl IMmiCore::getInstance()` → `0x117d5c ldr r1,[r0]` → `0x117d60 ldr r1,[r1,#60]` → `0x117d64 blx r1`（`IMmiCore` vtable 槽 +60，slot 15）→ 返回值 `r0`，`0x117d70 subne r5, r5, #16`（次对象 thunk 偏移 16）→ `r5` 就是最终对象。
- 调用：`r3 = [ [r5] + 32 ]`，即该对象 vtable 的 **slot 8**；实参 `r0 = r5`（this）、`r1`、`r2 = 0`。
- **接口类型静态不可判定**：`IMmiCore` 的 vtable 内容在运行时由实现类填充，`.rel.dyn` 里没有可直接落到具体符号的证据。这属于未证实项（U9）。

### 5.3 NULL 与非 NULL 的差异（"没有执行技能" ≠ "没有做任何后续处理"）

| 步骤 | 非 NULL | NULL |
|---|---|---|
| `[vtable+56]` 前置调用 | `res->[144]==0` 时执行 | 不执行 |
| `AudioManager::processMediaCommand` | 条件执行 | **不执行** |
| `*h` 回写 | 执行 | 不执行（调用方 `onNlpResult` 已预置 `h=0`） |
| 日志（行 242） | 执行 | 不执行 |
| `0x11802c`（JSON 解析/上报） | `res->[56]` 非空时 | 不执行 |
| `AudioManager::preProcessCommand` | 同上 | **不执行** |
| 链表遍历（`res->[120]`） | 条件执行 | 不执行 |
| **末尾 MMI 接口虚调用（`vtable+32`）** | **执行**（`r1 = res->[128]`） | **执行**（`r1 = 0`） |

结论：NULL 分支**确实跳过了整段技能/指令执行**，但不是空操作——它对 MMI 单例做了一次"空载荷"的接口调用，随后才返回。

### 5.4 什么时候真的会出现 NULL

| 调用者 | 能否以 `res == NULL` 进入 `playAudios` |
|---|---|
| `SessionDispatch::onNlpResult`（`0x119200`） | **不能**。`arg2 != 0` 时它先在 `0x118f44` 造对象；`arg2 == 0 && res == NULL` 时它在 `0x118f40` 就跳到收尾（`0x119570`），根本不到 `0x119200` |
| `SessionDispatch::onNlpResultInner`（`0x11899c`） | **能**（`res` 原样透传） |
| `SessionDispatch::onPushNlpResult`（`0x118a2c`） | **能** |

所以第二阶段 §3.4 说"`(sid,3,NULL)` 收尾因 `res==NULL` 跳过技能执行段"——**机制是错的**（那条路径会合成对象），但**结论（不执行媒体指令）仍然成立**，只是原因换成 `[+144] = -1`。

## 六、2.5 会话生命周期风险（R13 / R14 / R15）与最小修改方案

### 6.1 R13（P0）：`tg_nlp_cb` 丢弃 `type` 与 `res`

【源码】`hook_agent/libtg_hook.c:816-842`：

```c
static int tg_nlp_cb(void *self, int sid, int type, void *res)
{
    (void)self; (void)type; (void)res;      /* ★ 两者都不参与判定 */
    mode = nlu_mode_now();
    if (mode == NLS_PASS) return 0;
    ...
    drop = t8_to_should_drop(&g_to, key, wall_ms());   /* 只看 sid */
    return drop ? 1 : 0;
}
```

【源码】`nlu_takeover.c:248-286` `t8_to_should_drop()` 同样**只按 session 字符串**判定；命中即 `return 1`。

【反汇编】stub（`libtg_hook.c:844-860` 注释 + `0x930000` 页构造）在回调返回 1 时执行 `mov r0,#0; bx lr`，即**整个原函数不执行**。

因此接管开启且槽位命中时，同一 sid 下**三种调用全部被丢弃**：

| 调用 | 后果（静态可证） |
|---|---|
| 正常结果（what=7） | 丢弃 → 这是接管的本意 |
| `exitTalk` 的 `type=2`（what=14 → `0x111134`） | 丢弃 → `onRouterDetailInfo` / `playAudios` / 末尾 MMI 虚调用全部消失；`exitTalk` 自身后续清理仍执行 |
| 收尾 `type=3`（`0x11cbf8`） | 丢弃 → `setSessionStatus(6)` 已执行、`onNlpResultEnd` 仍执行，唯独中间的结果投递消失 |

### 6.2 R14（P1）：槽位只靠 TTL

【源码】`libtg_hook.c` 中 `t8_to_*` 的调用点只有 `init / enabled_set / on_final / should_drop / snapshot_take / enabled`；**`t8_to_on_session_end()` 与 `t8_to_purge()` 没有任何调用点**（`grep t8_to_` 全量核对）。

量化（【源码】+【反汇编】语义）：

- `T8_TO_SLOTS = 64`、`T8_TO_SESSION_MAX = 40`（单 session 字符串上限）、`T8_TO_TTL_MS = 30000`
- 过期判定：`t8_to_should_drop()` 在 `:263` 对**被查询的那个 slot** 做 `deadline_ms <= now_ms` 检查并 `t8_clear()`；`t8_to_on_final()` 在入口做 `t8_purge_locked()` 全表清理
- 因此：**过期槽位不会造成"误拦"**（读时即清），R14 的真实影响是**容量与可观测性**：
  - `t8_alloc_free_only_locked()` 找不到空槽时 → `overflow++` + **开启 5 s 全局 `degraded_until_ms` 窗口** → 该窗口内**所有未登记 sid 也被丢弃**（`:276-279`）
  - 同理 `failclosed_until_ms`（`:272-275`）
- 这两条 5 s 窗口是 `t8_to_should_drop()` 里唯二的"未登记也丢"来源，也是 R14 与 R13 叠加后风险最高的组合

### 6.3 R15（P1）：`type=2` 的唯一真实触发点

- `SessionManager::exitTalk(sid, flag)` 的两个调用点：
  - `SessionDispatch::onStream` `0x117c0c` → `mov r2,#0` → **flag=0，合成段完全跳过**（`0x111100 beq 0x111148`）
  - `SessionProxy::onHandler` `0x11c4dc`（`what=14` 分支）→ **flag=1，合成段执行**
- 所以"`exitTalk` 会合成 `type=2`"只在 `what=14`（`SessionProxy::onExitTalk`）这条路上成立；文本流路径（`onStream`）不会。
- `what=14` 的发起者是 `SessionProxy::onExitTalk(int)` @`0x11d98c`，其上游是 `SessionManager::onExitTalk`（`0x1145c8`，176 B）。谁调用 `SessionManager::onExitTalk` 属**未证实**（`0x1145c8` 无库内 PLT 调用者）——必须靠运行期观测（§八）。

### 6.4 最小修改方案（设计稿，**本阶段不落地**）

目标（按评审要求逐条对应）：

| 要求 | 方案 |
|---|---|
| 不丢弃正常会话收尾 | `should_drop` 前先做 `type` 分类：`type == 3`（NULL 收尾）→ **永不丢弃** |
| 不让 `type=2` 破坏 CDM | `type == 2` → **默认不丢弃**（保守），并在 `T8-13` 用观测数据决定是否改判（见 §九 D2） |
| 已结束会话不长期占槽 | 在 `what=1` 的异常收尾分支与 `type=3` 处调用 `t8_to_on_session_end()`（两处各一行）；不新增线程、不新增锁 |
| 不因 sid 缺失误拦 | `t8_to_should_drop()` 在 `session == NULL/空` 时直接 `return 0`（把 `:258-262` 的"未登记分支"改成显式放行），并把 `failclosed_until_ms` / `degraded_until_ms` 从 `should_drop` 里**移除**（降级窗口只用于计数，不用于放行决策） |
| TTL / 重复登记 / 容量 | TTL 30 s 保持不变；重复登记已由 `reentrant_marks`（只刷 TTL）覆盖；容量耗尽时**只计数不放行**（同上） |

改动面估计：`nlu_takeover.c` 约 15 行、`libtg_hook.c` 约 6 行、`nlu_takeover.h` 无接口变化。**本阶段不实施**，仅作为 T8-13 的候选方案。

### 6.5 不采纳的方案

- **"`res != NULL` 就拦"**：`exitTalk` 的 `type=2` 同样非 NULL（§4.6），会误伤。
- **"sid 相等就拦"**：`what=11` 恰恰是 sid 不等的情况；而 `type=3` 收尾 sid 相等 → 会误伤。
- **"把 5 s 窗口调大"**：会放大 R13 的影响面，方向相反。

## 七、2.6 探针工程方案修订

### 7.1 A. P2 与现有 `tg_nlp_cb` 补丁入口的冲突——**不支持二次安装，改用 `onHandler`**

【源码】`nlu_patch.c:157-196` `np_install()` 的第一步就是入口校验：

```c
rc = NP_E_ENTRY;
np_seterr(p, "install refused: entry is %s (%08x %08x), expected prologue %08x %08x", ...);
```

即：入口已是跳转指令时，**确定性拒绝**（`NP_E_ENTRY`），不会叠加、不会写坏。

【源码】`libtg_hook.c:1977-1980` T6 侧同样是幂等的（`g_patched && g_thread_started && !g_prot_dirty` → 直接返回 `TG_OK`），`verify_entry_state()` 会在入口不匹配时拒绝。

**结论**：同一入口**不支持**装第二个 Hook；如果强行用另一套框架覆盖，`trampoline` 会把已打成跳转的 8 字节当成"原序言"抄走，造成 `ldr pc,[pc,#-4]` 自环 → **必然死循环**。

**替代观测点（不改变原有行为）**：

> **P2' = `SessionProxy::onHandler`（`0x11c238`）入口只读探针**

理由：

1. 该入口**当前没有任何补丁**（`nlu_patch` 只覆盖 `0x118ebc`），无冲突；
2. 它是**全部 16 种 Message 的唯一漏斗**，一次安装即可拿到 `what / sid / arg2 / res` 四元组，覆盖 what=7/11/12/13/14/3 全部关键路径；
3. 它位于 `onNlpResult` **之前**，因此"补丁到底有没有被命中"可以用"`onHandler` 看到了 what=7，`onNlpResult` 探针（若有）是否也被命中"做**双点对账**；
4. 现有 `tg_nlp_cb` 在 takeover 关闭时是**完全静默**的（`NLS_PASS` 分支直接 `return 0`，计数器不加、无日志）——所以"用现有 Hook 的计数来当 P2"**不可行**，这条必须在方案里写明，否则 T8-13 会白跑。

### 7.2 B. P3 增加调用来源（返回地址）

**做法**：探针拥有**自己的** stub 页，因此在 stub 内捕获 `lr` 不产生任何额外风险：

```
; 探针 stub（每个被观测函数一份，由 probe .so 自建）
push {r0, r1, r2, r3, r12, lr}      ; 保存入参与返回地址
mov  r12, lr                        ; ★ 调用者返回地址
ldr  lr, [pc, #...]                 ; 装载回调地址后 blx（保持 8 字节对齐）
blx  lr
pop  {r0, r1, r2, r3, r12, lr}      ; 原样恢复（含 lr）
ldr  pc, [pc, #...]                 ; → trampoline（原序言 + 跳回 func+8）
```

回调原型固定为：

```c
void probe_cb(uint32_t site_id, uint32_t a0, uint32_t a1, uint32_t a2,
              uint32_t a3, uint32_t caller_lr);
```

- `site_id` 由 stub 里的常量给出（每个被观测入口一个），由此区分"哪个入口"；
- `a0..a3` 是原样透传的 r0..r3（`onHandler` 时 = `this, msg, -, -`；`onNlpResultInner` 时 = `this, sid, res, -`）；
- `caller_lr` = 被观测函数**被调用时**的 `lr`，即**调用点地址 + 4**（ARM `bl` 的返回地址）。

**寄存器与栈不被破坏的保证**：

1. stub 用 `push/pop` 成对保存 `r0-r3, r12, lr`，回调返回后原样恢复；
2. 回调**禁止**修改入参寄存器（C 调用约定下 r0-r3/r12 是易失的，但我们在 pop 之后才恢复，所以即使回调改了也不影响）；
3. `sp` 只被 `push/pop` 成对移动，且 `push` 的 6 个寄存器保持 8 字节对齐；
4. **不使用 `mov pc, lr` 返回**，避免 ARM/Thumb 位丢失（stub 全程 ARM，`func+8` 处的原指令是 ARM，跳回用 `ldr pc,[pc,#…]`）；
5. 探针只读：回调只写**自己的环形缓冲**，不调用任何原厂函数、不拿任何原厂锁、不 `malloc`（缓冲在 `dlopen` 时一次性 `mmap`）。

**已知限制（必须写进方案）**：`caller_lr` 只能证明"调用点地址"，不能证明"谁投的 Message"。要回答"谁调 `onHandler`"，需要再看 `Message[+36]`（handler 指针）与 `Message[+16]`（`HandlerCallback*`，本机三个 Proxy 全传 NULL）。

### 7.3 C. P4（函数内部代码块观测）——**取消，改用替代方案**

原方案 P4 想在 `0x11c410 / 0x11c424 / 0x11c444` 这些"内部小块"上装补丁。风险实测如下：

| 风险 | 说明 |
|---|---|
| 指令覆盖 | 这些块只有 6–12 条指令，`0x11c410` 前一条就是跳表的 `add pc, r1, r0`；在块首写 8 字节跳转会把整块吃掉 |
| PC 相对寻址 | `0x11c444` 块内有 4 处 `ldr rN,[pc,#imm]` 取日志字符串；补丁一旦移动指令位置，PC 相对偏移全部失效 |
| 线程并发 | `onHandler` 在 Handler 线程执行，但 `session` 释放、`MmiCore` 回调可能在别的线程；块内补丁没有"世界静止"窗口可用 |
| 跳表数据 | `0x11c290/0x11c394` 是**嵌在代码段里的数据**，任何写入都可能被误当成指令执行 |

**替代方案（零内部补丁）**：

1. 第二张表的 7 个块**全部可以通过第一层入口观测到**——`onHandler` 拿到 `what` 就等价于知道走了哪个块（§2.1.6 的表是 1:1 的）；
2. 想知道"块里那次调用成功了吗"，只需在**被调函数**上再装一个入口探针：`onNlpResultInner`（`0x11896c`）、`onPushNlpResult`（`0x1189ec`）、`onRouterDetailInfo`（`0x118830`）、`playAudios`（`0x117d40`）。这些都是**未被补丁占用**的函数入口；
3. 于是三层证据链闭合：`onHandler(what)` → 分支选择；`onNlpResultInner/onPushNlpResult` 是否被调用 → 分支是否走到；`playAudios(mask, sid, res)` → 是否真的执行技能。
4. **仍然不需要**碰 `SessionDispatch::onNlpResult`（已被 `nlu_patch` 占用），因此不存在双 Hook 冲突。

### 7.4 D. 完整回滚方案（逐步，可验证）

> 前提：探针是独立 `libtg_probe.so`，不复用 `libtg_hook.so` 的补丁框架。**同一时刻只允许一个 Injector 进程**。

| 步 | 动作 | 验证 |
|---|---|---|
| 0 | 记录基线：`ls -l /proc/<pid>/maps`、`cat /proc/<pid>/maps > maps.before`、三份 `/proc/<pid>/smaps` 关键行 | `sha256sum maps.before` 存档 |
| 1 | 装探针（`tg_probe_inject --on`），读回三处入口 8 字节 | 期望 `ldr pc,[pc,#-4] + <stub 地址>`；不匹配 → **立刻** goto 9 |
| 2 | 采集（单场景、单轮） | 环形缓冲 `PROBE=` 行数 > 0 |
| 3 | 关探针（`tg_probe_inject --off`） | 三处入口 8 字节**逐字节等于**基线原序言（`0xE92D4FF0 0xE28DB01C` 等） |
| 4 | 释放 stub 页 | `/proc/<pid>/maps` 中不再有 `libtg_probe.so` 对应的匿名可执行段 |
| 5 | 核对 T6/T7/T8 映射 | `maps.after` 与 `maps.before` **diff 为空**（只允许出现探针自己的行，且必须已消失） |
| 6 | 核对 Injector | `ps -A \| grep -c tg_probe_inject` == 0；`ps -A \| grep -c tg_injector` == 0 |
| 7 | 核对 `:core` 存活 | `getprop init.svc.*`、`ps -A \| grep :core` 与基线一致；不重启 |
| 8 | 归档 | 探针输出 + `maps.before/after` + 入口字节快照 一起进证据目录 |
| 9 | **失败处理** | ①入口字节不匹配 → 用 `maps` 里的 `libsmartbox.so` 基址重算出 `func` 地址，重试一次 `--off`；②`--off` 仍失败 → **不重启 `:core`**、不改 rc、先 `kill -STOP` 探针线程并保存现场（`/proc/<pid>/task/*/stat`、`maps`），然后上报；③stub 页 `munmap` 失败 → 记录 `errno`，页面留作孤儿但**不再被任何入口引用**（入口已恢复），只做记录 |

**"不会引入两个 Injector 并发"的具体做法**：

- 探针 Injector 启动时 `open("/data/local/tmp/tg_inject.lock", O_CREAT|O_EXCL)`，已存在即退出（打印持有者 pid）；
- 运行 `--off` 与 `--on` 之间不释放锁；
- 采集中途如需重装，必须先 `--off` 成功（步 3 通过）再 `--on`。

### 7.5 E. 观测数据关联

统一行格式（单行、定长字段、无逗号）：

```
PROBE=<seq> t=<ms> site=<id> what=<n> sid=<n> arg2=<n> res=0x<hex|0> lr=0x<hex> drop=<0|1> note=<tag>
```

- `seq`：全局单调递增（`__atomic_fetch_add`），用于**同进程内排序**；
- `t`：`wall_ms()`（与 `nlu_note_final` 同一时钟源），用于**跨 site 关联**；
- 关联规则：`|t(A) - t(B)| <= 50 ms` **且** `sid` 相等 → 判为同一轮语音；
- `site` 取值：`10=onHandler`、`20=onNlpResultInner`、`21=onPushNlpResult`、`30=onRouterDetailInfo`、`40=playAudios`、`50=exitTalk`；
- `note`：`w7a`（what=7 带 res）、`w7n`（what=7 res=NULL）、`w11`、`w12`、`w13`、`w14`、`w3` 等，便于直接 grep。

P1/P2/P3 的对应关系：`site=10` 取代原 P2；`site=20/21` 取代原 P3；`site=40` 取代原 P4；`site=30` 用于 `onRouterDetailInfo` 对账。原 P1（`onStream`）保持不变（T6 已在该函数上有 patch，但 `tg_onstream_cb` 存在且**会记日志**，可直接复用，不新增补丁）。

### 8.2 U1 / U2 / U3 的有效样本判据（按"有效 ASR 命中"计，不按播放次数计）

**有效样本定义**：一轮语音中，`PROBE site=10 what=5`（文本流进入）**且** 出现任一 `what ∈ {7,11,12,13,14}` 的后续行 → 记 **1 个有效样本**。只有 `what=5` 没有后续行 → 记"投递失败"，不计数。

| 未知项 | 判据 | 有效样本数 | 最大尝试次数 | 异常停止条件 |
|---|---|---|---|---|
| **U1**：云侧 AI 结果是否真的走 `SessionDispatch::onNlpResult`（what=7） | 同一 sid 下出现 `what=7` **且** `site=20/21` 均未出现 → 主路径被覆盖 | ≥ 5 | 20 轮 | 出现 `what=7` 但 `res=0` 连续 3 次 → 停止（说明结果打包方式与静态分析不符） |
| **U2**：`what=11` 是否在真实语音中出现 | `what=11` 的 `site=20` 行数 > 0；且该 `what=11` 行的 `sid` 与当轮 `what=5` 的 `sid` **不同**（验证 §3.2 的"sid 不匹配"前提） | ≥ 3 | 30 轮（含 TTS 流式播报场景） | 出现 `what=11` 且 sid 相同 → 停止（静态结论被推翻，需重审 §3.2） |
| **U3**：`what=14`（`onExitTalk`）是否在真实语音中出现 | `what=14` 的 `note=w14` 行数 > 0，且其后 100 ms 内有 `site=50`（`exitTalk`）`arg2=1` | ≥ 3 | 20 轮（含"打断/退出"话术） | `site=50` 出现 `arg2=0`（来自 `onStream`）→ 记录但不计入 U3 |

另加两项衍生观测（不作为独立未知项）：

- `site=40 playAudios` 的 `mask` 分布：期望只看到 `0x10000`（what=7/14/3 路径）；若出现 `0x20000` → 直接证明"补丁漏拦"在真机上发生。
- `site=30 onRouterDetailInfo` 的 `mask` 分布：期望 `0x10000`；出现 `0x20000/0x80000` → 对应 what=11/13 路径被走到。

### 8.3 异常停止条件（全局）

1. `:core` pid 变化 → 立即停止，不再继续场景。
2. `maps diff` 非空 → 立即停止并回滚。
3. 任一入口 8 字节读回与基线不符 → 立即停止并回滚。
4. `playAudios` 出现 `mask=0x20000` 且 `res != 0` → 记录后停止（安全边界被突破）。
5. 探针行数在单场景内 > 20000 → 停止（缓冲溢出风险）。
6. `site=10` 出现 `what > 16` → 记录后停止（出现未预期消息类型）。
7. 单轮语音超过 60 s 未出现任何 `site=10` → 停止（ASR 未命中，环境问题）。
