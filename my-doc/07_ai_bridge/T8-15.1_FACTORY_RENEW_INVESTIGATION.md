# T8-15.1 原厂连续聆听续期机制：调查结果与可实施方案

- 基线：`2174a17078b24d30649b877d2368db135be2507c`
- 目标（任务书 §一）：一次唤醒 → 提问 → 回答 → 播报结束 → **设备继续聆听** → 直接追问，不喊唤醒词
- 本轮范围：**只做调查 + 可实施方案 + 证据归档**。没有改任何代码、没有装 hook、没有部署、
  没有重启 `smartapp:core`、没有写设备文件（除 `evidence/` 里的本地副本）。
- 一句话结论：
  **续期参数是真的、可安全调用的；但"要不要续听"由服务端决定，客户端唯一的合法输入就是
  这个参数。而它今天恒为 0，原因已定位到云端下发的 `fullDuplexDeviceEnable: false`。**

## 1. 方法与边界

- 目标工件：`/system/app/smartapp/lib/arm/libsmartbox.so`、`libagmmi.so`、`libagui.so`。
  设备上 `libagmmi.so` 的 sha256 = `65062e2d95a6055d0786ef20c3201737b65975b6d16ad0ea8987746a23f05b78`
  与本地系统镜像**逐字节一致**，所以下面所有地址都对得上正在跑的进程。
- 工具：NDK r21e `llvm-objdump` / `llvm-readelf`；设备侧只做 `cat`/`grep` 读取。
- 没有做：任何注入、hook 安装、进程重启、设备文件写入、`setFullDuplexDialogRenewDuration` 调用。
- **一处证据勘误（影响后续所有地址解析）**：
  - `evidence/t8-12-p4/plt_map_libagmmi.txt` 的**文件内容对应 libagmmi.so**（`.plt` = `0x41be8`），
    但它的表头写着 "source: libsmartbox.so"，是上一轮复制表头时的笔误；

  - 本报告所有 `plt+N` 都按"目标库自己的 .plt 基址"换算，已逐条核对落点符号。

## 2. setter 的静态证据（A）

### 2.1 符号（两个库、同一语义）

```
libsmartbox.so: 000fd7d0    36 FUNC  GLOBAL DEFAULT  12  _ZN9AliAiLabs4AGUI8GenieApi32setFullDuplexDialogRenewDurationEj
libagmmi.so   : 00047f88    36 FUNC  GLOBAL DEFAULT  11  _ZN9AliAiLabs4AGUI8GenieApi32setFullDuplexDialogRenewDurationEj
libagui.so    : 00000000     0 FUNC  GLOBAL DEFAULT UND  （引用方）
libagui.so    : 00015a38     8 FUNC  GLOBAL DEFAULT  12  Java_com_alibaba_ailabs_geniesdk_AiLabsCore_setFullDuplexDialogRenewDuration
```

- `...32setFullDuplexDialogRenewDurationEj` 的 `Ej` = **参数类型 `unsigned int`**，函数本身返回 `void`。
- 说明它是 SDK 的正式 API：Java 侧 `com.alibaba.ailabs.geniesdk.AiLabsCore` 有这个 native 方法
  （libagui 里是 8 字节 thunk，跳到 libagmmi 的实现）。

### 2.2 实现（libsmartbox @0xfd7d0，36 字节，全文）

```
fd7d0: push {r4,r10,r11,lr}          ; 标准 prologue
fd7d4: add  r11, sp, #8
fd7d8: mov  r4, r0                   ; r4 = duration(ms)
fd7dc: bl   IMmiCore::getInstance()  ; (0x8dc80 → _ZN9AliAiLabs4AGUI8IMmiCore11getInstanceEv)
fd7e0: cmp  r0, #0
fd7e4: beq  +0x20 (return)           ; 实例不存在 -> 什么都不做
fd7e8: bl   MmiCtx::getSessionManager()   ; (0x91718 → _ZN9AliAiLabs4AGUI6MmiCtx17getSessionManagerEv)
fd7ec: str  r4, [r0, #128]           ; SessionManager + 0x80 = duration
fd7f0: pop  {r4,r10,r11,pc}
```

要点：
1. **只写一个 uint32 字段**（`SessionManager + 0x80`），不分配内存、不加锁、不发网络、不回调。
2. 有 **null 保护**：`IMmiCore` 实例不在时是 no-op，不会崩。
3. **无返回值**：调用方不需要判定成功；失败即"没设上"，可观测（payload 仍是 0）。
4. ABI 干净：`extern "C"` 风格单参数调用即可，不需要构造任何 C++ 对象（这正是任务书要求"不凭猜测构造结构体"的答案：**根本不需要结构体**）。

## 3. 值在哪里被消费（A）——决定"什么时候调"

`SessionManager::onStopTalk(int, _WakeEndInfo*)` @ `0x113918`（828 B）关键窗口：

```
113a48: ldr r4, [r5, #72]      ; r4 = 会话上下文对象 (this+0x48)
113a4c: ldr r0, [r5, #128]     ; r0 = this->[0x80] = 上面 setter 写的续期时长
113a50: mov r1, #0
113a54: str r0, [r4, #76]      ; ctx+0x4C = duplexDialogRenew   ← 进 UpdateContext payload
113a58: ldr r0, [r5]
113a5c: str r1, [r5, #128]     ; this->[0x80] = 0                ← 用一次就清零
113a60: ...
113a6c: blx r2                 ; 虚调用（本函数后续即"send end frame with payload"日志行所在路径）
```

推论（与真机日志完全吻合，见 §6.1）：

- `duplexDialogRenew` 的值**就是** `SessionManager+0x80`，在 **onStopTalk（用户说完、EOU）那一刻**被读走。
- 想让**当前这一轮**带上 N，必须在 **onStopTalk 之前**设值 → 也就是 **onStartTalk 之后、EOU 之前**；
  **在我们的 TTS 播报之后设值，对当轮无效**（只会留给下一轮）。
- 每次读完清零，所以**每轮都要重新设**，不能只设一次。

## 4. 为什么今天恒为 0（B）

### 4.1 设备上的云端设置（原始文件，只读）

`/data/data/com.alibaba.ailabs.genie.smartapp/shared_prefs/runtime_device_mirror.xml`
（7914 B，mtime `2026-11-22 13:24`，`system:system 0660`）：

```json
"fullDuplexDialog": {
  "version": 0,
  "value": "{ \"disableAppPages\": [], \"productFullDuplex\": true,
             \"fullDuplexEnable\": true, \"fullDuplexDeviceEnable\": false,
             \"value\": false }",
  "forceUpdate": false, "needUpdate": false
}
```

| 字段 | 值 | 含义 |
|---|---|---|
| `productFullDuplex` | **true** | 这个产品型号支持后续可续期的全双工/连续对话 |
| `fullDuplexEnable` | **true** | 功能总开关是开的 |
| `fullDuplexDeviceEnable` | **false** | **设备级开关是关的** ← `duplexDialogRenew` 恒 0 的直接原因 |
| `disableAppPages` | `[]` | 没有页面被排除（所以 §5 的"页面黑名单"不是拦路石） |

即：**能力有、总开关有、这台设备没打开**。

### 4.2 app 自己的开关路径（B 字符串级 / C 调用图未证）

`classes3.dex`（app 的 dex，已从设备提取）里存在这些符号：

```
DataBean$FullDuplexDialogBean          getFullDuplexDialog / setFullDuplexDialogRenew
MSG_fullDuplexDialogRenew              mFullDuplexDialogEnabled / fullDuplexDialogEnabled
onChange: full duplex dialog setting change to ...
setFullDuplexDialogRenewDuration       （AiLabsCore 的 native 声明）
```

说明原厂自己的链路是：**设置模式里的"全双工/连续对话" → 触发 `MSG_fullDuplexDialogRenew`
→ 调 `setFullDuplexDialogRenewDuration`**。这条链今天没有跑，因为设置是 false。（调用图未证：见 §8）

## 5. 客户端能否自己"接着听"（A）——不能（合法地）

`ContinuousDialogManager::onNotify(int code, void*, int, int)` @ `0x156900`：

```
156984: movw r0, #1102          ; 1102 = 0x44E
156988: cmp  r5, r0
15698c: bne  → 0x156AAC（清 this+96；而 0x156A38 那条分支会把 code 低字节写进 this+112 当"已武装"门闩）
156990: ... gettimeofday → 毫秒
1569b0: ldrd r2,r3,[r4,#120]    ; 上次 notify 的时间戳
1569b8: movw r2, #4999
1569c0: subs/rscs ...           ; 要求 delta <= 4999 ms
1569c8: blt  → 直接返回（超过 5 s，不续听）
1569d8: ... log(220)
156a0c: bl   IMmiCore::getInstance()      ; 空则返回
156a18: bl   MmiCtx::getSessionManager()
156a1c: bl   SessionManager::fullDuplexDialogCurPageInBlackList()   ; 非 0 则返回
156a2c: bl   ContinuousDialogManager::startFullDuplexDialog()        ; ← 真正续听
```

`startFullDuplexDialog()` @ `0x1565e8`（264 B）自身的条件与动作：

```
1565f8: ldrb r0, [r0, #112]     ; 门闩：为 0 直接返回（由上一个 notify 打开）
156650: ... 取会话 id（this+4）
156658: bl   IInputDeviceManager::getInputType()
156670: blx  r3                 ; 虚调用：请求输入设备开始（带上会话 id / 唤醒信息串）
156674: bl   TimerManager::getInstance()
1566b8: bl   resetWakupInfo()   ; 复位唤醒信息，避免"新一轮"被当成旧唤醒
1566bc: mov r0,#1 ; strb [this+96] = 1     ; 标记"续听中"
1566c4: mvn r0,#0 ; str [this+4] = -1      ; 清会话 id
1566d0: strb [this+112] = 0                ; 清门闩
```

结论：

1. **客户端没有任何"自己决定续听"的合法入口**。所有路径都要求"服务端先发 notify"留下的状态
   （`+112` 门闩、`+120` 时间戳、会话状态 ∈ {-1,14}）。
2. 因此**伪造这些门闩 = 构造原厂 CDM 状态**，正是任务书 §三.4 明确禁止的。
3. 唯一"原厂认可"的输入就是 **`duplexDialogRenew` 这个参数**（§2/§3）——告诉服务端
   "我这一轮支持在多少毫秒内继续听"。**续不续，由云决定**。

## 7. 可实施方案

### 方案 R1（零代码，先试这个）：把"连续对话"这个原厂开关打开

- 做法：手机侧"天猫精灵"App → 该设备 → 设置 → **连续对话 / 全双工对话**（若产品暴露）。
- 判定（全部只读）：
  1. `runtime_device_mirror.xml` 里 `fullDuplexDeviceEnable` 变为 `true`；
  2. logcat 里 StopTalk payload 出现 `"duplexDialogRenew": <非0>`；
  3. **不喊唤醒词**说第二句 → 出现新的 `onStartTalk`（`wakeupWord` 为空/旧值）或 `onListenStarted`。
- 优点：完全原厂、零风险、零 hook。
- 限制：如果该产品在 App 里没有这个开关，就只能由云端/账号侧配置；**改本地 mirror 文件不会生效**
  （那是"云端镜像"，app 内存里已经是 false，要生效必须重启 app，而本轮明令禁止重启 `:core`）。

### 方案 R2（代码，需你批准后实施）：在现有 TTS guard 里，每轮 EOU 前设置续期

设计（**不改 :core 业务代码、不加新 .so、不重启**）：

| 项 | 内容 |
|---|---|
| 载体 | `android/hook_tts/libtg_ttsguard.c`（已常驻 `:core` 的既有注入库） |
| 新 hook | 前置：`_ZN9AliAiLabs4AGUI14SessionManager10onStopTalkEiPNS0_19IInputDeviceManager13_WakeEndInfo_E` @ `0x113918`（ARM、`push {r4,r5,r6,r7,r8,r9,r10,r11,lr}` 开头，与既有两个 hook 同模式） |
| 前置回调 | `dlsym(RTLD_DEFAULT, "_ZN9AliAiLabs4AGUI8GenieApi32setFullDuplexDialogRenewDurationEj")` → 校验地址 == `libsmartbox.base + 0xfd7d0`（否则拒绝装）→ 调 `(renew_ms)`；随后跳回 trampoline 执行原函数 |
| 为什么放在 onStopTalk 入口 | §3：值在同一个函数体前面被读走并清零；入口处设值 100% 命中当轮，且不依赖任何时序 |
| 配置 | `renew_ms`（0 = **不安装这个 hook**，与今天行为完全一致；建议首测 60000） |
| 可观测 | `renew_calls`、`renew_last_ms`、`renew_last_err`、hook 装/卸状态；日志一行 `tg renew: set N (call#k)`，方便与 StopTalk payload 行对齐 |
| 失败策略 | 符号缺失/偏移不符/首字节指纹不符 → **拒绝安装并置错**（沿用现有 fail-closed 语义），绝不"尽力而为" |
| 明确不做 | 不伪造 `+112/+120` 门闩；不调 `startFullDuplexDialog`；不构造 CDM 结构体；不动唤醒/KWS/ASR；不改 `:core` 文件；不重启进程 |

风险与对策：

| 风险 | 对策 |
|---|---|
| 从会话线程调用 setter 有副作用 | 该函数只做一次空判 + 一次 32 位写，无分配/无锁/无回调（§2.2）；仍保留 `renew_ms=0` 一键关闭 |
| 第三个 inline hook 的稳定性 | 与既有两个 hook 同模式（ARM 序言 + trampoline），并且只在装配成功后启用；失败即不启用 |
| 服务端无视该字段 | 那就**没有**合法手段让原厂续听（§5）；届时只能回到"引擎级 ASR"或云端开通，报告会如实写"未实现"，不编造 |

### 7.1 hook 点唯一性与可安装性（本轮新增证据，A/B）

| 事实 | 证据 |
|---|---|
| `SessionManager::onStopTalk(int,_WakeEndInfo*)` 在镜像里有**两份**：`libsmartbox.so+0x113918`（828 B）与 `libagmmi.so+0x5f080`（828 B），**首 16 字节完全相同**（同源编译） | `symbol_copies_and_prologues.txt` |
| **但 `:core`（pid 30807）只加载了 libsmartbox**，`libagmmi.so` 根本没被映射 | `loaded_libs_core.txt`（读 `/proc/30807/maps`） |
| 因此该进程里唯一可达的实现就是 **`libsmartbox.so + 0x113918`**；libagmmi 那份是死代码 | 同上 |
| setter 同样两份，进程里只有 `libsmartbox+0xfd7d0` 可达；`dlsym(RTLD_DEFAULT, …)` 只会解析到它 | 同上 |
| 我们的 `libtg_ttsguard.so` **已经常驻 `:core`**（maps 里有 `/data/local/tmp/t7/libtg_ttsguard.so`） | 同上 |
| 两个函数的 ARM 序言（可做 fail-closed 指纹） | onStopTalk：`f0 4f 2d e9 1c b0 8d e2 54 d0 4d e2`；setter：`10 4c 2d e9 08 b0 8d e2 00 40 a0 e1` |
| 两个 onStopTalk 重载都**没有直接 BL 调用者**（走虚接口/回调指针），所以 inline hook 只能装在"函数入口"这一层，不能靠改调用点 | 全 `.text` 扫描 B/BL 与字面量指针，0 命中（`evidence/t8-15.1/` 记录扫描结论） |

结论：**hook 点唯一、可达、可指纹校验、载体已在进程内** —— R2 的安装前提成立。
安装时仍要求：`dlsym` 解析结果必须落在 `libsmartbox.base + 0x113918` / `+0xfd7d0`
（用 `dladdr` 或手工 base 计算核对），且序言指纹一致；任一不符 → **拒绝安装并置错**，
不做"尽力而为"。


### 方案 R3（列为观察项，未取证）：GenieApi ContentProvider 的 method 表

我们自己的 `TtsExec` 已经在用原厂 ContentProvider
`content://com.alibaba.ailabs.genie.assistant.provider/GenieApi`（`method=4` playTTS、`method=5` stopTTS）。

下一步若要做，需要先把 `classes*.dex` 静态解析出 `GenieTable.query` 的 `lookupswitch` 表。

审核提示"听不懂时会触发重听 + 提示音"。用只读 logcat + PC 放音做了一次探针

21:12:01.722 onNlpResult code = 0, sessionId = 1969746, data = 1        ← 只有唤醒词，没有命令

对照同一次捕获里的三次"真唤醒"：`wakeupType = 0`、`wakeupWord=tian mao jing ling`、

|---|---|---|

**即：原厂本来就有一条"不喊唤醒词、把麦克风重新打开、继续用原厂 ASR"的路径**，
触发条件我们这次看到的是"这一轮的 final 只有唤醒词（等于没听懂/没命令）→ NLU code=0
→ 提示音 → 新 session（type=1）"。这次没人接着说话，所以该会话没有产生 final
（`events.jsonl` 从 699 → 700，只多了上面那条"天猫精灵"）。

### 10.1 这条路径的调用入口（静态，A）

```
GenieApi::startTalk(InputDeviceType type, const _WakeUpInfo_* info) @ libsmartbox+0xfcff8, 88 B
  if (IMmiCore::getInstance() == 0) return 0;
  manager = instance->vtbl[4]();
  ok = manager->vtbl[2](type, info);          // 观察：type=1, info 空 => 就是上表的会话
  return ok > 0;
```

`InputDeviceManager::startTalk(type, info)` @ `0x107e14`（344 B）：
先按 type 找设备（`plt+0x51c8` 帮助函数），找到才把 `info` 原样传给
`device->vtbl[3](info)`；**本函数自身不解引用 info**，但下游设备实现是否接受 NULL
本轮**未证**（这正是要小心的点）。

### 10.2 这与"麦克风关闭时长 5/8/10 s"的关系

该选项对应 `devicesettingInfo::asrrecordtime = 5` / mirror `asrRecordTime.value = 5`
（`runtime.xml` / `runtime_device_mirror.xml`）。今天实测：唤醒 21:11:53.07 → 首次
EOU/退出 21:12:01.26，窗口 ≈ **8.2 s**，与"8 秒档"吻合。它是**本轮唤醒的最长录音窗口**，
不是续期开关；但如果走 11.1 的入口，续听窗口的长度就由它决定（想要更长就选 10 s）。

### 10.3 由此得到的两个方案（都要你点头）

**S1（零代码，先做）**：真人验证这条通道能被我们的链路接住——
唤醒后**只说"天猫精灵"**（或含糊说一句）→ 听到提示音后**立刻说真问题** →
查 `events.jsonl` 是否新增一条**新 session id、无唤醒词**的 final，且 worker 把它当成
同一会话的下一轮（`session_ctrl.round` 增加、`followup_rounds` 增加）。
这一步不需要改任何代码，却直接回答"设备能不能在不再唤醒的情况下把第二句交给 AI"。

**S2（代码，需批准）**：由我们在 TTS 播完之后主动调 11.1 的入口。
触发点用既有的 `TtsManager::onTtsEnd(int)` @ `0x11f780`，并且沿用 TTS guard 已有的
"我方 TTS 白名单"来区分"这是我们的回答播完了"，然后 `startTalk(1, NULL)`。
配置默认关闭；返回 0 / 没有出现 `wakeupType=1` 的 onStartTalk 就如实记为失败。

风险：`info = NULL` 是否被下游接受**未证**（§10.1）；首次测试必须在受控状态、可回滚，
并且只在 `:core` 不重启的前提下做。这一条就是任务书之前禁止的 `startTalk`，
但现在它不再是"未经证实"——原厂自己就在用同一条路（type=1、无唤醒词）。


### 10.4 S1 复现失败的原因（2026-11-23 晚，真人多次尝试未触发）

审核按 S1 试了多次"只唤唤醒词"，没有出现重听。原因可以从 §10 的时间线直接读出：

- 那次重听发生在 **已经有一轮在听（session 1969746）** 的时候；被 ASR 识别成 "天猫精灵" 的
  是**第二轮里又出现的唤醒词**（我的音频文件本身以"天猫精灵"开头，KWS 在 21:12:01.255
  又命中一次，于是新开一轮，ASR 只截到了唤醒词那 1.7 s）。
- 换句话说，触发条件更可能是"**这一轮 ASR 的结果恰好事唤醒词/空命令**"，
  而不是"用户唤醒后不说话"。正常用法里，唤醒后不说话 → ASR 没有文本 → **不会有 final**，
  客户端走的是超时退出（我们在 21:12:01.26 那次看到的 `exit=1`），不会提示重听。

结论：**S1 只能证明"通道存在"，不能当成可复现的触发器。** 想让设备自己重听，
必须在我们的时序里主动调 §10.1 的入口（S2）。

### 10.5 官方 JNI 入口的形状（补充证据，B）

`Java_com_alibaba_ailabs_geniesdk_AiLabsCore_startTalk`（libagui +0x13830，1208 B）开头
直接把 **栈上约 88 字节的一段内存整体清零**（`vmov.i32 q8,#0` + 多组 `vst1.64`），
再用 Java 参数（jint type + 字符串）填字段，然后才进 native `GenieApi::startTalk`。

也就是说**原厂自己的调用形状是"一个全零的 WakeUpInfo + type"**，而不是 `NULL`。
这给出比 §10.1 更稳的 S2 写法：**传一个全零的 88 字节缓冲**（和原厂 JNI 完全同形），
而不是赌 `NULL` 被接受。（注：JNI→native 的精确实参顺序本轮未逐条钉死，标为 B；
真正调用前会先在 guard 里用"返回值 + 日志"验证，不靠猜。）
