## 一、R13：收尾与已排队结果的竞争

### 1.1 三条确定性事实（先把"谁在队列里"钉住）

| 事实 | 证据 |
|---|---|
| **NLU 结果走 Handler 队列**，且用 **1 参** `Handler::postMessage(Message*)`（`ann 0x4fb8`，全库 43 处） | `0x11d9f0`（`what=7` 投递）、`0x11da3c`（`what=11`）、`0x11da88`（`what=12`）都 `b <plt+0x4fb8>`；`plt_map` 该桩 = `Handler::postMessage(Message*)` |
| **收尾不是消息，是内联调用**：`what=1` 的 handler 体内直接 `bl SessionDispatch::onNlpResult(sid, 3, NULL)` | `0x11cbf8`（在 `SessionProxy::onHandler` 体内），不是 `postMessage` |
| **`what=1` 自身用 4 参 `postMessage(msg,char,char,char)`**（`ann 0x5450`，全库 9 处），该重载把两个 char 转发给不同 enqueue 分支 | `0x11c374`（what=1 主路）、`0x11cb9c`（收尾后重投）；被调函数 `libagutils 0x2d3f8`：`str r5,[r4,#36]` 之后按 r2/r3 分支走不同 enqueue |

由后两条可得的结论是**反面的**：`what=1` 与结果消息可能不在同一个队列语义上，**无法证明"先投递的结果一定先被处理"**。因此：

- 用"FIFO ⇒ 不需要宽限"来论证 **不成立**；
- 用"2 s 足够覆盖队列延迟"来论证 **也不成立**（见 1.2 的实测）。

### 1.2 2 秒宽限期被证伪（主机模型）

`analysis/t8_12/p7/t8_12_7_lifecycle_model.c` 里两种策略并存：

- `POLICY_GRACE`（第六阶段）：`type=3` 时 `deadline = min(deadline, now+2000)`；
- `POLICY_EPOCH`（本阶段）：`type=3` **不改 deadline、不改 used**，只记 `closed_at_ms`。

`run_late(policy, δ)` 模拟"收尾执行完 δ 毫秒后，才有一个并发投递的同轮结果"：

```
[A1] 提前处理（队列延迟 2500ms）
  [PASS] GRACE : 早到结果命中（与队列延迟无关）
  [PASS] EPOCH : 早到结果命中
[A2] 晚到 delta=2500ms（大于 2 秒宽限）
  [PASS] GRACE : delta>2s 时漏拦（放行给原厂）——2 秒假设被证伪
  [PASS] EPOCH : 仍然命中（收尾不参与过期决策）
[A3] 晚到 delta=100ms
  [PASS] GRACE : delta<2s 时命中（只在阈值内有效）
  [PASS] EPOCH : 同样命中
[A4] 提前处理（队列延迟 8000ms，远超 2s）
  [PASS] GRACE : 早到结果仍命中
  [PASS] EPOCH : 早到结果仍命中
```

- `[A1]/[A4]` 说明"早到"与队列延迟无关（早到就是早到，延迟多大都在收尾前处理完）；
- `[A2]` 说明 **GRACE 的失效点只是一个时刻阈值**：任何 δ>2 s 的晚到结果都会被放给原厂 → 该轮接管失效（原厂执行技能，正是评审最担心的旁路）；
- `[A3]` 说明 GRACE 只在阈值内有效——这恰好证明它是**假设**而不是**证明**。

### 1.3 如果队列延迟真的超过 2 s 会怎样

| 策略 | 结果 |
|---|---|
| GRACE（2 s） | 槽位到期 → 该结果被判"未登记" → 放行原厂 → **AI 轮次的原厂技能被执行**（功能回退，且与 R16 的"旁路"同型） |
| EPOCH（本阶段） | 槽位仍在 → 仍然拦截；到期只由 TTL/下一次 `on_final` 决定 → **与延迟无关** |

### 1.4 EPOCH 策略的完整规则（不含任何时间常数）

```
on_final(sid, is_local):
    if is_local: 清槽（本地指令，交还原厂）           # 已有行为
    else:        重置 deadline = now + TTL；gen++；closed=0   # ★ 权威重判
type=3:
    只记 closed_at = now；不改 deadline/used          # ★ 收尾不参与过期
should_drop(sid):
    if !mutex_ready: return 1                        # fail-closed
    if key 为空:    开该 key 的窗口; return 1
    s = find(key); if s && s->deadline <= now: 清 s
    if s: return 1
    if 窗口(key) 生效: return 1
    return 0
```

- **唯一定时器是 TTL(30 s)**，这是既有行为，本阶段没有引入新常数；
- "收尾"不再影响是否拦截，只影响可观测性（`closed_at` 用于统计"收尾后仍拦到结果"的次数）；
- 新代次由 `on_final` 决定 → **快速复用安全**（见 §2.3 B3）。

### 1.5 残余风险（必须计数，不能靠时间来消）

| 残余 | 说明 | 处置 |
|---|---|---|
| **跨轮误归属** | 属于第 N 轮的结果，在第 N+1 轮的 `on_final` **之后**才到达 → 用第 N+1 轮的决定 | 计数 `stale_after_new_final`；若两轮都是 AI 轮，结论相同（仍拦），无功能影响；若 N+1 是本地轮，则会被放行（可接受：本地轮本就该交还原厂） |
| **收尾后仍拦到结果** | `res_after_teardown` > 0 说明"收尾与结果存在交错" | 只计数，不改变策略 |
| **长寿命槽位** | 最坏 30 s（TTL） | 由 `on_final` 覆盖 + 容量上限约束；见 §2 |

### 1.6 expire_soon 与查询的竞态

**已消除**：EPOCH 策略没有 `expire_soon`。剩下唯一的到期路径是 `should_drop` 内部"读时过期"，它与查表在**同一个临界区**（`t8_lock`）内完成，不存在"先过期后查询"的两段式竞态。

> 注：第六阶段提出的 `expire_soon` 若实施，本身也需要与 `should_drop` 同锁——这在 EPOCH 下不再是问题。

## 二、R14：按 key 绑定后的边界（主机模型）

### 2.1 边界矩阵与实测

| 边界 | 断言 | 结果 |
|---|---|---|
| **空 key 连续 5 次** | 每次都 fail-closed | 5/5 PASS |
| 空 key 的窗口是否污染具体会话 | `"555"` 不被拦 | PASS |
| **64 槽耗尽** | 溢出会话被拦；已有会话仍拦；无关未登记**不**被拦 | 3/3 PASS |
| **同 sid 快速复用** | 收尾 3 s 后仍未放行；新一轮登记后仍拦；新一轮若判本地则清槽放行 | 4/4 PASS |
| **TTL 到界** | 到期放行；到期后重新登记可再次接管 | 2/2 PASS |
| **mutex 不可用** | 已登记/空 key/未登记**一律拦** | 3/3 PASS |
| **4 线程 × 20000 次并发** | 无非法判定值；登记与命中双向计数非零；收尾路径被覆盖 16000 次 | 3/3 PASS |

```
[B5] mutex 不可用：必须 fail-closed
  [PASS] 已登记会话也拦（不碰共享状态）
  [PASS] 空 key 也拦
  [PASS] 未登记也拦（fail-closed 不退化）
[C1] 4 线程并发登记/收尾/查询/空 key
  [PASS] 并发期间没有任何非法判定值
  [PASS] 并发产生了登记(5266)与命中(1261)两个方向的计数
  [PASS] 并发覆盖了收尾路径(16000 次)
RESULT: PASS (checks=29 fails=0)
```

### 2.2 fail-closed 是否因"缩作用域"而退化

**没有**。三条硬点：

1. `mutex_ready == 0` → 首行 `return 1`，不碰共享状态（B5 三种输入全覆盖）；
2. 空 key → 每次必丢（B1 连续 5 次），且窗口只绑空 key，不污染其它会话；
3. 容量耗尽 → **溢出会话**仍被拦（B2），只是不再株连无关会话。

### 2.3 旧窗口是否误伤新一轮（B3 的实际序列）

```
on_final("300", AI)     -> 登记
should_drop("300")      -> 1        （第一轮接管）
on_teardown("300")      -> 只记 closed_at
+3000ms
should_drop("300")      -> 1        （收尾不丢拦：EPOCH 的关键差别）
on_final("300", AI)     -> gen++，deadline 重置
should_drop("300")      -> 1        （新代次继续接管）
on_final("300", LOCAL)  -> 清槽
should_drop("300")      -> 0        （新一轮是本地指令 → 放行）
```

旧轮的 `closed_at` 不会跨越 `on_final` 生效；真正的"旧轮影响新轮"只剩 §1.5 的跨轮误归属，且已计数。

## 三、R16：三入口 ABI 与三点安装事务

### 3.1 三入口 ABI 对照表（【静态已证实】）

| 项 | `SessionDispatch::onNlpResult` | `onNlpResultInner` | `onPushNlpResult` |
|---|---|---|---|
| vaddr / size | `0x118ebc` / 1952 B | `0x11896c` / 116 B | `0x1189ec` / 1072 B |
| C++ 原型 | `void (int sid, int type, NlpResult* res)` | `void (int sid, NlpResult* res)` | `void (int sid, NlpResult* res)` |
| `r0` | `this`，**被使用**（`0x118edc mov r8,r0` → `0x118f74 ldr r0,[r4,#52]!` 等成员访问） | `this`，**入口即被覆盖**（`0x118980 add r0,sp,#12`），不使用 | `this`，**保存到 r6**（`0x1189fc mov r6,r0`），后续是否使用未逐条核对 |
| `r1` | sid | sid | sid |
| `r2` | **type** | **res** | **res** |

**回调如何解释参数（按 site）**

| site | a1 | a2 | a3 | 判定 |
|---|---|---|---|---|
| 11 `onNlpResult` | sid | type | res | 先看 `type∈{2,3}` → 放行；否则按会话 |

### 3.2 三点安装事务状态机

```
IDLE
 └─> PRECHECK            三个入口逐一比对原始 8 字节（E92D…/E28D…）
      │  任一不符 → FAILED（未写任何字节，无需回滚）
      └─> FROZEN         pause_and_check(三个区间)：ptrace 暂停全部线程 + PC 区间核对
           │  冻结失败/区间不干净（12 次重试后）→ FAILED（未写）
           └─> INSTALLING(i=0..2)
                │  每点：写 8 字节（E51FF004 + stub 地址）→ 读回校验 → applied[i]=1
                │  任一点失败 → ROLLING_BACK
                └─> ROLLING_BACK(j=i..0)   逆序恢复 applied[j] 的原始 8 字节
                     │  任一恢复失败 → ROLLBACK_FAILED（保留 applied[j]=1，可重试）
                     └─> FAILED
           └─> 三点全部成功 → DONE（唯一成功出口）
```

**关键约束**

1. **一次冻结覆盖三点**：不允许"每点各自冻结一次"（会在点与点之间留下未冻结窗口，且无法保证原子性）；
2. **回滚逆序**，且只回滚 `applied[j]==1` 的点（未写的点 `restore` 是 no-op，见 S7）；
3. **回滚失败不等于失败已处理**：状态必须是 `ROLLBACK_FAILED`，且失败点保留 `applied=1`，否则下一次重试会把它当成"已恢复"；
4. **DONE 的唯一条件**是三点都 `applied` 且都读回成功——不存在"部分成功"这种状态。

### 3.3 故障注入结果（13 类故障 / 82 条断言）

```
[S0]    无故障                    → DONE，三点均为补丁态
[S1.0..2] 预检失败 at point i     → 非 DONE，未写任何字节
[S2]    冻结失败                  → 非 DONE
[S3.0..2] PC 落在 point i 区间    → 非 DONE，三点仍为原始序言
[S4.0..2] 写入失败 at point i     → 非 DONE，已装点全部回滚，三点逐字等于原始
[S5.0..2] 读回不一致 at point i   → 同上
[S6.0..1] 写入失败 + 回滚 point i 也失败 → ROLLBACK_FAILED，applied[i]=1（可重试）
[S7]    未 applied 的点被要求回滚 → no-op，状态 FAILED（不是 ROLLBACK_FAILED）
RESULT: PASS (checks=82 fails=0)
```

四条不变式在每类故障下都被断言：

- **I1** 只有三点全成功才 `DONE`；
- **I2** 任何失败 → 终态 ∈ {`FAILED`, `ROLLBACK_FAILED`}，**永不为 `DONE`**；
- **I3** 回滚后三点 8 字节逐字等于原始序言；
- **I4** "半安装被报告为成功"计数 = 0。

### 3.4 三点覆盖是否引入重复执行 / 遗漏

| 情形 | 结论 |
|---|---|
| 同一轮命中多个入口 | 不会：`what=7/11/12` 是三种不同消息，一轮只投递一种 |
| 三点都跳过后的副作用 | 被跳过的是三个被调函数本体；调用者在返回后只清 `msg[+12]` 并返回，不重投 |
| 是否还有第四跳 | 无：`playAudios` 全库 3 个调用者，`processMediaCommand`/`preProcessCommand` 的唯一调用者都在 `playAudios` 内 |
| 新的写错风险 | site 20/21 的 `r3` 是垃圾值（§3.1 表），实现必须按 site 取参 |

### 3.5 工程缺口（本阶段发现，P1）

现有 `nlu_patch` 是**单点**事务（一个 `np_patch` 对象、一处 entry）。三点覆盖需要：

- 一个 `np_group`（3 个 `np_patch` + 一次 freeze + 逆序回滚 + 组级读回）；
- 冻结必须由 Injector 侧完成（`pause_and_check` 覆盖三个区间），库内只做"已冻结"断言（沿用现有 `world_frozen` 契约）；
- 组级状态：`installed_mask`、`rollback_pending`。

这不是"改一个常量"，而是一个新模块（估计 150–200 行），应在 T8-13 里单独立项。
