## 一、任务三（P1）：并发模型纠错

先做这一项，因为第七阶段的并发 PASS 本身不可信，后面的结论都要靠它支撑。

### 1.1 竞争点清单（逐字段）

第七阶段 `worker()` 里 `w->st->now += 1;` 是**无锁读-改-写**，4 线程同时执行属 C 语言层面的数据竞争（UB）。逐字段审计后，需要保护的共享对象如下：

| 共享对象 | 谁会写 | 修复后的保护 | 并发线程是否触及 |
|---|---|---|---|
| `now` | `clock_add/set`（原 `now += 1`） | 与表同一把 `mu` | 是 |
| `slots[64]`（含 `key/deadline/gen/closed_at/local_decided`） | `on_final`/`on_teardown`/`should_drop`/`find_locked`/`alloc_locked` | `mu` + `need_lock()` 断言 | 是 |
| `win[2][4]` | `window_open`/`window_active` | `mu` + 断言 | 是 |
| 18 个 `long` 计数器（`marked/dropped/passed/unknown/teardown_seen/teardown_hit/local_declined/...`） | 上列函数 | `mu` + 断言 | 是 |
| `illegal_decisions` | `worker` 检测到非法判定值 | `__atomic_fetch_add`（唯一允许原子访问的字段） | 是 |
| `lock_violations` / `owner` / `depth` | `lock`/`unlock`/`need_lock` | `mu`（`need_lock` 只在"已经违例"的路径上无保护地自增，见 1.5） | 违例路径 |
| `checks` / `fails` | `chk` 仅主线程 | 不需要；`worker` **不再触碰**（第七阶段是触碰的） | 否 |
| `worker_t.l_*`（7 个本地计数） | 各自线程 | 线程私有 | 否 |

修复方式：新增 `clock_set/clock_add/clock_get`，全部在 `mu` 内完成；`worker` 第 4 分支改为调用 `clock_tick_worker()`。

### 1.2 为什么"改成锁内自增"就够

`now` 的所有读点（`alloc_locked`、`should_drop` 的到期判断、`window_*`）本来就已在临界区内；只有写点漏锁。写点收进同一把锁后，`now` 与 `slots[]` 处于同一个临界区，因此"读到某个 deadline 时 now 是多少"与"此刻谁在改 now"不再有窗口 —— 这同时消掉了第七阶段遗留的一个隐含问题：到期判定与槽位写入原本可能用两个不同时刻的 `now`。

### 1.3 pthread 返回值

```c
chk(create_ok, "pthread_create 全部成功（rc=%d,%d,%d,%d）", rc[0], rc[1], rc[2], rc[3]);
chk(join_ok,   "pthread_join 全部成功（rc=%d,%d,%d,%d）",   jrc[0], jrc[1], jrc[2], jrc[3]);
```

`pthread_mutex_init/lock/unlock` 失败直接 `exit(3)`，不再静默继续（第七阶段是忽略返回值的）。

### 1.4 ThreadSanitizer：本机不可用（实证）

三次真实编译尝试（见证 `evidence/t8-12-p8/tsan_unavailable.txt`）：

```
gcc -fsanitize=thread    -> ld.exe: cannot find -ltsan
gcc -fsanitize=address   -> ld.exe: cannot find -lasan
gcc -fsanitize=undefined -> ld.exe: cannot find -lubsan
```

工具链旁证：`gcc.exe (tdm64-1) 10.3.0`（mingw-w64，**本身不提供 TSan 运行时**，TSan 需要 Linux/POSIX）；`C:\msys64`、`C:\cygwin64`、`C:\Program Files\LLVM` 均不存在；`docker`/`podman`/`clang` 均无；`wsl -l -q` 无任何发行版（只有帮助文本）。NDK r21e 里的 clang 是交叉编译器，Windows 宿主也不支持 TSan。

**结论：编译器级数据竞争检测在本机做不了**，这属于工具链限制，不是省略。要在 Linux 上复跑，命令是：

```
gcc -fsanitize=thread -g -O1 -std=c99 -pthread -o model_tsan t8_12_8_lifecycle_model.c
./model_tsan            # 期望 0 条 "WARNING: ThreadSanitizer: data race"
./model_tsan --race-control   # 负向对照，期望出现 data race 报告（证明 TSan 装得上时会报警）
```

### 1.5 替代证据（TSan 不可用时用什么证明"没有竞争"）

三层，逐层可查：

**(D1) 持锁断言**：`need_lock()` 放在每个触碰共享状态的函数入口，检查 `owner == pthread_self() && depth > 0`。任何漏锁访问都会打印 `LOCK-AUDIT violation` 并计为失败，而不是静默通过。并发运行结果：`lock_violations=0`。

**(D2) 精确计数恒等式**：把"计数 > 0"换成等号。任何一次丢失更新都会让等式不成立：

| 恒等式 | 本次运行 |
|---|---|
| `teardown_seen == Σ 各线程收尾调用` | 13334 vs 13334 |
| `teardown_hit == Σ 命中数` | 8780 vs 8780 |
| `local_declined == Σ 本地判定` | 13334 vs 13334 |
| `empty_final == Σ 空 key 判定` | 13332 vs 13332 |
| `marked + alloc_fail == Σ AI 判定` | 8782+4551 vs 13333 |
| `dropped + failclosed + degraded + unknown == Σ 查询` | 13334 vs 13334 |
| `clock_get() == Σ 各线程推进量` | 13333 vs 13333 |

（每轮运行数值会变，等式必须是等号，不是"大于 0"。）

**(D3) 灵敏度负向对照**：`--race-control` 把一次原子自增拆成"读 → 写回"两步。这样拆**不产生 UB**（两次操作都在锁内），但语义上等价于第七阶段的 `now += 1`：中间的其它线程自增会被覆盖。结果：

```
!!! NEGATIVE CONTROL MODE: clock ticks are intentionally lossy !!!
  [FAIL] 时钟精确等于各线程推进量之和（12343 vs 13333）—— now 无丢失更新
RESULT: FAIL (checks=69 fails=1)
```

约 990 次自增被吞掉，恒等式立刻报警。**这证明 D2 的断言不是形式主义**。对照组的失败是**预期输出**，不是回归。

**已知残留（诚实记录）**：`need_lock()` 的违例路径会写全局 `fails`/`lock_violations`，该路径本身无锁。它只可能在"不变量已经被破坏"时执行，且执行后程序就是 FAIL；接受这个瑕疵，但不把它当作正常路径。

## 二、任务一（P0-1）：EPOCH 跨轮结果误放行

### 2.1 复现（E1）

时序与审查意见完全一致：

```
t=0     on_final("S", AI)     -> 登记，开始拦截
t=20    type=3 收尾           -> 只记 closed_at
t=3000  on_final("S", 本地)    -> 第七阶段：释放槽位
t=3100  第 N 轮云侧结果迟到     -> 查表：无槽位 -> 放行给原厂 -> 执行
```

```
[E1] 第七阶段 EPOCH：第 N 轮收尾 -> 第 N+1 轮本地指令 -> 第 N 轮结果迟到 100ms
  [PASS] 复现 P0-1：EPOCH 下旧轮结果进入原厂技能执行路径（exec=1）
  [PASS] 原因：本地判定直接释放了槽位（passed=1）
  [PASS] 该结果既未命中槽位也未计入 stale（dropped=0 stale_after_local=0）
  [PASS] 被当成"从未登记"的 key 放行（unknown=1）
```

审查意见成立：**"本地指令该放行的是本轮结果"这个区分在第七阶段模型里根本不存在** —— 槽位一释放，旧结果就退化成"从未登记的 key"，`stale_after_*` 计数器连一次都不会动。所以第七阶段把这件事写成"可接受的跨轮误归属"是错的分类：它不是"归属错了但还是被拦住"，而是"根本没拦"。

### 2.2 修复规则 EPOCH2

只改一处语义：**本地判定不再释放槽位，改为把槽位标记为"已判本地"并继续压制，直到 TTL 到期或被下一次 AI 登记取代。**

```c
/* 第七阶段 */
if (is_local) { if (s) s->used = 0; }          /* 放行 —— 泄漏点 */
/* 第八阶段 */
if (is_local) { if (s) { s->local_decided = 1; s->deadline_ms = now + TTL_MS; } }
```

同一时序下（E2）：

```
[E2] 第八阶段 EPOCH2：同一时序，本地判定不释放槽位
  [PASS] 旧轮结果被压制，未进入原厂技能执行路径（exec=0）
  [PASS] 命中槽位并拦下（dropped=1）
  [PASS] 同时被标注为"上一轮的迟到结果"（stale_after_local=1）
  [PASS] 本地判定不再计入放行（passed=0）
```

代价与边界（都要写清，不能只报好消息）：

- **压制是"沉默"而不是"放行"**。如果某一轮 `on_final` 没被我们观察到、却真有本轮云侧结果到达，它会被丢掉而不是交给原厂 → 表现为"这轮没反应"。这是**功能退化风险**，属于策略取舍，必须由审查确认是否接受。选择沉默而不是错执行，理由是"错执行会触发原厂技能"，不可控，而沉默可控。
- 压制只对本 key 生效（E6），不误伤其它会话。
- 压制长度受既有 TTL 约束（E5），到期即解除 —— 这是**残留窗口**，见 2.5。

### 2.3 关联能力审查：现有接口能不能判定"这条结果属于哪一轮"

这是审查要求的重点。逐条判定：

| 候选判据 | 粒度 | 能否区分新旧轮 | 依据 |
|---|---|---|---|
| `sid`（`NlpResult[+140]`，`SessionManager[+64]`） | **会话** | **否**。同一会话内连续两轮 sid 不变，这正是危险区间 | p5 的 C5 审计：`isSessionValid(1,sid)` 即 `sid == SessionManager[+64]` |
| `type`（r2 ∈ {1,2,3,7,11,12}） | 消息类别 | **否**。`type=3` 只表示"这轮收尾"，不带轮次号；且 type 来自网络数据（`MmiCtx::getId`） | `0x11cbf8`（收尾）/`0x111134`（exitTalk）调用点 |
| `NlpResult` 其余字段 | 未证实 | **不可用**。152 字节结构里只有 `[+140]=sid` 经过审计确认，其余字段语义未证实 | p5 结构审计 |
| Handler 队列顺序 | 消息 | **未证明**。`what` 投递用 1 参 `postMessage`，`what=1` 用 4 参重载，两者是否同一队列/同一 enqueue 分支未证实 | `ann 0x4fb8` vs `ann 0x5450` |
| 时间戳字段 | — | **不存在**（已审计字段中未发现），且"投递时刻"≠"处理时刻"，即使有也不能直接当代次 | — |
| 我们自建的轮次 token | **轮次** | **原理上可行，当前无回传通道**：`onStream(isFinished)` 能拿到 sid/text，但结果回到 `onNlpResult` 时没有任何我们写入的标记 | 见 2.6 |

**结论**：现有接口**没有**可靠的轮次代次。因此：

1. 我们不能"识别旧结果"；
2. 我们能做的是"对处于已判本地状态的 key 一律压制"（EPOCH2），把**原厂执行**这条路堵死；
3. **归属错误无法消除**，只能计数与保留。

### 2.4 能力边界矩阵

把"我们放行"和"原厂真的执行"分开，因为原厂自己还有 C5（`isSessionValid(1,sid)`）：

| 旧结果到达时的情形 | 能否区分新旧 | EPOCH（七阶段） | EPOCH2（八阶段） | 真实执行风险 |
|---|---|---|---|---|
| 旧轮 sid ≠ 当前 sid | 能（原厂 C5 就拒了） | 放行 | 放行 | **无**（E7 数字：`exec=0`） |
| 旧轮 sid = 当前 sid，新一轮已判本地 | **不能** | **放行 → 执行** | 压制 | EPOCH 有，EPOCH2 **无** |
| 旧轮 sid = 当前 sid，新一轮已登记 AI | **不能** | 拦截 | 拦截 | **无原厂执行**，但归属错（E4） |
| 同 key 槽位已过 TTL / 被容量驱逐 | 不能 | 放行 | 放行 | **有残留**（E5） |

E7 的结论也一并记录：**"放行 ≠ 执行"**，危险区间被原厂 C5 从"所有跨会话"收窄到"同一 sid 的连续两轮"。这一点让 EPOCH2 的收益比看起来更大。

### 2.5 剩余风险（明确保留，不宣称解决）

| # | 剩余风险 | 性质 | 当前影响 | 收口条件 |
|---|---|---|---|---|
| R-1 | 旧结果在新一轮 AI 登记之后到达 → 被当成新一轮结果交给接管路径 | 归属错误 | takeover 未开启，接管路径当前只计数/记录，无实际动作 | 需要真正的轮次代次（2.6） |
| R-2 | 压制状态在 TTL 之后消失，极端迟到的结果仍会放行 | 时间边界 | 窗口长度 = 既有 TTL(30 s)，不是新引入的常数 | 需要设备侧延迟分布数据（仍待测） |
| R-3 | 容量驱逐（64 槽）→ 槽位消失 → 退化为未登记 | 容量边界 | 同 R-2 | 需要容量上调或驱逐策略改造（P1） |
| R-4 | 本地判定压制可能吞掉"本该放行"的结果 | 功能 | 表现为该轮无反应 | 需要审查确认策略取舍（2.2） |

**不做的声明**：本轮**没有**宣称 EPOCH 跨轮问题已解决。已解决的部分只有一句：`type=3` 之后的旧结果不再因为"本地判定释放槽位"而进入原厂执行路径；**归因**仍然不可判定。

### 2.6 若要真正做代次识别，需要什么（下一轮候选，不在本轮范围）

1. **设备侧只读观测**：在 `tg_nlp_cb` 里把 `Message` 的 `what/arg1/arg2/obj` 与 `NlpResult[+140]` 一起打印，看同一次 `onStream` 到结果回来之间，是否有任何字段是**每轮唯一**的。这是纯读操作，不改行为。
2. **继续逆向 `NlpResult` 剩余字段**：152 字节里找出可能的序号/时间/请求 id。
3. **自建 token 的回传通道**：只有在 1 或 2 证明存在可回传字段时才有意义；否则任何"我们记一个轮次号"的方案都传不进结果。

在这三条任一成立之前，EPOCH2 的"一律压制"是唯一能保证不误执行的方案。

## 三、任务二（P0-2）：三点安装的部分写入

### 3.1 模型改造：8 字节 = 两次 4 字节字写

第七阶段把 `install_one()` 写成"写两个字"的**不可分割**操作，并在最后才 `applied[i]=1`。这掩盖了三件事：字写可以中途失败、失败后入口处于**半补丁**状态、回滚按 `applied[]` 判断会**跳过**这个半补丁入口。

新模型：

```c
static int w_write(world_t *w, int i, int wi, unsigned long v)
{
    w->word_writes++;
    if (w->f.fail_install[i][wi]) { w->word_write_fail++; return -1; }  /* 该字未写入 */
    w->mem[i][wi] = v;
    return 0;
}
static int install_point(world_t *w, int i)
{
    if (w_write(w, i, 0, PATCH_JMP)) return -1;      /* ldr pc,[pc,#-4] */
    if (w_write(w, i, 1, TRAMP[i]))  return -1;      /* 半写：字 0 已是补丁 */
    return 0;                                        /* applied[] 由调用者在读回后置位 */
}
```

**建模前提（写清，避免"未经证明的假设"）**：ARM32 上**地址对齐的 32 位字存储是原子的**（不会出现"半个字"），所以最小的可观测中间态就是"字 0 已是跳转、字 1 仍是原序言"。8 字节补丁因此必须按两次字写建模，不存在把它们当一次原子操作的合法理由。

### 3.2 恢复判据：从 `applied[]` 改为实际字节

```c
static int needs_restore(const world_t *w, int i)
{ return w->mem[i][0] != ORIG[i][0] || w->mem[i][1] != ORIG[i][1]; }
```

```c
for (i = NPTS - 1; i >= 0; i--)
    if (needs_restore(w, i)) restore_point(w, i);   /* applied[] 完全不参与 */
```

状态只由**字节验证结果**决定：

```c
w->state = all_orig(w) ? ST_FAILED : ST_ROLLBACK_FAILED;
```

`install_recover()` 只允许从 `ROLLBACK_FAILED` 进入；成功后才把 `applied[]` 按字节清零。

### 3.3 故障矩阵与结果（审查要求的 6 类逐条对应）

| 审查要求 | 对应场景 | 关键断言 | 结果 |
|---|---|---|---|
| 第一字成功、第二字失败 | `S3.0/1/2` | `applied[i]==0` 但 `at_rollback[i]` 真的是 `PATCH_JMP \| ORIG[1]`（半写）；`restore_writes >= (i+1)*2` 证明**没有跳过**；回滚后 6 字逐字等于原序言 | PASS |
| 第一字失败 | `S2.0/1/2` | 该入口未被触碰；`applied[i]==0`；全部回滚到原字节 | PASS |
| 读回只有一字不匹配 | `S4.0/1/2` | `rb_fail>0` 触发回滚；`applied` 未置位；6 字恢复 | PASS |
| 回滚时第一字成功、第二字失败 | `S5.0/1` | `ROLLBACK_FAILED`；`restore_pending[i]==1`；该入口**可证明非原值** | PASS |
| 回滚失败后再次恢复 | `S5`（两次尝试）+ `S6` | 第一次（故障仍在）→ 仍 `ROLLBACK_FAILED`；清除故障后 → `RECOVERED` 且 6 字全等；第三次调用被拒（非法状态迁移） | PASS |
| 已部分写入但 `applied` 未设置 | `S3` | 上述"半写 + applied==0 + 仍被回滚"三连断言 | PASS |

补充场景：

| 场景 | 内容 | 结果 |
|---|---|---|
| `S0` | 无故障：`DONE`，6 次字写、12 次字读（逐点读回 + 组读回），3 点 `applied=1` | PASS |
| `S1*` | 预检字节不符 / 冻结失败 / 停止的 PC 落在入口区间：`word_writes==0`，一个字节都没写 | PASS |
| `S5b` | 恢复写的那个字**本来就等于原值**（安装时从未写过）→ 字节判据应当认定"已恢复"（`FAILED`，不是 `ROLLBACK_FAILED`） | PASS |
| `S7` | 安装故障 + 恢复故障叠加 | PASS |
| `S8` | 只有需要恢复的入口才被恢复（3 点 × 2 字 = 6 次恢复写，不多不少） | PASS |

`S5b` 值得单独说：它证明"以字节为判据"不是形式主义 —— 如果按 `applied[]` 或按"某个写调用失败了"来判断，就会把一个**本来就干净**的入口报成 `ROLLBACK_FAILED`，从而永远无法收敛。字节判据同时要防止"假失败"和"假成功"。

### 3.4 事务状态机

```
IDLE
 └─> PRECHECK        预检：6 个原字节 + 冻结结果 + 停止点 PC
      ├─ 任一不符 ─> (返回非零, 状态保持 PRECHECK, 0 次写入)
      └─> FROZEN
           └─> INSTALLING   逐点：字0 -> 字1 -> 逐点读回 -> applied
                ├─ 任一步失败 ─> ROLLING_BACK
                └─> (组读回：全部 3 点再读一遍)
                     ├─ 不一致 ─> ROLLING_BACK
                     └─> DONE
 ROLLING_BACK   逆序，按 needs_restore(实际字节) 决定是否恢复
      ├─ 全部逐字等于原序言 ─> FAILED
      └─ 仍有入口非原值   ─> ROLLBACK_FAILED  ── install_recover() ──> RECOVERED
                                                        └─ 仍失败 ─> ROLLBACK_FAILED（可重试）
```

四条不变式（每个场景都跑，共 5 条断言/场景）：

- **I1** `DONE ⇒ 3 点全部读回为补丁态`，且**没有任何入口处于"字 0 补丁 / 字 1 原值"的混合态**；
- **I2** 任何失败都不会以 `DONE` 结束；`ROLLBACK_FAILED` 以外的失败态**不留下补丁**；
- **I3** `FAILED`/`RECOVERED ⇒ 6 个字逐字等于原序言`；
- **I4** `ROLLBACK_FAILED ⇒ 至少一个入口可证明非原值`（不允许"假失败"卡死）；
- **I5** `半安装被报告为成功` 计数恒为 0。

### 3.5 工程实现缺口（保持第七阶段结论，且更具体）

`nlu_patch` 现在是**单点**事务。三点覆盖需要一个 `np_group`：3 个补丁点 + **一次**冻结 + 逆序回滚 + **组级读回**，且必须满足：

1. `applied[]` 只作为缓存，恢复判据一律用 `memcmp(entry, ORIG, 8)`；
2. 逐字写 + 逐字读回，不用 8 字节原子假设；
3. `ROLLBACK_FAILED` 必须能被重复恢复，且恢复后按字节清零 `applied`；
4. 组读回失败也要回滚（不能只有逐点读回）。

规模估计 150–220 行，建议在 T8-13 单独立项。
