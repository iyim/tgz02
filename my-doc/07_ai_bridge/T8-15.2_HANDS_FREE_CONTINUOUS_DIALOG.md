## 1. `duplexDialogRenew`：能上线，但不是开关（否定结论，有证据）

本轮先按要求用 TTS 守卫在 `SessionManager::onStopTalk` 入口写入续听时长并原样装到真机：

```
21:31:10.881  tgt: renew: self=0xb22f4dcc pre=0 set=8000 n=1
21:31:10.884  SessionManager(onStopTalk，send end frame payload)  duplexDialogRenew": 8000
21:32:06.534  tgt: renew: self=0xb22f4dcc pre=0 set=8000 n=2      ← 上一轮的值已被原厂清零
```

- 写入点正确：值确实进了本轮 EOU 帧，`pre=0` 证明原厂在 `0x113a5c` 清零、字段被消费（证据等级 B）。
- **结果：服务端没有任何续听动作**，这一轮结束后平台照常 `exitTalk`，第二句无人听（证据等级 B）。
- 对照：**原厂自己成功续听的那一轮，发出的 `duplexDialogRenew` 是 `0`**（`evidence/t8-15.1/device_relisten_probe.log` 21:12:01.525）。⇒ 这个字段不是续听开关，续听不依赖它。

**修正 T8-15.1 的一处推断（等级 C → 已被 B 推翻）**：原厂续听不是"服务端 1102 通知驱动"，而是**客户端本地**流程：

```
21:12:01.581 AGSpeechEngine: handleWakeupPromptFinish,895
21:12:02.220 AGSpeechEngineProxy: startTalk,506:[NearbyWakeup] type:continuity, wakeupWord:(null)
21:12:02.235 AGSpeechEngine: onListenStarted → onStartTalk wakeupType=1
```

`handleWakeupPromptFinish` 的两次打印就是"提示音开始播 / 播完"。原厂做法：识别不到命令 → 播提示音 → 播完 → 本地 `startTalk(continuity)`。

## 2. 真正的入口：`GenieApi::startTalk(type=continuity)`（本轮已打通）

### 2.1 静态：结构体 +0 才是类型

`AGSpeechEngineProxy::startTalk(_WakeUpInfo_*)`（libsmartbox `0xe90a8`，2136 B）：

```
e9108: ldr r0,[r1]        ; info+0 = 类型枚举
e910c: str r0,[sp,#104]   ; 写进本地副本 -> 之后成为会话的 wakeupType
e9110: bl   <type->name>  ; 日志里的 "type:continuity"/"type:active" 就是它
e9120: ldr r1,[r5,#4]     ; info+4  = wakeupWord   (char*)
e9134: ldr r1,[r5,#8]     ; info+8  = wakeupFilterWord
e9148: ldr r0,[r5,#24]    ; info+0x18 = vadtime
```

⇒ `_WakeUpInfo_`：`+0x00 int type`（0=active，1=continuity）、`+0x04 char* wakeupWord`、`+0x08 char* wakeupFilterWord`、`+0x18 int vadtime`。

**第一次真机实验（全零结构体）的失败被这条解释**：`startTalk` 确实开麦了，但打印 `type:active`、会话 `wakeupType=0`、`wakeupWord=` 空，服务端 20 s 后回"无指令"，一句都没听到（session 1969862）。
**把 `+0` 置 1 后**，日志与原厂逐字段一致：`type:continuity, wakeupWord:(null)`、`onListenStarted,696: 1, , ,`、`wakeupType = 1`。

### 2.2 调用方式（可撤销、默认关闭）

| 项 | 值 |
|---|---|
| 载体 | 既有 `libtg_ttsguard.so`（已在 `:core` 内，符号+偏移+序言三段校验，失败即拒绝安装） |
| 入口 | `libsmartbox+0xfcff8`（本地符号，dynsym 无）；序言 `E92D4830 E28DB008` 必须匹配 |
| 参数 | `startTalk(1, &info)`，`info` 全零 + `+0=1`（88 B，与官方 JNI 同形状，**不是 NULL**） |
| 开关 | `/data/local/tmp/t7/renew.conf`：`continuity_enable=0/1`、`continuity_auto=0/1`、`continuity_type=1`、`continuity_auto_max=12` |
| 默认 | 文件不存在 ⇒ 全关；`continuity_enable=0` ⇒ 线程不启动、入口不解析 |
| 失败方向 | 入口校验不过 ⇒ 只关续听，**TTS 守卫照旧安装**（守卫缺失会让原厂回答盖住我们的回答，比不续听严重） |

### 2.3 自动触发时机（关键）

手动触发（宿主写计数器）先验证了通道；随后补上自动触发，读 T5 TTS 执行器发布的 `play.public.json`：

```
state → idle 且 finished_ms 变化  ⇒  我方这一条 TTS 真的播完了  ⇒  立即 startTalk(continuity)
```

- 原厂回答被守卫拦在 `onTtsStart`，不会产生这个变化，所以只会对**我方回答**触发。
- `:core` 的 SELinux 域**不能写/删** `/data/local/tmp/t7`（实测 `avc denied write/unlink`，permissive），所以触发通道改成**只读**：`:core` 只读文件，不写任何东西。
- 轮询 120 ms；`continuity_auto_max` 默认 12 次封顶，超限后彻底安静（不会无限开麦）。

**踩过的坑（已修，写下来免得复现）**：
1. `strtol` 在 ARM32 是 32 位，`finished_ms`（1.79e12）被截成 `LONG_MAX` ⇒ 恒等、永不触发；改 `strtoll` 后立刻正常。
2. `uninstall` 停掉轮询线程后 `install` 不重启（`g_cont_started` 残留）⇒ 改写为等待线程退出（≤500 ms）+ 允许重启，避免出现"第二个线程重复开麦"。
3. 计数器必须**严格递增**（守卫只比较变化）：宿主侧改用 unix 秒。

## 5. 尚未解决 / 下一步

1. **音量的逐项回归没做**：本轮只验证了唤醒/ASR/退出语，音量、静音、播放暂停没在连续对话中逐条复测。
2. **`onListenStarted,696` 后三个字段与原厂有差**：原厂 `1, , , 0.000000, 0, 1, -1`，我们 `1, , , 0.000000, 0, 0, 0`（疑似 vadtime/标志位）。实测不影响识别，但含义未查清。
3. **自动续听没有"页面黑名单/打断"策略**：现在只要我方 TTS 播完就开麦，最多 12 次。原厂 `disableAppPages` 那套我们没有对齐。
4. **重复开麦风险**：若用户在我方 TTS 期间又说了一句，原厂那一轮会先被识别并走原厂意图；自动续听仍会在播完后补一次开麦。需要用真机复测"边播边说"。
5. **HUD/提示音**：原厂续听前有提示音，我们这条路径没有提示音（用户可能不知道麦开着）。是否补提示音要产品决定。
